## 1. 跑法（可复现）

```bash
export DEEPSEEK_API_KEY=...            # 主模型
export AS_BYPASS_API_KEY=...           # 旁路（可同一个）
export AS_ENABLED=1 AS_DEBUG=1 AS_MAINT_EVERY=1
export AS_DB=.../e2e.db PI_HOME=.../e2e-home

pi -p -e ./pi/src/index.ts --session-id as-e2e \
   --session-dir .../sessions --no-builtin-tools "<提示词>"
```

`AS_MAINT_EVERY=1` 是为了把维护节拍压到每轮一次（否则要 10 轮才轮到降权）。
`--no-builtin-tools` 是必须的：否则模型会去读仓库文件，"它凭什么知道"就没有说服力。

**六轮对话**：① 记住项目信息 → ② 问项目名（验注入）→ ③ 复杂迁移请求（验立计划）→
④ 报"第 1 步做完了"（验 `STEP`）→ ⑤ 追问计划原文（验视图注入）→ ⑥ 长接口规格（验 `summary`）。

## 2. 逐项证据

### 2.1 计划区：一条完整链路

```
as/plan {"action":"created","goal":"把缓存层从 Redis 迁到进程内 LRU 并安全上线","steps":5}
as/plan {"action":"step_done","steps":[1]}
```

库里最终状态：

```
steps: [
  '✓ 盘点 Redis 全部使用点并记录命中率/P99/内存基线',
  '实现进程内 LRU 并对齐 TTL/并发/淘汰语义，以影子读+双写过渡',
  ...
]
```

**视图注入的硬证据**：第 ⑤ 轮问"你上下文里那份【当前计划】的 5 个步骤是什么"，模型回答里出现
**"把缓存层从 Redis 迁到进程内 LRU 并安全上线"**——这串字**只存在于 `plan` 表**，
用户从未说过（用户原话是"从 Redis **迁移**到进程内 LRU"，没有"并安全上线"）。
它还说"不是 0/5，是 **1/5** 已完成"，与库里 `✓` 的数量一致。

⇒ `withPlan` 的视图注入 + `completeStep` 的推进，两者都是真的在跑。

### 2.2 降权：第一次真跑

```
as/decay {"decayed":1,"ids":["m-mwkpifkc-2"],"at":1794920857730}
```

被降的是 40 天没被用过的那条（`salience 0.90 → 0.77`，正好 ×0.85），
新写入的与近期用过的都没动。`gapDays` 闸生效：同一批次里后续轮次不再重复降。

### 2.3 A10：跳过的都是"刚说过"的

```
as/inject_skip {"count":3,"ids":["m-mwkpjrbb-1","m-mwkpl09e-1","m-mwkpiflh-3"]}
```

四次跳过，全部发生在"同一句话刚被说过/刚被注入过"之后。**这是记录 2 末尾那个老账的正面回执。**

### 2.4 R5：机制对了，措辞没落地

工具被调了两次（`as/archive_query {key:"2025-03", refs:0}`、`{q:"缓存方案 讨论", refs:0}`），
两次都返回 `【取不回来】…不要补全细节…请对方给线索`。
模型的行为是**要线索**（R4），不是复述这句话。

**判断**：不算失败。R5 的目的是"不要硬猜"，这一点达成了——它一个字都没编。
但"承认不可恢复"这层语义没有传导到用户面前，属于**提示词层面待优化**（见记录末尾）。

## 3. 抓到的两个真 bug

### 3.1 `judgeDoc` 的 promise 没人持有，`-p` 退出时被砍掉

**现象**：187 字的长条目写进库了，`doc_verdict` 与 `summary` 却是空的。
**根因**：`void judgeDoc(...)` 是 fire-and-forget；`pi -p` 在 turn 结束后立刻退出，
那条 await 中的 fetch 直接被中断。`pendingWrapup` 有人等，转存判断没有。
**修法**：`trackDoc()` 把 promise 收进 `pendingDocs` 集合，`session_shutdown` 里 `Promise.allSettled` 等一次。
**复验**：`AS_SEED` 播种 269 字条目 → `doc=doc`、`summary=记录了 GET /v1/orders 的接口规格…`。

> 这条只影响"短进程"（`-p`、脚本调用）。TUI 长会话里它会自然完成——所以单测和人工试用都看不见。

### 3.2 信任键的路径写法不一致 → 开关"失败开"

**现象**：把会话设成 `untrusted` 后，写入照旧进库（`memory_entry 3 条`，`pending_write` 空）。
**根因**：测试脚本用正斜杠写键，宿主 `getSessionFile()` 返回反斜杠。
`getTrust()` 查不到记录 → 返回默认值 `trusted` → **写放行**。
**修法**：`store.trustKey()` 归一化（`\` → `/`），写读两侧都用；查询用 `IN (归一化, 原始)` 兼容历史行。
**复验**：反斜杠设、正斜杠读，两种写法都读到 `untrusted`；真会话写入 `memory_entry 0 条`、`pending_write 2 条`。

> 这不是"测试写错了"就完事的：**开关类判断查不到记录时的默认值，必须朝"不写"**。
> 归一化是治标，真正的原则是"失败要关"。这条记在这里，改别的开关时照抄。

## 4. 顺带发现（没修，留给优化阶段）

### 4.1 同义副本靠字面去重挡不住

六轮下来库里 18 条，其中大半是同一件事的不同说法：

```
用户的项目叫 Halcyon，缓存层用进程内 LRU
项目名 Halcyon，缓存层用进程内 LRU
用户的项目 Halcyon 缓存层使用进程内…
项目名 Halcyon，缓存层用进程内 LR…
```

`findSimilar()` 的二元组 Jaccard 阈值 0.82 挡不住"换个说法"。记录 20 当年测到 3 条，
是因为那时只有几轮；会话一长就会露出真实规模。

**影响**：召回结果被同类条目挤占（同叶只出一条能挡一部分，但没挂标签的挡不住）；
注入预算被浪费；`summary` 的意义也被稀释。
**方向**：写入时先按标签叶查"槽里现值"，把新事实交给旁路判 merge/supersede，
而不是只靠字面相似度——`memory_link` / `supersede` 的机制都在，缺的是"写入时用起来"。

### 4.2 模型会把"工具没匹配上"讲成"系统坏了"

第一轮模型调用 `memory({say:"记住…"})` 得到"没能在候选里对上号"，于是对用户说
"记忆系统当前没有可关联的既有记忆条目，导致无法落库"——而实际上 `as/wrapup` 那一轮
把内容写进去了（`remembered:1`）。**回执措辞需要让模型知道"写入另有通道"**，
否则它会基于错误前提向用户道歉。这是文案问题，不是机制问题。
