# 记录 46：显著性的评分机制（P19，2026-11-18）

> 依据：`01` §7 硬边界「**写进去绝不提升权重，只有被判真被用上（`USED`）才涨**」；
> `01` §5 的召回淘汰线 `MIN_SALIENCE = 0.15`；`03` §2 的「降权 → 可恢复权重」；
> `08` C 表 `salience` 一格 🟡「写入常量 + 判用加分 + 批量降权，无评分旁路」；
> 降权的原始设计见[记录 26](26-decay-and-link-filter.md)。
> 本篇记：为什么原来的三件套不算"评分模型"、新的绝对分怎么算、它和降权怎么共存。

---

## 0. 一句话

> `salience` 从"三个各写各的数"变成**一个可复算的函数**：输入是库里的可测信号
> （判用次数、最后一次判用、写入时刻、pin、自身 trust、连接数），输出是 0–1 的
> 绝对分与一句话理由。**写入不进公式**，判用是唯一加分项，闲置按 90 天半衰期
> 向地板 0.15 收敛而永不跌破。评分取代降权成为默认口径（`AS_SALIENCE=0` 可退回）。

## 1. 原来的三件套为什么不算评分

| 动作 | 原实现 | 问题 |
|---|---|---|
| 写入 | `options.salience ?? 0.5`（旁路给 0.6 / 0.7 / 0.8） | 没有依据，是"猜的初值" |
| 判用 | `MIN(1.0, salience + 0.05)` | 线性累加：用 10 次 +0.5，与"用第 1 次"的权重相同 |
| 维护降权 | `MAX(0.15, salience × 0.85)` | 乘法，**不幂等**，必须靠 `meta.decay_at` 闸 |

三者没有共同量纲：`+0.05` 加十次与乘一次 `0.85` 之间没有任何可解释的关系，
也没人能回答"这条 `0.63` 意味着什么"。更要紧的是**没有统一的输入**——
写入看旁路的猜测，判用看历史累加，降权看当前值，同一个事实在三处被三种方式定价。

`08` C 表标 🟡 的理由就是这句：**"有加减乘，没有模型"**。

## 2. 分数怎么算（`src/salience.ts`）

纯函数 `scoreSalience(signals) → { score, reason }`，无 IO、无副作用、可单测。

```
证据 = 0.45 + 0.40 × (1 − 0.5^(判用次数 / 3)) + 连接加成(≤0.05，仅当判用过)
因子 = pinned ? 1 : 0.5^(闲置天数 / 90)
分   = 0.15 + (证据 − 0.15) × 因子
上限 = 0.5 + 0.5 × trust              ← 可信度只当天花板
分   = min(分, 上限)；pinned 时 max(分, 0.60)
```

### 2.1 基线 0.45：为什么低于中性的 0.5

一条从没被用过的条目**没有证据**支持"至少中性"。取 0.45 是"略低于中性"，
差值刻意压到 0.05：存量条目第一次评分会整体下移这么多，但离召回线 0.15 还很远，
**不改变任何一条"能不能被召回"**，只改排序里的细微位次。

**为什么允许它低于写入常量 0.5**：写入常量是旁路猜的**初值**，评分是证据给的**收敛值**。
初值高一点没代价（只影响"还没被评过分"的那段时间），长期起作用的是收敛值。

### 2.2 判用是唯一加分项，且递减、有上限

- 半衰期 3 次：第 1 次涨 0.091，第 3 次累计 0.20，第 9 次 0.35。
- 增量上限 0.40，所以证据满分是 `0.45 + 0.40 = 0.85`，**永不封顶到 1.0**——
  分数一旦到 1.0，再多用几次也没地方可涨，反馈就断了。留的 0.15 空档也是给
  可信度天花板与未来新信号的。

之所以刻意递减：一条事实被用上 10 次与 11 次之间的差别，远小于 0 次与 1 次之间。
线性累加会让"被反复提及的常识"长期霸占排序顶部——那正是 `CONFIDENCE_BY_ORIGIN`
的注释里警告过的形态（"反复复述的模型推断看起来像用户亲口说过的事实"）。

### 2.3 硬边界怎么落实（`01` §7）

两条，都是结构性的，不靠自觉：

1. **"写入"不在输入里**：`SalienceSignals` 里没有"写了几次"。`useCount` 只由
   `touch()`（判用）推进，`add()` 把它初始化成 0。
2. **基线与来源、篇幅、标签无关**：同一组证据 → 同一个分。要越过基线只有一条路：
   `useCount > 0`。

单测 1a–1f 钉这条：算两遍相等；新条目恰为基线；**多写一条不改变已有条目的分**；
新写的那条也只是基线。

### 2.4 闲置衰减：90 天半衰期，收敛到 0.15

衰减作用在**高出地板的那部分**上：`0.15 + (证据 − 0.15) × 因子`。
所以无限久不用会收敛到 0.15，而不是 0——与 `decay()` 的 `floor`、`recall()` 的
淘汰线三者同源。`store.ts` 的 `MIN_SALIENCE` 现在直接引用 `salience.ts` 的
`SALIENCE_FLOOR`，不另抄一份（两个 0.15 一旦漂移，"地板"就只是其中一边的意见）。

半衰期从旧的"30 天起每天 ×0.85"改成"连续衰减、90 天减半"，理由是节奏不同：
旧口径是**离散乘法**，30 天只是"开始扣"的门槛，之后约 12 天就到底；
新口径从写入那一刻连续算，若半衰期仍取 30 天，一条季度性记忆（每季度用一次）
会在两次使用之间被压到地板。

### 2.5 可信度只当天花板，不当加项

`recall()` 的排序是 `relevance × salience × trust`，trust 已经乘过一次。
评分里再把它加成加项，同一个信号就被算了两次（平方效应）。
上限的作用只有一个：**低可信条目不可能仅靠反复被用就爬到顶格**——
`trust 0.5`（model）的上限是 0.75，`trust 0.9`（user）是 0.95。
单测 2f/2g 钉这条。

### 2.6 不用"有效 trust"（含一跳污点）

污点是**关系图的函数**：加一条边就变。把视图层的东西固化进 `salience` 这一列，
等于让"加边"悄悄改了"事实的权重"——而 `salience` 是要落盘、要被审计、要被回放的。
污点仍然在召回时生效，那才是它该待的地方。

### 2.7 连接数：小权重，且只给判用过的条目

加边也是写（`addLink` 是 `relation.write`）。若"多连几条"就能提分，等于给写入
开了一条绕过硬边界的侧门。所以连接加成只对 `useCount > 0` 生效，上限 0.05，
饱和在 6（双向边会被数两次，即 3 条显式边）。单测 1d 钉"没用过时连接不带来任何加分"。

### 2.8 pin：抬下限，不是加分

pin 是**人的动作**（既不是写入，也不是判用），它表达"这条不许沉底"。所以：

- 不参与闲置衰减（否则十年后它照样沉到 0.15）；
- 地板 0.6，且地板在可信度上限**之后**应用——pin 抬的是"不许沉底"，不是"更可信"。
  信不信仍由 `MIN_TRUST` 与召回的 trust 因子管。

## 3. 与降权（`decay`）的关系

两者算的是**同一个字段的两个方向**，算法不同：

| | `decay()` | `rescore()` |
|---|---|---|
| 算法 | 在当前值上乘 `0.85` | 按证据重算绝对值 |
| 幂等 | 否（靠 `meta.decay_at` 闸） | 是 |
| 输入 | 当前 `salience` | **不使用**当前 `salience` |
| 覆盖范围 | `active AND pinned=0` 且闲置 ≥30 天 | 全部 `active`（pin 由模型处理） |

**它们不能同时生效**：`rescore()` 不读当前值，所以谁后跑谁就是最终值。
若两者都跑，评分刚写下的绝对值会被下一轮的 `×0.85` 再压一次——
"闲置即降"被算了两遍，而该降多少变成"评分节拍与降权闸的相对频率"，没人能解释。

所以 `index.ts` 里是**二选一**：

```ts
if (salienceOn) { asTouch.rescore() } else { asTouch.decay() /* 记 as/decay */ }
```

- 默认评分：绝对分已经把闲置衰减算进去了，降权是它的一个特例。
- `AS_SALIENCE=0` 退回旧口径：留给"想保持既有分数分布"的库，**不迁移任何已有数据**。

`decay()` 本身**一行没改**，`store-forgetting` / `wiring` 两组测试照旧全过——
旧口径仍可复现，只是不再是默认。

## 4. 与「叶 = 槽」的关系（`09` §4.4）

`rescore()` 只处理 `state = 'active'`。这与"叶 = 槽"的取代语义是同一条线：

- 被 `supersede` / `merge` 的旧条目**不参与评分**，它的分数停在被取代那一刻。
  若继续评分，一条"当年很重要"的旧值会在历史里显得比现值更重要——
  而 `recall()` 的同叶去重是"按分数选出该留的那条，再让现值压过分数"，
  分数本身不该反过来影响"谁是现值"。
- 因此分数只在**跨槽排序**里起作用；槽内的新旧由 `state` 与 `t_end` 决定，
  不由分数决定。这条边界不写清楚，很容易变成"谁分高谁是当前事实"。

## 5. 接线：能力表、审计、不删数据

### 5.1 能力分级（`08` D 表 B5）

新增两个写方法，都归 `memory.touch`（与 `decay` 同一类动作：改的是 `salience`）：

| 方法 | 能力 | 用途 |
|---|---|---|
| `setSalience(id, value)` | `memory.touch` | 单条入口，夹到 `[0.15, 1]` |
| `rescore(options)` | `memory.touch` | 批量入口，按证据重算 |

**两个都登记进了 `METHOD_CAPABILITY`**。漏登记的后果是那个方法不受闸，
而 `verifyCapabilityTable()` 会在构造时抛"能力表自检失败"——这是刻意的自检，没绕过。
单测 7a–7e 覆盖：开关开着时直调被拒、`memory.write` 作用域改不了权重、
`memory.touch` 作用域能评分。

### 5.2 审计：`as/salience`，只记 id 与分数

`rescore()` **自己**记审计（与 `decay()` 由调用方记不同）。理由：批量评分一次改的
是一整批绝对值，漏记就是一次无痕的批量改权重；而它幂等、可能在任意节拍被调用，
没有"每天至多一次"的天然上限可以依赖。

data 形状：`{ scanned, changed, items: [{ id, score }] × 前 10, at }`——
**不含正文、不含理由**（理由里只有信号名，但审计口径统一为"只留凭据"）。
前 10 条是日志长度约束，全量在库里可查（与 `as/decay` 只带前 5 个 id 同一口径）。

### 5.3 不删数据

评分只写 `salience` 一列。`state`、正文、`use_count`、`last_used`、`t_end`
一概不碰——单测 6e 与 `store-forgetting` 2g 各钉一遍。
`setSalience` 的夹取也是这条的下半句：库里不允许出现"低于召回线、却还留在池子里"的行。

## 7. 没做什么（都是有意留的）

1. **没有 `USED` 负例**。"被注入但没被用上"仍然不是一个信号：
   `injection_log` 只记注入，判否没有落笔。所以现在仍是"**闲置即降**"，
   只是从"批量乘法"换成了"按天连续衰减"。要细一档得先让负例落库（记录 26 §四的"仍缺"）。
2. **没有自动 pin**。`pinned = 1` 在本仓里没有写路径（只有测试用 SQL 直接改）。
   评分对 pin 的保护是为"将来有了 pin 的动作"准备的；今天它只影响手工改过的库。
3. **不看内容**。字数、摘要、`docVerdict`、标签深度都不进公式。
   "这条重不重要"由人判、由判用判，不由篇幅判——否则"写得长"就成了加分项。
4. **不重算非 active 条目**。见 §4：历史条目的分数停在被取代那一刻。
5. **不迁移存量分数**。第一次评分会把全库 `active` 条目收敛到模型的绝对分
   （多数会从 0.5 降到 0.45、从 0.8 降到 0.45 除非它被用过）。
   这是口径切换的必然结果，但没有写迁移脚本，也没有一次性跑全库：
   它按维护节拍、按 `limit` 分批发生。
6. **`decay()` 没删、没改**。它是 `AS_SALIENCE=0` 的退路，也是"两种算法可以对比"的凭据。
7. **`origin` 不进公式**。它是 `trust` 的来源，两者同时进就是同一信号两遍；
   它只出现在 `reason` 里（"user 基线，判用×3，闲置 120 天"），供人核对。
