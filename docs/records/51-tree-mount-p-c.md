## 1. 加了什么

```sql
CREATE TABLE tree  (id PRIMARY KEY, name UNIQUE, created);
CREATE TABLE mount (id PRIMARY KEY, parent_tag_id UNIQUE, tree_id UNIQUE, readonly, created);
ALTER TABLE tag ADD COLUMN tree_id TEXT NOT NULL DEFAULT 'main';   -- 判存在后才 ALTER
```

| 方法 | 能力 | 做什么 |
|---|---|---|
| `trees()` / `treeOf()` / `mounts()` / `globalPathOf()` | 读 | 查树、查归属、查挂载、算全局路径 |
| `ensureTree(name)` | `tree.write` | 建一棵空树（只建根标签） |
| `attachTree(parentTagPath, treeId, {readonly})` | `tree.write` | 挂载 |
| `detachTree(treeId)` | `tree.write` | 卸载（只删 `mount` 行） |

### 1.1 `tree.write` 为什么单独一项能力

维护旁路持有 `relation.write`（它能改标签：合并、上提、剪枝）。
但**它不该能挂一棵外来的树**——那一下会让一整棵树的记忆突然变得可达，量级完全不同。
能力分开，闸才分得开（记录 42 的那道闸按能力生效）。

### 1.2 `add` 多了 `treeId`

不加的话，子树里**只能有枝、不能有记忆**——挂载就没有意义了（挂过去一个空目录）。
加上之后，老调用点一字不改（省略 = 主树）。

---

## 2. 为什么不用重建 `tag` 表

`tag.path` 是 `TEXT NOT NULL UNIQUE`。看起来多棵树会撞（两棵都有 `项目`），
但**每棵树的路径都以自己的根名开头**：`记忆/项目` vs `碧蓝航线/项目`——天然不撞（`09` §8.3）。

所以只需要 `ALTER TABLE tag ADD COLUMN tree_id`（有默认值，老库直接过）。
代价是一条新约束：**根名必须全局唯一**（`tree.name UNIQUE`，且与已有 `tag.path` 不撞）。
`ensureTree` 把这两条都提前挡住了，而不是等 `INSERT` 撞 `path UNIQUE` 时报一个看不懂的错。

---

## 3. 全局路径 vs 树内路径（这一期最容易混的一对）

```
AI 看到的：  记忆/项目/碧蓝航线/舰船/企业      ← globalPathOf()，算出来的，不落库
库里存的：         碧蓝航线/舰船/企业          ← tag.path，树内路径
```

**为什么不落库**：全局路径会随挂载点变化，落库就要级联更新所有子孙。
而 `tag.path` 是稳定的，`(tree_id, path)` 才是身份。

`globalPathOf` 的实现是"往上走"：查标签所在树 → 若不是主树，找挂它的 `mount` →
把挂载点的全局路径当前缀 → 递归。因为「一棵树只挂一处」+「不许成环」，这个递归一定终止。
**坏库兜底**：带 `seen` 集合，环上停下返回 `undefined`，不死循环。

## 4. 五条拒绝（每条对应一条约束）

| 拒绝 | 理由 |
|---|---|
| 树不存在 | 挂一个不存在的东西没有意义 |
| 树是主树 | 主树是命名空间的根，不能被挂到自己的枝下 |
| 挂载点不存在 | 挂载点必须是**真标签**——这样它能被继承、剪枝，也能挂自己的记忆 |
| 该点已挂 / 该树已挂 | `mount` 的两条 UNIQUE：一个点只挂一棵、一棵树只挂一处 |
| 成环 | 否则路径解析与祖先继承死循环（`treeChainOf` 判） |

「一棵树只挂一处」是刻意的，理由与 filesystem 的 bind mount 不同：
bind mount 是"同一份数据多个入口"，而我们的**位置是身份**——多挂会让"这条记忆在哪"有两个答案（`09` §8.2 约束 3）。

## 5. 两处**已知边界**（写进测试，不是忘掉）

### 5.1 召回还没有"可达树"过滤（P-d）

写完 P-c 时，未挂载的树里的记忆**照样会被 `recall` 召回到**——
因为 `recall` 压根不知道"树"这回事（它按 `tag.path` 段名匹配，而树内路径照样能匹配）。

测试第 9 组专门断言了这一点：

```js
check('9b 未挂载时 recall 仍能召回它（P-c 如此，P-d 才加"可达树"过滤）', ...)
```

**为什么要在测试里断言一个"缺陷"**：如果只写在记录里，下一个人读代码会觉得
"有了 mount 就该解耦了"。断言把它变成会红的事实——等 P-d 做完，这条测试改成反向断言。

### 5.2 嵌套挂载待 P-d

`attachTree` 的 parent **只按主树路径解析**（`记忆/...`）。在子树里再挂一棵需要按**全局路径**解析，
那要配一个 `resolveTag()`（全局路径 → 标签 id，逐段跨挂载）。现在硬做会得到一个
"路径有两种含义"的半成品，所以明确不做。

判环的代码（`treeChainOf`）已经按"可以嵌套"写好了——P-d 打开嵌套时不用改它。

## 7. 这一期**没做**什么

- **召回的可达树过滤**（P-d）：见 §5.1，测试里断言了它还没做。
- **`resolveTag()`（全局路径 → 标签 id）**（P-d）：嵌套挂载的前提。
- **注入渲染用全局路径**（P-d）：现在渲染用的是 `tag.path`（树内路径）。
- **挂载的人侧命令**（`/as-mount` 之类）：P-c 只到 store 层，命令等 P-d 一起接——
  否则挂上去了召回也不认，等于给用户一个"挂了没反应"的命令。
