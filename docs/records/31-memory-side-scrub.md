## 一、为什么库侧必须脱敏

注入是一条闭环，脱敏只在其中一环做，等于没做：

```
旁路写入 ──→ memory_entry.text（SQLite，明文）
                     │
recall / 联想 / 摘要 ─┘
                     ↓
                inject.render → 模型上下文
```

- 记录 23 的 `applyRedactions` 作用在最右端：它改的是**这一次请求的视图**。库里那张表
  一个字节都没动（这是它的设计前提——"存档即真相，视图可复算"）。
- 于是同一条密钥有三次机会漏出去：下一轮**召回**又把它捞回来、**联想边**把它从邻居带出来、
  **摘要**（`mode='summary'`）把它再转述一遍。更糟的是模型读到明文后会把它写进新条目，
  派生扩散。
- 反过来看，库侧是唯一"作用在数据本身"的位置：写进去时替掉，之后无论召回、联想、
  摘要、导出、`grep` 二进制页之外的一切路径，拿到的都是占位符。

`03` §2 的定义决定了它**不是删除、也不是 suppress**：

> 脱敏 | 敏感内容替换或屏蔽 | 原始受权限保护

条目还在、`state` 还是 `active`、还能被召回——只是敏感的那一截变成了占位符。
`03` §1 的铁律「遗忘不含删除」在这里体现为：**结构全留，只替片段**。

> **一处必须说清的取舍**：库侧脱敏是**破坏性**的。视图可以回放，落库的占位符回放不出原文
> （原文只在会话存档/来源侧）。这正是 `03` §2 表格里"原始受权限保护"那一列的意思——
> 库不再持有原文，也就不需要"从库里取回原文"的权限模型。代价是**写错了没法从库里撤回**，
> 所以规则必须保守（下一节）。

## 二、规则清单与误伤边界

八条规则，全部只认**形态**，不做语义猜测（`redact.ts` 的 `SCRUB_RULES`）。

| `kind` | 形态 | 替哪一段 |
|---|---|---|
| `private-key` | `-----BEGIN [RSA ]PRIVATE KEY-----` 到 `-----END …-----` | 整块 |
| `sk-token` | `sk-` + 前缀后 ≥20 字符 | 整段令牌 |
| `github-token` | `ghp_` / `github_pat_` + ≥20 字符 | 整段令牌 |
| `slack-token` | `xox[baprs]-` + ≥10 字符 | 整段令牌 |
| `bearer` | `Bearer <token>` | 只替 token，`Bearer` 留着 |
| `auth-header` | `Authorization: <value>`（含 `Basic xxx` 两段） | 只替值，头名与冒号留着 |
| `password` | `password=` / `passwd=` / `pwd=` / `secret=` 后面的值（≥3 字，可带引号） | 只替值，键名、分隔符、引号原样 |
| `base64` | ≥32 字符的 base64/hex 形态，且**大写、小写、数字齐全** | 整段 |

四条抑制误伤的手法：

1. **长度门槛**：`sk-` 前缀后不足 20 字、`secret=` 值不足 3 字一律不动（单测 4c / 9b）。
2. **前置边界**：`(?<![A-Za-z0-9_-])sk-` 让 `task-key` 里的 `sk-` 不算凭据。
3. **负向断言**：占位符自身不匹配（`(?!\[已脱敏)`、token 字符集不含 `[`），**幂等靠它**——
   对已脱敏文本再跑一次，输出一字不改、`hits` 为空（单测 6b / 6c）。
4. **重叠只替一次**：命中按起点排序、同起点取更长者，落在已接受区间内的丢弃。
   所以 `Authorization: Bearer sk-…` 只产生一个占位符，不会被啃成三段。

**明确放过的三类**（宁可漏）：

| 形态 | 为什么放过 |
|---|---|
| 散文里的 `password` 一词（不带 `=` / `:` 与值） | 单测 5a：这是正常技术讨论，替了等于毁掉一条记忆 |
| 纯小写 hex（md5、40 位 git sha） | 单测 5c：那是**标识符**不是凭据。要覆盖它就得把判据放宽成"字母 + 数字"，会把哈希、commit、内容摘要一起卷进来 |
| 短串（<20 的 `sk-`、<8 的 bearer 值、<3 的 `pwd` 值） | 阈值以下的"像"不足以支撑破坏性替换 |

**误伤边界一句话**：这套规则只敢替"长得就像凭据"的东西；`sk-` 这种前缀本身就是强信号，
所以它比 base64 那条激进（后者给了开关，见第四节）。

## 三、接入点：三处写路径，两张表刻意不接

| 位置 | 行为 |
|---|---|
| `store.add()` | `scrubSecrets(text)` → 落库用替换后的文本；`span` 按替换后的长度派生；命中则在 INSERT 成功后记 `as/scrub`；返回的 `MemoryEntry` 带可选 `scrubbed: string[]`（种类列表） |
| `store.addInSlot()` | 不复刻逻辑——它内部调 `this.add()`，脱敏自然生效（单测 13a / 13b） |
| `store.setSummary()` | 摘要先脱敏**再**截 120 字（反过来会让截断点落在占位符中间）；UPDATE 真的改了行才记审计（单测 14a–14c） |

**为什么摘要也要过一遍**：摘要会被注入（`mode='summary'` 优先读它，记录 30），而且它是
旁路从正文"转述"出来的——正文里刚被替掉的密钥，很可能在摘要里再出现一次。

**刻意不接的两张表**：

| 表 | 为什么不动 |
|---|---|
| `anchor`（L0/L1/L2 锚点） | 那是**身份层**，且只允许 `human` / `maintenance` 写（`addAnchor` 白名单）。替它等于代码改人的原话，而且它靠版本链（`replaced_by`）+ 审批链管理——脱敏会让"上一版是什么"变得不可解释 |
| `note`（用户备注） | 备注**由人写**、不注入、只作检索入口（`03` §3.2）。它本来就是"人记得某段时间发生过什么"的原话，替了它，人自己搜不到自己写的东西 |
| `pending_change`（大改申请） | 同上：它保存的是"改前 / 改后"两版身份文本，是审批依据，不是可替换的正文 |

单测 15a / 15b 把这条**不对称**钉住了——不是漏了，是故意。

`MemoryEntry.scrubbed?: string[]` 留给调用方（`index.ts` 的 `writeMemory`）以后要记自己的
审计时用（该批未改 `index.ts`；后续脱敏闭环与二次重扫见记录 37 / 41）。

## 四、`AS_SCRUB_BASE64` 的取舍

base64/hex 那条是唯一给了开关的规则（`AS_SCRUB_BASE64=0` 关，默认开）。

| | |
|---|---|
| **为什么它单独有开关** | 它是八条里唯一**没有强前缀**的规则，纯靠长度与字符构成判断。哈希、内容指纹、压缩串、某些 ID 都长这个样子 |
| **默认为什么是开** | 现实里的泄露大多不是整整齐齐的 `sk-`：JWT、`Basic` 凭据、加密串、签名 blob 都长成 base64。漏掉这一类的代价比误伤高 |
| **误伤了怎么办** | 关掉开关重写那一条；或放宽到"只要字母 + 数字"（**不建议**：git sha 会被卷进来） |
| **反向的代价** | 关掉后，长 base64 形态的密钥就完全不设防——这是用户自己要背的选择 |

同一条规则还自带一层收紧：必须**大写、小写、数字三者齐全**（`accept`），所以纯小写 hex
与纯大写 ID 都不动。这一条是"含大小写与数字"的字面落地。

## 五、审计只记种类与条数

```
as/scrub { kinds: ["sk-token"], count: 1 }
```

- **不记原文**：审计链如果存一份密钥，它就成了"第二份明文副本"，而且带着哈希链一路复制下去。
  记录 23 / 30 的同类决定是"审计不该长成第二份正文"，这里同口径。
- **不记位置偏移**：位置只在 `ScrubHit.at` 里给纯函数自用（便于测试与将来做高亮），
  落审计没有解释价值——它既不能还原原文，也不比种类更能说明"发生了什么"。
- **种类够解释了吗**：够。"某一轮写入被替掉了 1 处 sk-token"回答的是审计要回答的三件事
  （发生了什么、影响哪条路径、要不要处置）；再细就只能是原文，而原文正是不能进审计的东西。
- **可复核**：单测 12a–12c 断言审计里**没有**密钥子串、字段只有 `kinds` / `count`。

## 七、已知边界与偏离

1. **只对"以后写入"生效，不回溯老数据**（重要）。迁移不改表结构、不重写已有行：
   本次之前落库的条目仍是明文。要么人工清一次，要么在注入前加一道二次扫描——
   后者是本记录之外的另一件事（`08` B.2 脱敏行里记的就是它）。
2. **`pending_write` 队列不脱敏**。不受信任会话的写入先进积压队列（`enqueueWrite`），
   等人逐条批准。队列里的正文是**给人看的原话**，替了它人就没法判断该不该批；
   而 `adoptWrite()` 最终走 `this.add()`（`store.ts:1246`），**入库那一刻仍会被脱敏**——
   这条路绕不过去。
   而且条目被采纳（`state='adopted'`）后队列行**也不清空正文**（`dismissWrite` 的注释写着
   "不删正文，表里留着凭据"）：队列是"人提过什么写入请求"的记录，清掉正文就没了复核依据。
   所以 `pending_write` 应当**整体**被当作人侧材料（与 `redaction` 表同档），
   它不是第二份记忆库——注入通道从不读它，这是它与 `memory_entry` 的本质差别。
3. **`import` 用的是 `./redact.ts`（带扩展名）**。源码由 node 直接跑
   （`--experimental-strip-types`），ESM 要显式扩展名、不做补全；而 `tsc` 的 bundler 解析
   默认拒收 `.ts` 后缀（TS5097）。两边只能满足一边：取**运行时**（宿主与测试跑的都是源码），
   类型检查侧由 `.workbuddy/typecheck/tsconfig.json` 的 `allowImportingTsExtensions: true`
   放行（团队在验收时补上）。**不用 `@ts-ignore` / `@ts-expect-error`**：前者太宽，
   后者在"打开了该 flag"的检查方式下会变成 TS2578（未使用的指令）——两种跑法都要能过。
   这是本包唯一的静态内部导入，也是本次唯一动到"非业务代码"的地方。
4. **纯小写 hex 不替**（见第二节）。字面满足"含大小写与数字"，但如果有人把
   "hex 串"理解成"40 位 git sha 也要替"，这里就是偏离——**有意为之**，理由在那里。
5. **`base64` 规则会命中很长的英文标识符吗**：不会。它要求 ≥32 字符且大写、小写、数字齐全，
   普通单词/路径通常缺数字或缺大小写之一；同起点时厂商前缀规则优先于它（顺序在
   `SCRUB_RULES` 里）。
