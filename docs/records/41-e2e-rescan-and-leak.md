# 实测记录 41：二次扫描的端到端验证，与一个"防泄漏机制自己漏"的漏洞（2026-11-17 23:45）

> 验证记录 37（注入前二次扫描）时撞到的新东西。这一篇只讲**实测**与**新发现**，
> 机制本身的设计见 [`37-injection-rescan.md`](37-injection-rescan.md)。

---

## 0. 一句话结论

**二次扫描是真的在工作**：一条绕过写侧脱敏的"旧明文"记忆被注入时，
**两条独立防线同时命中**——我们新加的 `as/rescan` 与旁路自己发的 `REDACT`——
模型拿到的是 `[已脱敏:sk-token]` 占位符，**没有明文**。

**但同时发现一个更糟的漏洞**：旁路在写 `REDACT` 指令时把"含密钥的原文"抄进了 `reason`，
我们把 reason **原样落库**——于是**为防泄漏的机制自己成了泄漏通道**，
而且泄漏进了审计链（审计链是这套系统的"唯一凭据"）。

---

## 1. 怎么造这个现场

写侧脱敏只管"以后写入的"，所以要验证二次扫描，得造一条**历史明文**：

```sql
-- 直接用 SQL 插，绕过 store.add 的写侧脱敏（模拟去年的数据）
INSERT INTO memory_entry (id, text, t_start, salience, origin, state, summary)
VALUES ('m-legacy-1',
        '部署用的访问令牌是 sk-live-AAAABBBBCCCCDDDDEEEEFFFFGGGGHHHH1234，放在环境变量里。',
        <now>, 0.95, 'user', 'active',
        '部署访问令牌：sk-live-AAAABBBBCCCCDDDDEEEEFFFFGGGGHHHH1234，放在 DEPLOY_TOKEN 环境变量里')
```

注意 **summary 里也放了密钥**——因为旁路看到的是 summary（不是正文），
只把密钥放正文的话，旁路看不到它、也就不会触发注入。

---

## 2. 实测结果

审计链（`as/rescan` 与 `as/redaction` 都在）：

```
as/rescan   {"ids":["m-legacy-1"],"kinds":["sk-token"]}
as/redaction {"id":"r-mwkuzo97-3","find":"部署用的访问令牌是",
              "reason":"sk-live-AAAABBBBCCCCDDDDEEEEFFFFGGGGHHHH1234，放在环境变量里。\" 候选记忆里含明文凭证值…",
              "invalidated":1}
as/redaction_view {"hits":1}
```

上下文组成页（记录 33 那套）记下的当步注入预览：

```
注入 2 条：
  部署用的访问令牌是 [已脱敏:sk-token]，放…
  模型拒绝在对话中复述凭证值，建议用户自行 grep …
```

**两道防线**：
1. **我们的二次扫描**：`as/rescan` 命中 `sk-token`，递出去的那份被换成占位符；
2. **旁路自己的剔除**：记忆旁路判断"注入会把密钥带进上下文"，发 `REDACT`，
   `as/redaction_view {hits:1}` 表示发送视图里那一处被替换。

两条机制互相独立，却指向同一个结论——这正是"防御要分层"的意义。

（顺带：模型自己也没复述令牌，还说"这类凭证不适合在对话里复述，建议你自己 grep 变量名"，
并主动去读 `.env` 只看**键名**不看值。它做得对，但那是模型的判断，不是我们的机制——
**机制不能指望模型自觉**。）

---

## 3. 新漏洞：`reason` 里存着明文密钥

`redaction` 表那一行的原文：

```json
{"id":"r-mwkuzo97-3",
 "find_text":"部署用的访问令牌是",
 "replace_text":"……",
 "reason":"sk-live-AAAABBBBCCCCDDDDEEEEFFFFGGGGHHHH1234，放在环境变量里。\" 候选记忆里含明文凭证值…"}
```

`audit_chain` 里那条 `as/redaction` 的 data 同样带明文。

**成因**：记忆旁路在发 `REDACT` 指令时，为了说明"为什么剔除"，把候选记忆里那段原文**抄进了 reason**。
模型就是这么写的——它需要证据。而我们把 reason 原样落库。

**为什么这条比原漏洞更糟**：
- 原漏洞是"旧条目在库里是明文"，那是**已知且被承认**的残余（回溯改库 = 篡改历史）；
- 新漏洞是"**审计链**里有一份密钥抄本"，而审计链是我们反复强调的"唯一凭据、承重墙"。
  一旦审计链里有明文凭据，它就既不是"证据"也不是"链"——它变成了攻击者的目标。

**处置**（派给实现，见记录 37 的补记）：
- 落库前对**模型能自由书写的字段**（reason）跑 `scrubSecrets`；
- **`find_text` / `replace_text` 不能消毒**——它们要精确匹配原文，消毒会让剔除失效；
  若它们本身含凭据，则保留精确性 + **另记一条审计**（只记 id，不记原文）提示"这条剔除的匹配片段本身含凭据"；
- 同样的铁律要推广到**所有**"模型可书写且落库"的字段（note、summary、标签……）。

---

## 4. 一条要写进铁律的话

> **持久化位置不允许出现明文凭据——包括"为了解释为什么而写的说明文字"。**

这条与写侧脱敏（记录 31）是同一条规则的两个位置：
**写入前换一次、写入后落库前再换一次**。
两层都要，因为第一层防的是"新写的"，第二层防的是"模型为了解释而复述的"。

---

## 5. 证据级别

- 端到端：真会话（`pi -e` + `deepseek-chat`）+ 手工造的旧明文条目。
- 注入是否发生**受旁路判断影响**：前两次尝试旁路都 DROP 了那条候选（"candidates:1, dropped:1"），
  第三次把密钥也放进 summary 才让它进入注入路径——**说明旁路对"含凭据的候选"本身就偏保守**，
  这是个顺带发现（可能与 `as/redaction` 是同一次判断的两面）。
- 库里的旧明文**仍在**（这是有意的残余，不回溯改库）。

## 补记：漏洞修复后的复验状态（2026-11-18 00:50）

### 已修（记录 37 §九–§十一）

`store.ts` 11 处落库路径消毒（`scrubDeep` 递归）、`redactionAudit()` 净化视图、
`as/redaction_raw_risk` 事件（只记 id 与 kinds）。另有两条接线时追加的决策：

- **`pending_change.new_text` 现在脱敏**（原口径是"改前/改后都保持原样"）。
  理由：它会被 `applyChange` **直接写成锚点正文**，而锚点正文**每轮会话开头都注入一次**
  ——模型能把密钥写进一条待审批的身份改动，人批准后它就进锚点，从此每轮递一次。
  按 §11.3 的判据（会流到模型上下文的最严重），这一档优先于"审批依据要逐字"。
  审批者看到的也是脱敏版：人本来就不该批准一个密钥进锚点。`old_text` 保持原样
  （它来自已落库的锚点，是"改前"那版）。
- `index.ts` 的 `as/redaction` 审计条目改用 `store.redactionAudit(id)` 的**净化视图**：
  库里那份保持逐字（匹配要精确），但**进会话存档的这一份是展示用**，该净化。

### 复验的诚实结论

| 项 | 状态 |
|---|---|
| 机制（落库前消毒、审计链深度消毒、raw risk 事件） | ✅ **单测 56 项**（`redaction-secret.test.mjs`，12 组）守住 |
| 修复**前**的端到端现场（本文 §2） | ✅ 复现过：旁路自发 `REDACT`、`as/rescan` 命中、模型拿到占位符 |
| 修复**后**的端到端复现 | ⬜ **未复现**——连跑三场，旁路都没再发 `REDACT`（模型判断是随机的），所以**这条路径在修复后没有被再次触发** |

也就是说：**"审计链里有密钥抄本"这个漏洞，已由单测证明被堵住；但"修复后真会话里那条路径确实被走到"这件事没有证据。**
两者不是一回事——第一件是代码事实，第二件是现场事实。宁可留白，不把空表上的"没有明文"当成通过
（本记录第一版就差点犯这个错：一次复跑里剔除表是空的，"已消毒"三个字是假的）。

### 顺带一个观察

复跑时模型（这次**没有**关内置工具）读了我们的仓库，然后**引用了我们自己写的规矩**来回答用户：
"按你自己定的规矩（记录 41 / `redact.ts`）：明文凭据不许落到任何持久化位置……所以正确的落法
应该是变量名 + 轮换方式，而不是令牌原文。"

——它把我们内部的铁律用上了。这既是"规则写下来就有用"的证据，也是"模型会读仓库"的又一次提醒：
**验证"模型看到了什么"仍然必须关掉工具**（它读到的仓库内容会污染对上下文的判断）。
