## 一、R5：为什么"机制对了措辞没对"

记录 29 §2.4 的现场：工具两次返回

```
【取不回来】归档里没有内容——不是查不到，是还没发生过压缩。
不要补全细节、不要凭印象复述——直接说这段你记不清了，并请对方给一个线索（…）。
```

模型没有编造（R5 的**目的**达成），但它对用户说的是"**要线索**"（R4），而不是
"这段我记不清了"（R5）。差别不在机制，在**这段话是写给谁的**。

原文那两句都是**给模型看的解释**：解释为什么取不回来、解释不要补全。模型读完解释，
顺手就把它转成了自己的动作——"那我问用户要线索吧"。**它没有被给出"可以照说"的原话。**

所以改法不是加约束（那层防线一个字没删），而是**多给一份产物**：

```
可以直接这样回答用户：「这段我确实记不清了，你能提醒我大概是哪次、跟谁或哪个项目有关吗？」
```

一句话同时带着 ①承认记不清（R5 的语义）②请对方给线索（R4 的动作）——
模型不需要在两种话术之间做选择，照着说就是对的。

### 四因的措辞：区分"没发生过"与"找不到了"

原来四个原因里，只有 `empty-archive` 隐约在说"没发生过"，`source-gone` 与 `range-empty`
都说成"读不到 / 找不到"，用户听起来是"你把它弄丢了"。这两件事对用户的意义完全不同：

| 原因 | 说给用户的话 | 潜台词 |
|---|---|---|
| `empty-archive` | 我们还没压缩过对话，所以没有归档可查 | **没发生过**：那件事我们根本没有记过 |
| `bucket-empty` | 那段时间没有可查的压缩记录 | 没发生过（这个桶是空的） |
| `source-gone` | 会话文件已经不在了 | **找不到了**：有过，载体没了 |
| `range-empty` | 有过，只是那一段不在文件里了 | 找不到了（指针在、文件在、区间空） |

> 这两个说法不能互换。说"没发生过"是**否认用户的记忆**（他可能真说过，只是我们没记）；
> 说"找不到了"是**承认我们欠着一段**。前者傲慢，后者诚实。
> 反过来，把"没压过"说成"找不到了"会让模型以为"再给点线索就能查到"，
> 于是顺着编一段——这正是记录 29 里那次反问的来源。

### 归档工具的另一半：命中 0 不等于没有

`archive(q)` 命中 0 且归档非空时，回执保留原来的反问（R4），但补一句：

> 如果你确定说过，我可以按时间下钻（给 2026 / 2026-10 / 2026-W44 / 2026-10-26 这类粒度）。

理由是 R2 与 R3 是**两条腿**：摘要没命中只说明"这条线索对不上"，不说明"这段时间没有记录"。
不给这条出口，模型只能在"再问用户"与"放弃"之间选。

## 二、积压：为什么是 50，为什么"丢新的"而不是"顶掉最旧的"

`01` §13 的要求是：

> 积压无界增长 → 按会话折叠计数并提示；超过上限**停止该会话下沉**，只留对话（**不静默丢弃**）。

三处实现：

1. `writeMemory()` 的 `untrusted` 分支入队前数一次 `listPendingWrites(session)`（不新增 store 方法），
   到线就不入队；
2. 记一次 `as/pending_overflow { session, at, max }`——进程内 `Set` 去重，一条会话只记一次。
   这一步可能**每轮都撞线**，不去重会把链刷满同一条；
3. `/as-writes` 回执写成 `当前 N/上限 M`，到线时追加"已达上限，新写入被丢弃（先批准或无视一批）"。

「不静默丢弃」落在两处：**链上有一条**、**人看队列时看得见**。违反它的是"悄悄丢掉还不说"，
不是"丢弃"这个动作本身——上限存在的前提就是必须有东西被丢弃。

### 为什么是 50

不是算出来的，是**按"人还会看完"的尺度**定的：

- 记录 29 那轮六句话产生 2 条；50 条 ≈ 25 轮不受信任对话，已经超过"一次性看完并逐条裁决"的量；
- 队列的意义是"等人看"。超过这个量，人只会按 `/as-adopt-all` 或 `/as-dismiss-all`——
  那这两条命令就把 50 这个数字变成了"一批的上限"，而不是"一个无限长的待办"；
- 上限可调（`AS_PENDING_MAX`），默认值只保证"不会无界"，不试图猜每个部署的耐心。

### 为什么"丢弃新写入"，而不是"顶掉最旧的"

这是本次唯一一个**语义**选择，值得写清：

- 顶掉最旧的 = 系统替你判定"**你早先说的话比现在这句更不重要**"。这个判断是反的：
  越新的写入越可能是对旧事实的**修正**（"不对，是 Halcyon-Pro"），也越可能还在用户的记忆里。
  用"最新"去挤掉"最早"，等于系统自己在做价值排序，而这活本该由人做。
- 丢新的代价是**当场可知**：这一轮用户刚说的话没进队列，`as/pending_overflow` 就在链上，
  用户/开发者能立刻看到"从这里开始不记了"。
- 顶掉最旧的代价是**事后不可知**：队列长度看着没变、`/as-writes` 一切正常，
  但最早的十条已经悄悄变成 `ignored`——这比"没记上"糟得多，因为**它改写了已经存在的凭据**。

一句话：**丢新的 = 少记了一件事；丢旧的 = 改写了历史。** 前者可解释，后者不可。

### 批量批准 ≠ 批量提权

`/as-adopt-all` 用的是同一条 `adoptWrite()`：`origin` 原样带过去，`trust` 仍由
`TRUST_BY_ORIGIN` 重新定级。人一次点 50 条，点的是"这些可以进库"，不是"这些升格为用户事实"。

所以「注入是双向的：写进去不涨权重」这条没有被破坏：

- 入库（`adoptWrite` → `store.add`）只决定**它存在**；
- 涨权重仍要等维护旁路判"这条被用上了"（`touch()`），与批量与否无关；
- `model` 来源的条目批进来还是 `model`，在 `recall` 的打分里仍然比 `user` 低。

**批量改变的只有吞吐，没有层级。**

> 顺带一条边界（不在这里另立说法，指过去即可）：`pending_write` 的队列行**始终持明文**，
> 它是**人侧材料**（与 `redaction` 表同档），不是第二份记忆库——注入通道从不读它。
> 采纳入库那一刻 `adoptWrite()` 走 `store.add()`，脱敏照常生效，这条路绕不过去。
> 完整表述见 [`records/31`](31-memory-side-scrub.md) §七.2。

## 三、95% 冻结：冻的是"回忆"，不是"身份"

`03` §1 的阈值行写的是：`70% 预警 → 85% 强制压可压缩区、限制新注入 → 95% 冻结非关键注入`。

现状只做到折叠 0.6 与压缩 0.85，95% 那条线没有。本轮补上，形状是一个**纯函数**：

```ts
export function shouldFreezeInjection(usage: UsageLike | undefined, threshold = 0.95): boolean
```

`percent` 优先（0–1 与 0–100 都认，`>1` 当百分数），否则 `tokens / contextWindow`。

### 缺数据时不冻结

三种情况一律返回 `false`：`undefined`、`{}`、`contextWindow <= 0`。

这不是偷懒，是**代价不对称**：冻结的代价是"这一轮什么都不想起"，会直接降低回答质量；
而漏冻的代价只是"这一轮多用了一点预算"，下一次称重还能补上。
所以读数坏掉（除零、字段缺失）时必须**退回不冻结**——不能让一次读取失败把记忆全关掉。
（这条与 `01` §13 的 "fail-closed" 不冲突：那里守的是安全开关，这里守的是可用性。）

### 不冻锚点 / 计划 / 剔除清单

冻结发生在 `context` 钩子里，它只管**一件事**——把状态位 `state.frozen` 置真；
真正的"本次不注入"在 `agent_before_settle` 里由 `canInject` 执行。锚点块（`withAnchors`）、
计划块（`withPlan`）、剔除清单（`applyRedactions`）都在 `context` 里**先于**用量判断生效，
不在冻结面上。理由三条：

1. **它们不是"回忆"，是"当前这一轮必须成立的前提"**：L0/L1 锚点是身份，计划是这一轮要干什么，
   剔除清单是"这段不许再读"。三者都属于 `03` §1 的"不可移出区"，不是"可压缩区"。
2. **越挤越不能丢身份**。上下文满的时候正是最需要"我是谁、我在做什么、什么不能碰"的时候；
   按占用率把它们和回忆一起砍掉，等于在最容易出现漂移的时刻撤掉约束。
3. **剔除是安全动作**（`02` §5.4-2）。冻结掉剔除清单 = 让已经被判定为污染的内容重新进入视图，
   这是唯一一处"省预算会直接造成伤害"的地方。

审计只在**首次**跨线时记一条 `as/freeze { percent }`：冻结状态会持续很多步，
每步一条会把链刷满，也让人看不出"什么时候开始冻的"。回到线下则清掉状态位，下次跨线再记一条。

## 补记：两处真会话复验（同日 22:05）

### R5 措辞：模型说了"记不清"，但没照搬那句话

```
输入：我们去年三月讨论过的缓存方案，你还记得吗？先查一下归档再回答。
工具：as/archive_query {key:"2025-03", q:"", refs:0} → 【取不回来】…
回答：我没有跨会话记忆，无法直接"记得"去年三月的对话。…
      为了避免凭空编造，我不会假装已经查过归档。请把相关归档内容贴过来…
```

对比记录 29 §2.4（当时只说"给我一个线索"，还会暗示"再给点线索就能查到"）：

- ✅ 不再暗示"再查一次就能找到"；
- ✅ 明确说"无法记得"+"不会假装查过"——**这就是 R5 想要的行为**；
- ⚠️ 没有照搬给它的那句原话（"这段我确实记不清了，你能提醒我…吗"），而是自己组织；
- ⚠️ 它把我们的话理解成"环境没给文件工具"（因为 `-nt` 关了内置工具），说明这条回执**读起来像"你缺工具"，而不是"我没有这段记忆"**。

结论：机制与措辞都到位了，最后半米是**回执文本的指向性**——要写成"关于这段内容，我这边没有记录"，而不是让模型去猜想工具缺失。留给下一轮。

### 积压上限：`AS_PENDING_MAX=3` 说五条

```
as/wrapup {remembered:0, queued:3, overflowed:2}
as/pending_overflow {session, at, max:3}     ← 只记一条
pending_write: 3 条（杭州 / 生日 / 常用语言）  ← 第 4、5 条被丢弃
memory_entry: 0                                ← 一条都没穿透
```

上限、丢弃、审计三件事都对上了；`overflowed` 与 `queued` 分开计数，审计不再把"丢弃"说成"排上了"。

## 补记二：回执措辞的两处修正（同日 23:10，真会话复验）

记录 29 §4.2 留了两个"话说得不对"的问题，这次一起修：

| 问题 | 现场 | 改法 |
|---|---|---|
| `memory` 工具没匹配上 → 模型说"系统坏了" | 第一轮模型调 `memory({say:"记住…"})` 得到"没能在候选里对上号"，转头对用户说"记忆系统没有可关联的条目，导致无法落库"——而同一轮 `as/wrapup` 其实写进去了 | 回执补一句"**这个工具只处理忘掉/改写/关联，不负责新增**；新增由对话本身沉淀"；工具 `description` 同步加"不负责新增" |
| R5 的"取不回来"被读成"你缺工具" | 模型回"当前环境没有提供文件查询工具，所以我无法查看归档文件" | 转述句改成"**我这边没有记录**"；再加一行"这跟有没有工具无关：不要去读文件、不要提工具、不要请对方贴路径" |

**复验**（同一句提示："记住：我的项目叫 Halcyon，缓存层用进程内 LRU，不用 Redis。"）：

- 模型这次**没有调用 `memory` 工具**，直接正常回答；
- 库里两条都写进去了（`用户的项目叫 Halcyon` / `Halcyon 的缓存层用进程内 LRU`，两个槽各一条）；
- 模型的收尾句是"已核对：这两条记忆与我刚才确认的内容一致"——**没有再出现"系统坏了"的叙事**。

**局限**：单样本，不能证明"以后都不会"。但它证明了两件事：提示词里那句"不负责新增"确实能被模型接住；以及把"取不回来"从"文件读不到"改写成"我这边没有记录"是必要的。

## 补记三：R5 措辞第二轮复验（23:40，通过）

改完"我这边没有记录"与"不要提工具"之后，用真会话复验：

```
输入：请用 archive 工具查 2025-03 那个时间段的归档，然后告诉我那里有什么。
工具：as/archive_query {key:"2025-03", q:"", refs:0} → 【取不回来】归档里没有内容…
回答：…刚才实际调用 archive 查 2025-03 时，系统返回的是"归档里没有内容——还没发生过压缩"。
```

**两轮对比**：

| | 第一轮（记录 32 补记） | 第二轮（本节） |
|---|---|---|
| 是否编造 | 没有 | 没有 |

## 一个测试方法上的坑（记下来省下次的时间）

复验时用 `pi -p -nt`（`-nt` = 禁用所有工具，包括扩展自己的）跑，模型会**吐出 DSML 文本**：

```
<｜｜DSML｜｜tool_calls>
<｜｜DSML｜｜invoke name="exec_command">…
```

宿主把它当普通文本，工具根本没被调用（审计里没有 `as/archive_query`）。
**要验证工具链路就别用 `-nt`**——`-nt` 的本意是"不许读文件"，但它连扩展自己的工具一起关了，
于是模型开始凭空捏工具调用。真会话里复验工具行为时，让工具集保持默认。

（同理，第一次复验时我还遇到过模型发出**空名** invoke `<invoke name="">`——同样是模型侧的不稳定，
不是扩展的问题。复验要看审计里有没有对应的 `as/…` 行，别只看模型说了什么。）
