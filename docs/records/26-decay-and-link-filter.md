## 依据

- `03` §2 七种操作里的**降权**：「降低自动注入优先级 / 可恢复权重」。原文对审批分工的写法是"常规压缩、去重、**低显著降权** → 代码服务按预算自动做"，即降权不需要旁路点头。
- `03` §1 的铁律「**移出 ≠ 删除**」：降权改的是权重，不是正文、不是状态。
- `02` §3.2 第 2 条传播规则：「抑制条目不参与联想展开（一跳、二跳都不参与），否则"忘掉"形同虚设」。
- `08` B.2 降权行（当时 ⬜：`touch()` 只做 `salience + 0.05`，全仓无减号）、偏差表"抑制条目不参与联想"行。

## 一、降权：为什么是乘法

```ts
decay({ now?, idleDays = 30, factor = 0.85, floor = 0.15, limit = 50, gapDays = 1 })
  → { ran, decayed, ids, at }
```

`salience' = max(floor, salience × factor)`，只作用于 `state = 'active' AND pinned = 0`
且 `COALESCE(last_used, t_start)` 早于 `now − idleDays` 的行。

**乘法 vs 减法**，不是口味问题：

| | 高分条目（0.9） | 低分条目（0.2） | 结果 |
|---|---|---|---|
| 减法（每次 −0.15） | 6 次才到底 | 1 次就到底 | **只惩罚本来就弱的**，与"被反复忽略的自然沉下去"正相反 |
| 乘法（每次 ×0.85） | 12 次到底 | 1–2 次到底 | 按比例衰减，久未被用的高分条目也能沉下来 |

减法还有一个更坏的副作用：它会**先把"低显著"和"该消失"混为一谈**。库里 salience 低的条目
本来就有两种成因——"写得就轻"和"长期没用"。减法对两者的处置一样，乘法至少先按比例分摊。

**`floor` 为什么是 0.15**：`recall()` 的淘汰线就是 `MIN_SALIENCE = 0.15`（`01` §5 写死的常量）。
把下限对齐那条线，语义才闭合——"降到底"= "退出自动召回"，而不是"降到 0 之后还在池子里占位"。
降到线下不等于删除：正文、`use_count`、`last_used`、`state` 一概不动，`touch()`（判用加分）
随时能把它拉回来，`memory` 工具的 `remind` 也照旧能调出。

**`gapDays` 幂等闸挡的是什么**：`decay()` 由维护节拍调用，而节拍按轮算（默认每 10 个用户轮）。
如果没有闸，一个活跃会话里同一天会连乘几十次：

```
0.85^k = 0.15  →  k = ln(0.15)/ln(0.85) ≈ 11.7
```

也就是说**连续 12 次调用就到底**。一天之内跑出 12 次维护节拍，在长会话里是常态——
结果是"睡一觉起来全库沉底"，而"被忽略"的判断依据是 30 天，逻辑上根本不成立。
所以闸设在 `meta.decay_at`：不足 `gapDays`（默认 1 天）直接返回 `ran: false`，一条都不改。

**为什么不写审计**：`decay()` 只算与写，返回 `ids` 交给调用方。理由是审计要能说明
"这一轮为什么动手"（节拍到了、维护跑完了），那是 `index.ts` 才知道的事；
写在 store 里会变成一条只有结果的孤立记录。实际落点是 `as/decay`，data 只带
`{ decayed, ids: 前 5 个, at }`——日志要短，全量 id 在库里可查。

**幂等闸与维护节拍不共用键**：`decay_at` 与 `maint_last` 是两条独立记账，
互不覆盖（单测 3b/3d/3e 就是为这条写的）。

## 二、联想过滤：修的是 `02` §3.2 第 2 条

`linkedEntries()` 原来只按 `kind = 'explicit'` 取边。后果是：一条记忆被 `suppressed` 后，
正文还在库里、召回确实不再捞它，但如果它和某条活跃条目有显式边，**下一轮仍会顺着那条边被带出来**。
"忘掉"只剩一半。

改法是**两侧都堵**：

```sql
JOIN memory_entry seed ON seed.id = l.from_id AND seed.state = 'active'
JOIN memory_entry m    ON m.id    = l.to_id   AND m.state = 'active'
```

只堵终点不够：规则说的是"这条目参不参与联想"，不是"从哪一侧参与"。
换个调用方从被抑制的条目调入，终点过滤就管不住它。二跳由调用方对返回值再调本函数实现，
过滤写在函数里，两层自动成立。

顺带一句语义边界：过滤的是**参与资格**，不是删除边。`memory_link` 里那行还在，
被抑制的条目将来若被恢复（`state` 回 `active`），边立刻重新生效——这符合"降权/抑制可恢复"。

- **2g**：`use_count` / `last_used` / `state` 全部未动（降权 ≠ 删除 ≠ 判用）。

## 四、文档复核

| 要求（`03` §2 / `02` §3.2） | 实现 |
|---|---|
| 降权降低注入优先级 | ✅ 只改 `salience`，`recall()` 按 `relevance × salience × trust` 排序，天然降位 |
| 权重可恢复 | ✅ `touch()` 仍是唯一加分路径；降到底的条目再被用上会回升 |
| 不含删除 | ✅ 正文 / 状态 / 计数不动 |
| 抑制条目不参与联想（一跳二跳） | ✅ 两侧 `state = 'active'`；二跳因过滤在函数内而自动成立 |
| 降权不需要旁路点头 | ✅ 代码在节拍里直接做，无模型调用 |

**仍缺**：降权只看"多久没用"，不看"被注入后有没有被忽略"（`USED` 判为负例）。
现在的口径是"闲置即降"，比"被忽略即降"粗一档；要细一档得先有负例信号，属于后续项。
