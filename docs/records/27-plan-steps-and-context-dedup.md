## 一、`STEP <n>`：给计划一条写入路径

### 契约

```
STEP <n>        ← n ∈ 1..20，指"已立计划里的第 n 步做完了，并且验过"
```

与旧的 `DONE <n>` **合并**成同一个正则，理由有两条，都不是"顺手"：

1. 提示词在不同版本里换过写法，**旧输出的 `DONE` 仍在流通**（旁路的输出是模型生成的，
   没有"版本号"可对），只认新写法会让老会话里的步骤推进静默失效；
2. 两者的语义**完全一致**——都是"这一步完成了"。留着两个字段会逼后续每个消费方都做一次合并，
   而合并逻辑迟早会漏。所以解析成一个 `steps: number[]`，`dones` 字段直接改名删除。
   改名前核过全仓：`dones` 零消费方。

`parseMemoryBypass()` 里 `STEP` 排在 `PLAN` / `REDACT` 之后匹配，去重保序，
`<1` 与 `>20` 当乱值丢掉（实际计划只有 2–5 步，20 已是很宽的上界）。

### 接在哪

`agent_before_settle` 里，**立计划那一段之后**：

```ts
let doneSteps: number[] = []            // 与 slots 同级声明
...
doneSteps = result.steps                // 旁路可用的那一支
...
if (doneSteps.length > 0) {
  const marked = doneSteps.filter(n => store.completeStep(planFile, n))
  if (marked.length > 0) audit.push({ ... 'as/plan', data: { action: 'step_done', steps: marked } })
}
```

三点取舍：

- **放在立计划之后**：同一轮刚立的计划也可能带 `STEP`（模型一边立一边报"第 1 步已做完"）。
  新计划序号不匹配时 `completeStep` 返回 `false`，无害；能匹配时正好省一轮。
- **`✓` 只由代码写**：模型输出的是"第几号做完了"，`✓` 前缀是渲染层认的完成标记，
  不能让它出现在模型可控的文本里（否则计划区可以自称 4/4）。`completeStep` 是唯一写 `✓` 的地方。
- **幂等**：已带 `✓` 的步骤再报一次返回 `false`，审计里只记真正被改的那几条。
  这层幂等很有必要——续步循环会让同一次 settle 逻辑以外的旁路调用重复看到同一段思考。

**早退分支返回 `steps: []`**：旁路不可用时本轮零注入，也不推进任何步骤（宁可哑火，不可错注）。

### 顺带修掉的一个真 bug

`runMemoryBypass()` 里的 `REDACT` 分支此前引用 `sessionFileOf(ctx)` 与 `audit`，
但函数签名里**两个都没有**——`tsc` 报 `TS2304: Cannot find name 'ctx'` / `TS2552: Cannot find name 'audit'`，
运行期一旦旁路发出剔除就是 `ReferenceError`，整条阻塞相（注入、判用、交涉）跟着断。

那处还留着一条过期注释（"这里既没有 ctx 也没有 audit"），说的正是这件事，但它把
"没有"当成了理由而不是问题。这轮把 `ctx` / `audit` 作为参数传进去，注释改成如实描述
"计划**创建**不在这里，这里只收 `STEP`"。

## 二、A10：注入前过滤"已在上下文里"

### 判据是**字面前缀**，不是语义

```ts
normalizeForMatch(text)             // 去掉所有空白（\s 含全角空格），其余原样
alreadyInContext(text, ctxText)     // prefix = normalize(text).slice(0, 12)
                                    // 条目不足 8 字 → false；空上下文 → false
                                    // 否则 ctxText.includes(prefix)
```

三个参数都是刻意选的：

| 选择 | 理由 |
|---|---|
| 只去空白，不做同义 / 分词 | 目的是抹平"复制时多一个空格"，不是文本相似度。做多了会开始误杀 |
| 前缀 12 字 | 中文 12 字已足够具体（"用户住在杭州市西湖区文三路"）；再长会被改写轻易打断 |
| 不足 8 字直接放过 | 7 字条目的前缀几乎必然在上下文里出现（"用户在杭州"这种），宁可多注入一次 |

**它抓不住什么**（必须写在代码注释里，也写在这里）：

- **改写**：换了语序（"杭州市西湖区文三路是我住的地方"）、换了说法（"家安在杭州西湖区"），
  前缀对不上，一律放过；
- **开头带引号 / 修饰**：`「我住在…」` 的前 12 字里含 `「`，上下文里没有，同样不命中。
  这是字面判据的已知代价，不是 bug；
- **联想带出的条目**：过滤只作用于 `prefetched + recalled`，`linkedEntries()` 带出的那条不过滤。

为什么不在这里做语义级：**旁路本来就看得见上下文**，它判"这条是不是用户刚说的"比字符串匹配可靠得多；
这一层只负责最便宜、零调用、零延迟的那一档，把"刚说完又被递一次"这种最刺眼的情况挡掉。
语义级去重属于旁路的注入决策（`DROP`），不该在渲染层复制一遍判断。

### 位置：必须在调旁路**之前**

`picked` 过滤完再编号：

```ts
const picked = [...prefetched, ...recalled.filter(...)]
const kept = picked.filter(entry => !alreadyInContext(...))   // ← A10
let slots = kept.map((entry, i) => ({ entry, index: i + 1, ... }))
```

候选编号是旁路与代码对账的**唯一凭据**（`DROP 2` / `REWRITE 3` / `USED 1` 全按它解释）。
先调旁路再过滤，编号就会整体错位，`DROP` 打中的是另一条——这比不过滤更糟。
过滤保持原顺序（预取在前、召回在后），被滤掉的条数 > 0 时记 `as/inject_skip { count, ids: 前 5 个 }`。

## 三、`summary` 落库

`judgeDoc()` 里，`parseDocVerdict()` 现在解构出 `summary`（`DOC_RULES` 里新增
`SUMMARY <一句话，≤60 字>`）：

```ts
const { verdict, reason, summary } = parseDocVerdict(judged)
store.setDocVerdict(id, verdict, reason)
if (summary !== '') store.setSummary(id, summary)      // store 内部截 120 字
... data: { id, reason, hasSummary: summary !== '' }   // 审计只记有没有，不记内容
```

- **落库点选在写入时判转存的那一次调用**，不另起一次：这条调用本来就在读全文前 1200 字，
  顺手让它说一句"这条讲什么"是零增量成本；每轮重判既费调用又会前后不一致。
- **只在 `summary !== ''` 时写**：空串意味着旁路没给（或给了空行），此时索引区退回
  "日期 + 标题 + 字数"，不硬造一个。
- **审计只记布尔**：摘要正文在库里，日志塞整段会让审计链变成第二份正文。
- **还没被用起来**：注入时仍按 `full / excerpt / summary` 裁决渲染，`render()` 不读这个字段；
  索引行也还没接。所以这一项是"字段有了、写入通了"，不是"索引区因此变好了"。
