# 形态与平台约束

> 结论先行：**AuthenticSelf 是一份 Pi 扩展**——不做模型、不做界面、不做运行时。
> 与扩展 API 打交道的细节（哪个钩子做什么）在 [`04-implementation.md`](04-implementation.md)；本文管的是"为什么是这个形态、它在各端受什么约束"。
> 当时的完整跨平台调查（四个运行时方案、Operit / Aether 拆解）已移入 [`archive/platform-survey.md`](archive/platform-survey.md)。

---

## 0. 为什么是扩展，而不是自己搭一个基座

| | 提议甲：直接用 Aether 作基座 | 提议乙：做成 Pi 扩展 |
|---|---|---|
| 得到 | 三端白送；壳、权限、文件桥、扩展市场都是现成的 | **同一份语义跑在任何 Pi 宿主上**：`pi` CLI（终端）、Aether（移动）、其他发行版 |
| 失去 | UI 自主权（它用 Compose，不是 Web）；绑死一个项目 | 不能改宿主内部；受扩展 API 边界约束；UI 由宿主决定 |
| 风险 | 作者业余开发、发行节奏不稳；**GPL-3.0** | API 变化；宿主不给审计入口时"白盒"没地方看 |

**甲是乙的一个特例。** 选乙，Aether 只是"可选宿主之一"；选甲，就只剩 Aether，还多付一份代价。所以选乙。

## 1. 决定性发现：Pi 的钩子几乎是为这套设计长的

查证后才敢下的判断（逐条实测过，见 `04` 的落点表）：

| 我们的机制 | Pi 里的落点 | 结论 |
|---|---|---|
| 无工具注入 | `context` 每次请求前**非破坏性**改消息 | 与"发送视图 = 存档 + 清单"同构 |
| 一句话内多轮注入 | `agent_before_settle` + `continue` | 原生，不需要寄生技巧 |
| 接管压缩 | `session_before_compact` / `ctx.compact()` | 可接管（但本体对单 turn 无效，见 `records/04`） |
| 交涉通道 | `registerTool` 注册自然语言入口 | 一个工具够 |
| 归档库 = 所有会话 | `SessionManager.listAll()` | 返回 `allMessagesText`，归档成立 |
| 预算 / 超时 | `ctx.model.contextWindow` / `maxTokens` / `getContextUsage()` | 取重与阈值都有把手 |

**最有价值的一条**：注入以 `custom_message` 落地，模型看到的角色是 **`custom`**，不是 `user`——它把补充并入原答案，不当作新提问；同时写进存档，可审计可回放。这两点在 dsh 上要靠"借 user 角色 + 反复改措辞"硬凑（为此返工过两次）。

## 2. 三个必须摊开的后果

### 2.1 前端换岗：从“Agent 界面”变成“人的控制台”

宿主提供对话界面，因此不再自建聊天 UI；白盒可观测先由 `/as-*` 命令与 [`view.ts`](../pi/src/view.ts) 只读上下文组成页承担，封存的前端素材留作远期只读控制台参考（见 [`07-roadmap.md`](07-roadmap.md)）。

### 2.2 GPL 的边界

Aether 是 GPL-3.0，Operit 2 是 AGPL-3.0。**"运行时加载的扩展"通常不构成衍生作品**（通过公开 API 与宿主交互，是独立包），但这是法律判断，不是我们能拍板的。实践上：

- 扩展独立成一个 npm 包，通过 `pi.extensions` 声明接入；
- **不复制宿主任何代码**——这条无论许可如何都成立；
- 若将来要进 Aether 生态，让许可兼容（MIT / Apache 对 GPL 宿主通常没问题，反向才要小心）。

### 2.3 扩展没有沙箱：与宿主同权

Aether 文档原话：扩展是可信代码，装扩展等于把 Node 运行时、Android 上下文、工作区全交出去。

对我们不是问题（本来就要读写记忆库、调模型），但必须说清：**AS 装进宿主后，它与宿主是同等权限的。** 隔离承诺只在我们内部（主 AI ⟂ 旁路），不延伸到宿主。

## 3. 平台结论

### 3.1 三端的难度不在一个量级

```
Windows / Linux / macOS    容易（Node 原生）
Android                    难——不是"另一个 OS"，是另一套运行时规则
iOS                        不做
```

Android 的难在三件事：**没有 Node**（要塞）、**后台会被杀**（Doze / 省电 / 厂商定制）、**文件系统沙箱化**（app 私有目录可用，"用户能直接打开看"不成立）。

### 3.2 Android 怎么做：塞 Node，不塞 Linux 用户空间

参考项目的教训：

- **Operit 1 → 2**：Android 做到 5000 star 后跨平台，**没有选 Node，也没有每端原生，而是用 Rust 重写了核心**——说明"每端原生"不可持续。它用 PRoot 跑 Ubuntu，下一代放弃了这条路："PRoot 是能用不是好用"。
- **Aether**：唯一"三端跑 pi"的活样本。它每个平台都塞了一个 Linux 用户空间（Android 用 proot + Alpine，iOS 用 iSH 模拟），因为它的卖点是内置 shell / apt。

**我们的需求比它们窄得多**：不要 shell 工具、不要 apt、不要本地大模型、不要设备自动化。所以取中间：

| 项 | 选择 | 理由 |
|---|---|---|
| 运行时 | **塞 Node**（nodejs-mobile 或打包二进制），**不装 Alpine** | 只要能跑 `pi` + `node:sqlite` + 文件 |
| 壳与核心 | **跨进程边界**：原生壳（UI + 持久化）↕ JSON over stdio ↕ Node 进程 | Node 崩了壳还在，壳能重启它 |
| 持久化 | **归原生壳**，Node 侧尽量无状态 | 记忆库 / 会话 / 备注由壳持有，崩了不丢数据 |
| 上架 | 先侧载（不上架），按 A 方案做；要上架再换 nodejs-mobile 绕开 W^X | 侧载时商店审核风险归零 |

代价：每次记忆检索跨一次桥。可接受——召回本来返回几条，不是全表。

### 3.3 持久化在桌面与移动的差别

| 端 | 库在哪 | "不易直读"的强度 |
|---|---|---|
| Windows / Linux / macOS | `$PI_HOME/agent/authentic-self/memory.db` | 二进制页格式提高门槛，但模型仍可用 shell 打开——**约定，不是边界**（`02` B1-a） |
| Android | app 私有目录 | 其他应用读不到，比桌面强 |

### 3.4 不做 iOS

iSH 那类 x86 用户态模拟代价过高，且 iOS 不允许 JIT、不允许运行外部二进制——本地跑 Node 这条路会彻底堵死。明确排除。

## 4. 路线

```
AuthenticSelf = Pi 扩展（语义层）
    ├─ 跑在 pi CLI 上      → 终端（当前唯一验证过的宿主）
    ├─ 跑在 Aether 上      → 手机
    └─ 跑在自建壳上        → 桌面 + 人的控制台（可选，后做）
```

分三步：

1. **先做扩展**（已完成）：用 `context` / `agent_before_settle` / `session_before_compact` 三个钩子实现注入、多轮、接管压缩。跑通即证明整套设计在 Pi 上成立。
2. **两个宿主各验一遍**：`pi` CLI 已验证（1.4.0）；Aether 未验，门槛见下。
3. **控制台后置**：只有当审计与记忆浏览真的需要界面时，再启用封存的前端。

## 5. 待定

1. **Aether 用的 pi 版本**：README 写 `0.85.1`，本地实测 `1.4.0`。这些钩子是 1.x 才齐的——**低版本宿主可能根本没有**，这是"装进 Aether"的实际门槛，也是 M5 的主要风险。
2. **桌面壳用 Tauri 还是 Electron**：尚未决定，等有控制台需求时再选。
3. **Android 打包**：nodejs-mobile 还是自带二进制，取决于将来是否上架。
