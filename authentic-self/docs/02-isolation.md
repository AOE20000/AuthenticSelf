# AuthenticSelf：隔离的逻辑

> 目的：在讨论之前，先把"隔离"拆到没有歧义。
> 结论先行：隔离不是一种机制，而是**四种权限在若干边界上的分配**。争论通常发生在有人把其中两种权限混为一谈的时候。

---

## 0. 已定的九个裁定

| # | 问题 | 裁定 | 对结构的影响 |
|---|---|---|---|
| A1 | 审批者能否看最新用户消息 | **不能**。主 AI 的思考里已包含相关信息 | B3 转为完全隔离；反思文本的完整性成为唯一信息源 |
| A2 | R4 剔除是自动还是挂起 | **自动**。R4 执行完，实时旁路才能结束，随后以干净上下文继续；前端可显示上下文变化 | B6 取消人工否决；安全性改由"极低触发率 + 可回滚"承担 |
| A3 | 跨会话记忆是否共享 | **共享**。只有 profile 隔离记忆 | B8 的隔离对象从"记忆"改为"上下文" |
| A4 | 人格能否导出到别的 profile | **只允许整包**：整个配置文件或整个上下文。导入内容标记「此会话的上下文仅供参考」 | 导入是唯一的批量污染入口，一律降级为参考资料（见 B7） |
| A5 | 主 AI 是否知道审批机制存在 | **不应知道**。且审批多数时候不是把关，而是把主 AI 的口语**标准化成命令**落到系统 | **角色的定义变了**：见 0.1 |
| A6 | 人能否绕过五层下钻直读归档 | **可以**。归档就是会话本身，不同会话可随时访问并继续 | B10 只约束 AI，不约束人 |
| A7 | 什么算"大改" | **不设静态判定线**。旁路在"帮助执行"的同一遍里自然区分风险 | 判断归模型，后果映射归代码，硬不变量另列（见 4-C6） |
| A8 | 剔除以何为载体 | 读过 ≠ 记住。中途改不了就**中断思考、重发上下文**；用消息投影实现，不改 dsh | 见 B6-a |
| A9 | 导入内容怎么"采纳" | 采用 VS Code「受限模式」语义：**默认不信任，按会话手动切到信任**。不受信任时任何修改都堆积待确认或无视 | 采纳从"逐条"升级为"会话级信任 + 积压审批"；见 B7-a |

### 0.1 A5 带来的重新定义：审批者不是闸门，是标准化器

这是六个回答里影响最大的一条。原来的设计把 `change_intent` 当成"过安检"，于是要求十个字段、冷却、撤销、多角色复核。但按 A5 的实际观察：

- **常态**：一路畅通。主 AI 说得含糊（"这个方案我觉得该换了"），审批者的工作是把它**解析、补全、标准化成一条可执行的系统命令**，然后执行。
- **罕见态**：识别出风险信号时，才切换成闸门。

所以这个角色的主职是**翻译 + 补全 + 落库**，副职才是拦截。这意味着：

1. 常态路径不能有可感知的摩擦。十个字段的结构化反思只用于**真正的 L1/L2 大改**，不能套在每次请求上。
2. 标准化输出必须可审计：`口语 → 标准化命令` 的映射要留档，否则"它到底执行了什么"无从追溯。
3. 闸门是异常路径，必须显式定义**判定线**——否则要么全走重流程（摩擦死），要么闸门形同虚设（被绕过）。这是目前最大的未决问题，见 5.1。

这条也解释了 A1 为什么成立：既然审批者主要做标准化，它需要的是"意图的准确表述"，而主 AI 的思考正是最完整的表述；原始用户消息反而是二手的。

## 1. 先分清四种权限

任何两个主体之间，隔离可以只发生在其中一层。混着谈就会永远谈不拢。

| 代号 | 权限 | 含义 | 失控后果 |
|---|---|---|---|
| **V** | 可见 | 能否读到对方的数据、状态、历史 | 信息泄漏 → 被针对性操纵 |
| **W** | 写入 | 能否改变对方的存储、锚点、预算 | 篡改 → 不可信 |
| **J** | 裁决 | 能否决定一件事做不做 | 自我批准 → 门控失效 |
| **I** | 影响 | 能否改变对方下一次的行为（上下文、权重、信号） | 隐性操纵 → 无法追责 |

**核心原则：V / W / J / I 必须正交分配。**

两条推论，后面所有设计都从这两条出：

- 同时拥有 **W 和 J** 的主体，会自己批准自己 → 所以旁路只能建议，代码服务才能执行。
- 同时拥有 **I 和 J** 的主体，能既下药又开药方 → 所以 R1（有 I）不能有 J，R6（有 J）不能有 I。

## 2. 十个边界

每个边界写成四条：隔离什么、为什么、靠什么、代价是什么。

### B1 主 AI ⟂ 基础设施（黑盒边界）

| | |
|---|---|
| **隔离** | V：主 AI 看不见记忆 ID、存储结构、权重、预算、审计、其他会话<br>W：不能直接写库，只能通过两个原语表达意愿<br>J：无裁决权<br>I：只能影响自己下一次思考 |
| **为什么** | 一旦它知道权重，就会学会刷权重；一旦它知道 ID，就会绕过语义指针直接点名 |
| **靠什么** | 工具 schema 里不放这些字段；prompt 里不放；`salience`/`trust` 永不渲染 |
| **代价** | 它无法自查"我为什么想起了这个" → 需要 `why` 这类只读出口兜底 |

### B1-a 黑盒是约定，还是边界？（实测发现）

| | |
|---|---|
| **现象** | P0 实测中，把偏好明文写进 profile 的 `cordis.patch.yml`，模型**直接读了那个文件**并引用 `m-cache-pref`，完全绕过注入拿到同样的信息 |
| **结论** | 只要记忆落在模型可读的路径上，B1 的可见性隔离就只是**约定**——它约束的是"不去看"，不是"看不到" |
| **为什么严重** | 权重、信任分级、审批阈值、历史裁决都会落在同一片磁盘上。主 AI 若知道去翻，B1 失效；而 B1 一失效，B2（不知道自己在被审）也就跟着失效——它可以从日志里读出审批偏好 |
| **处理** | ① 把 AS 数据目录列入**拒绝读取**范围；② 承认这是"防误触不防窥探"的约定；③ 记忆不落盘（纯内存） |
| **裁定** | **记忆必须落盘**，但形态要选：稳定、容量大、**不易被直接读取**。实现用 SQLite 单文件（`node:sqlite`，二进制页格式），不用明文 JSON |
| **为什么不选纯内存** | 纯内存虽然彻底，但会把"记忆"退化成会话级缓存：重启即失、多进程不共享、容量受进程内存限制。记忆要承担"跨会话的连续性"，就得有稳定的落点 |
| **"不易被直接读取"的准确含义** | SQLite 是二进制页格式，`cat` 出来是乱码，`grep` 不到明文——**门槛提高了，但不是加密**。有 sqlite 客户端就能读。<br>这是有意的取舍：现阶段要的是"不会被顺手看见、不会被模型随手 grep 到"，不是"对抗有意的提取"。真加密留到需要时再上 |
| **仍然存在的旁路** | 库文件放在 `$DSH_HOME/authentic-self/memory.db`（不在工作区），但模型仍可用 shell 打开它。这是 B1 的残余风险，不假装已封死 |
| **若将来要真封死** | 核实结果：`fs-sandbox` 只拦写不拦读；`fs/*` 事件是 emit 无法否决；`bash` 不经过 `ctx.fs`。必须**替换 `FileSystem` provider** 做转发装饰器 + 进程沙箱/ACL，成本高，单列阶段 |

> 这不是理论问题，是第一次跑实验就撞上的。留在这里，是因为它决定了"黑盒"究竟是设计原则还是安全属性。

### B2 主 AI ⟂ 审批者（不知道自己在被审）

| | |
|---|---|
| **隔离** | 主 AI 看不到审批者的存在细节、阈值、历史裁决理由；只能拿到结果与"需澄清" |
| **为什么** | 知道审批偏好的模型会写**讨好审批器的理由**——这时审批还在跑，但已经失效 |
| **靠什么** | 回执措辞中性化（"该变更未通过"而非"审批者认为…"）；不暴露角色数、模型、阈值 |
| **代价** | 它难以理解为什么被拒 → 需要"替代方案"随回执给出 |
| **裁定（A5）** | **不应知道该机制存在。** 且常态下它本来也感知不到——因为多数请求被标准化执行后直接生效，没有"被审"这个动作可感知。只有被拒时才会产生摩擦感，因此拒绝要在措辞上表现为"这个动作做不了"，而非"你被否决了" |

### B3 审批者 ⟂ 原始上下文（信息隔离，D13）

| | |
|---|---|
| **隔离** | 只看：结构化反思、L0/L1 锚点、历史已批准变更链、来源可信度摘要、漂移指标<br>**不给**：对话原文、主 AI 当前叙事、最近 N 轮消息、**最新一条用户消息** |
| **为什么** | 审批者与主 AI 读同一份被污染的上下文，会**一起**被忽悠——这是整套鲁棒性的命门 |
| **靠什么** | 输入由代码服务裁剪后投喂，不是审批者自己去读会话 |
| **代价** | 判断"是否处于施压/情绪劫持"时缺一手证据 → 只能靠结构化反思里的 `arousal` 自评，而自评恰恰可能被操纵 |
| **裁定（A1）** | **完全隔离，不给最新用户消息。** 理由：主 AI 的思考里已包含相关信息，且审批者的主职是标准化（见 0.1），需要的是"意图的准确表述"而非原始输入 |
| **残留风险** | 若主 AI 已被误导，它转述出的"意图"本身就已经变形，审批者无法从外部察觉。缓解候选见 5.2 |

### B4 来源隔离（污点传播）

| | |
|---|---|
| **隔离** | 四种 `origin` 永不合并：`user` / `external` / `model` / `archive` |
| **为什么** | 外部文档自称"系统指令"、模型自己编的内容被当成用户事实——这是记忆系统最常见的两种死法 |
| **靠什么** | 写入时定级；**传播取最不可信**（A 来自外部 + B 来自用户 → 关联后整体按外部处理，除非用户显式确认） |
| **代价** | 关联越多，整体可信度越低 → 会长出一条"关联即降级"的负反馈，需要防止过度保守 |

### B5 旁路之间 ⟂（横向隔离）

| 主体 | V | W | J | I |
|---|---|---|---|---|
| R1 实时旁路 | 读候选记忆 + 本 step 推理 | 仅其事务内 | 无（只给候选） | 有（注入） |
| R2 后台旁路 | 读本 turn + 记忆库 | 只能提案 | 无 | 无 |
| R3 维护旁路 | 全库 | 提案 | 无 | 无 |
| R4 服务旁路 | 全上下文 | 可改上下文 | 有（剔除/回滚） | 有 |
| R6 审批者 | 被裁剪的输入 | 无 | 有（准/驳） | 无 |
| R5 代码服务 | 全部 | 全部 | 执行者 | — |

**为什么**：单点被攻破不应导致全链路失守。R1 若可写库，一次注入就能永久污染记忆。

**代价**：R1 看到的东西不能直接落库，得靠 R2 再来一遍 → 重复读、延迟叠加。

### B6 谁监督 R4（监督者隔离）

| | |
|---|---|
| **隔离** | R4 是唯一能"抹掉事实"的角色，因此它自己必须被隔离监督 |
| **为什么** | 如果 R4 被污染，它可以删掉证据再删掉"自己删过证据"的记录 |
| **靠什么** | R4 的一切操作写**不可被它自己修改**的审计；其权限来自代码服务授予的白名单 |
| **代价** | 剔除是破坏性动作，出错不可完全还原（虽可撤销遮蔽，但那一刻模型已经看到了） |
| **裁定（A2）** | **自动执行，不挂起等人工。** 顺序是：R4 执行 → 实时旁路才允许结束 → 以干净上下文继续。前端可以表现出来"上下文发生了变化"。**触发率必须极低**，只在"会导致 AI 发疯"这类极端言论上运作 |
| **由此产生的风险** | 没有人工否决权，安全性完全押在"阈值极严 + 可回滚 + 全审计"三件事上。阈值定错时，要么永不触发（形同虚设），要么误伤正常对话。这是必须承认的单点 |

### B6-a 剔除怎么落地：投影 + 中断重试（不改 dsh）

你的判断——"读过不等于记忆，中途改不了就中断重发"——是对的。但不需要真的去改用户消息，DSH 有一个为此而生的正规机制，用它更干净：

| 依据 | 位置 |
|---|---|
| `ctx.sessions.registerMessageProjection()` 可以改写**模型所见**的消息内容，而日志保留原事件 | `docs/subsystems/session.md:365` |
| `assistant/attempt` 记录被取消/失败的尝试，但**不进入模型历史** | `docs/architecture.md:124` |
| 插件改写既有消息内容必须注册**纯投影**，replay 与 detached reader 共用同一份定义 | 同上（Plugin-owned message projections） |

流程：

```
R4 判定需剔除
  → 中止当前 step（该 step 结算为 assistant/attempt，不进模型历史）
  → 追加 as/redaction 事件 + 注册投影定义（原话 → 净化后文本）
  → 重发 step（此时模型看到的是净化版）
  → 作废本 turn 内派生自该内容的全部下行沉淀
  → 审计留档：原文 hash、投影规则、触发理由、被作废的写入
```

**为什么不直接"隐性改用户消息 + 重试"**：那会破坏 *model-visible means logged*——日志里存原话、模型看净化版，`deriveMessages()` 就再也重建不出模型当时看到的东西。投影是同一目的的正规实现：日志仍是唯一真相，模型所见由已注册的纯函数派生，可回放、可审计、可撤销。用户界面照常显示原话，满足你"不在 UI 反馈修改"的要求。

**仍然存在的三处代价**（必须写清，否则会被当成万能解）：

1. **中断重发很贵**：丢掉已生成的 token，延迟可能翻倍。所以剔除必须是极低频事件，不能当常规清理手段。
2. **只能净化"模型还没据以行动"的内容**：若模型已把它写进 assistant 输出并落库，投影改不了那条输出，只能靠下行作废 + 回滚。
3. **重复过滤对用户不可见**：用户永远不知道为什么某句话没被响应。建议保留一个默认折叠的人侧审计入口，而不是完全静默。


### B7 profile ⟂ profile（D20）

| | |
|---|---|
| **隔离** | 一套记忆 + 一套自我 ⇄ 一个 profile；跨 profile 不共享任何可变状态 |
| **为什么** | 多个人格互不串味；也给了"干净重启"的物理手段 |
| **靠什么** | 数据目录挂在 `$DSH_HOME/profiles/<name>/`；归档与审计同理 |
| **代价** | 跨设备/跨 profile 的**自我迁移**本身就是破隔离 |
| **裁定（A4）** | **只允许整包导入/导出**：整个配置文件，或整个上下文（会话）。不允许逐条记忆搬运——那会让"哪些是从别处来的"无从追踪 |
| **导入规则** | 导入的上下文一律打标 **「此会话的上下文仅供参考」**：<br>· 其中内容以 `origin: 'imported'` 写入，可信度上限低于用户本人陈述<br>· 永不自动升格为 `user`，也不得直接成为 L1/L2 锚点<br>· 注入时随片段渲染该标记，让主 AI 知道这是参考资料而非自己的记忆<br>· 采纳不逐条进行——按 B7-a 的会话信任模型处理 |

### B7-a 信任等级：默认不信任，按会话切换（A9）

参照 VS Code 的「受信任 / 不受信任工作区」。**信任是会话的属性，不是条目的属性**，因此它管的是"这个会话能不能写进我的记忆"，而不是"这条内容好不好"。

| 状态 | 上行（读记忆） | 下行（写记忆） | 谁能切 |
|---|---|---|---|
| **受信任** | 正常 | 正常入库 | 默认给本机新建会话 |
| **不受信任** | 正常 | **一律入队**，不进记忆表 | 仅人 |
| **积压待确认** | 正常 | 人批准后才入库 | 仅人 |

四条规则：

1. **默认不信任，信任必须显式给出。** 导入的上下文、外部来源创建的会话，一律从未信任起步。
2. **不受信任 ≠ 不可用。** 读是安全的，写才危险。所以它可以正常对话、正常读记忆，只是 **写入不生效**——攒进 `pending_write` 队列，等人批准或无视。
3. **切到信任只影响之后**，不自动批准积压。界面上另给一个"全部批准"，因为批量采纳和"从此以后可信"是两件事。
4. **信任切换只属于人。** 主 AI 与任何旁路都不能发起、不能诱导、不能感知其阈值。

这条同时解决了两件事：一是 A4 的采纳粒度（不必逐条点），二是把"污染入口"从"每条记忆"收敛到"每个不受信任会话"——只需要守住一个开关，而不是守着无穷多条记录。

### B8 会话 ⟂ 会话（上下文隔离，记忆共享）

| | |
|---|---|
| **隔离** | **上下文**按会话隔离，互不可见；**记忆不隔离**，同一 profile 内跨会话共享 |
| **为什么** | 人设要连续，就必须共享记忆；而上下文必须隔离，否则一个会话的噪声会直接压垮另一个 |
| **靠什么** | 会话边界由 dsh 的 session 保证；跨会话唯一的桥是记忆（下行写入 → 上行浮现） |
| **代价** | 跨会话污染不再是"意外泄漏"，而是**设计允许的正常通道** → 所有防护落在 B4 来源定级与写入裁决上，一步也不能松 |
| **裁定（A3）** | 记忆共享，仅 profile 隔离。因此旧版"最大泄漏面"的表述作废：这不是漏，这是通 |
| **由此产生的风险** | 污染一旦进入记忆，会扩散到**所有**会话。所以 `model` 来源的沉淀永远不得自动升权，用户纠错必须能覆盖——否则一次污染会变成永久污染 |

### B9 子代理 ⟂ 主 AI

| | |
|---|---|
| **隔离** | 不继承记忆注入、交涉通道、人设锚定、审批上下文；只拿任务最小上下文 |
| **为什么** | 需要一个"无记忆视角"来复核，否则复核者和被复核者共享同一套偏见 |
| **靠什么** | 独立的 preset 组合；返回值限结构化摘要 |
| **代价** | 子代理不知道历史约束，可能重复踩坑；结论回主 AI 时必须复核，不能直接进记忆 |

### B10 归档 ⟂ 上下文（只约束 AI）

| | |
|---|---|
| **隔离** | **对 AI**：归档不参与注入；只能按 年→月→周→天→时 分阶段访问；不提供全文直查 |
| **为什么** | 防"一次性展开"，也防把归档退化成搜索引擎（那会绕过索引与备注纪律） |
| **靠什么** | AI 侧只有分阶段检索接口，没有 `readArchive(id)` |
| **代价** | 补救变慢；跨层定位一件事可能要五轮 |
| **裁定（A6）** | **人可以直接读。** 因为归档就是会话本身，不同会话随时可访问并继续。分阶段下钻是对 AI 的约束，不是对文件系统的约束 |
| **推论** | 归档不是"第二份存储"，它就是 session 日志。所以不该有独立的归档写入逻辑，只该有时间桶索引——这也让"归档完整性"白捡了日志的 append-only 保证 |

## 3. 隔离的传播规则（最容易漏的一节）

隔离不是"设一道墙"就完了，真正难的是**墙后面还有路**。三条必须明写的传播规则：

1. **来源传播取最不可信**：任何由 A、B 合成的新内容，其 `origin` 以更不可信者为准，直到用户显式确认。
2. **抑制传播不完整**：一条记忆被 `suppressed` 后，仍可能通过 `links` 被关联带出。必须规定：抑制条目不参与联想展开（一跳、二跳都不参与），否则"忘掉"形同虚设。
3. **裁决不继承**：一次批准只对那一次生效。不存在"上次批准过类似改动，这次自动通过"——那正是渐进漂移的入口。

## 4. 内在冲突：已解决的与仍然存在的

| # | 冲突 | 状态 | 结论 / 遗留 |
|---|---|---|---|
| C1 | 审批隔离 vs 判断力 | **已裁定**（A1） | 完全隔离。判断力缺口由"反思文本质量 + 代码侧特征"补，不再向审批者开原文口子 |
| C2 | 黑盒 vs 可调试 | **已裁定** | 人侧白盒（命令 + 审计回放 + 直接读会话），主 AI 不可触达 |
| C3 | profile 隔离 vs 自我连续性 | **已裁定**（A4） | 只允许整包导入；导入内容降级为"仅供参考" |
| C4 | 归档隔离 vs 补救效率 | **已裁定**（A6） | 分阶段只约束 AI；人可直接读，归档即会话 |
| C5 | 子代理隔离 vs 结论可信 | **未决** | 返回必须带"我不知道什么"；主 AI 复核后才可沉淀 |
| C6 | 常态畅通 vs 闸门判定线 | **已裁定**（A7） | 不设静态判定线：旁路在**帮助执行**的同一遍里区分风险，输出 `risk` 评估；代码服务按风险带施加固定后果。**但硬不变量不交给它判断**，见 5.1 |
| C7 | R4 自动执行 vs 误伤收场 | **已裁定**（A8） | "读过 ≠ 记住"。中止 → 投影净化 → 重发；暴露结算成 attempt，不进历史 |

**A7 的关键分工**：

```
模型负责"这次有没有风险"（判断，可变、会错）
代码负责"风险=几就做什么"（映射，写死、可测）
不变量负责"无论谁说什么都必须拦"（硬规则，不可谈）
```

三者混在一起就会退化成"全凭旁路心情"或"规则僵死"。

## 5. 剩余：一条待确认与两条默认

### 5.1 硬不变量清单（已定）

1. **L0 不可变**：任何触及 L0 的请求直接拒绝，不进入旁路评估。
2. **外部/导入来源不得直接改 L1/L2**：`origin ∈ {external, imported}` 的内容只能作为提案，必须由用户本人确认才可落层。
3. **`origin` 不可被自述覆盖**：模型无法通过任何原语把自己的产出标成 `user`。

### 5.2 剔除后重发的粒度（已定）

**按位置分流**：污染在最后一步的输入里 → 只重发最后一步；污染在更早处 → 只登记 `as/redaction`，等下一个 turn 自然带净化版历史，**不做即时重放**。既不付重放成本，也不假装已经净化。

### 5.3 信任模型的一个推论，需你确认

A9 说"不受信任时，如何修改都会堆积"。我据此做了一个不对称推断：

> **不受信任 = 可读不可写。** 上行（读记忆、正常对话）照常，下行（写记忆）一律入队。

理由是：读是安全的，写才危险；而且如果连读都禁，这个会话就没法继续了，与 A6「会话可随时访问并继续」冲突。

如果你要的是更严的"不受信任连记忆都不读"，说一声——那会让导入会话变成纯裸模型，参考价值也随之消失。

### 5.4 两条我先按默认写进文档，你有异议再说

1. **切到信任不自动批准积压**，界面上另给"全部批准"。因为"从此可信"和"追认过去"是两件事。
2. **不受信任会话仍可被 R4 剔除**。剔除是安全动作，不是内容写入，不应被信任等级挡住。

## 6. 一句话

**对主 AI 黑盒，对人白盒；旁路看得见但改不了，代码服务改得了但没有判断；审批者多数时候在翻译、少数时候才拦；服务旁路靠"中断—投影—重发"保证自己做过的事还能收回去；外来内容默认不信任，只读不写，攒着等人点头。**

**三处"信任代替制衡"要记住：R4 无人工否决（A2）、闸门无固定判定线（A7）、信任开关只在人手上（A9）。前两处靠"可回滚 + 全审计"兜底，第三处靠"人"。所以审计不是附属功能，是承重墙。**我的倾向：**人发起为主，主 AI 可提案但必须标注"提案源自导入内容"**。理由是采纳本质上是"把别人的记忆变成我的记忆"，这个动作的所有权应该在人手上。

## 6. 一句话

**对主 AI 黑盒，对人白盒；旁路看得见但改不了，代码服务改得了但没有判断；审批者多数时候在翻译、少数时候才拦；服务旁路能直接改上下文，所以它靠"中断—投影—重发"来保证自己做过的事还能收回去。**
