# P0：在 Pi 上验证注入闭环

> 这一版取代了原来的 dsh 版 P0（那份从 `tag pre-standalone-2026-10-24` 取）。
> 基座换成 `pi-coding-agent` 之后，验收标准没变，但落点全变了。

---

## 验收（唯一，与基座无关）

**关掉插件，对话质量与基线一致；打开插件，模型在第二步引用了它第一步没想到的事。**

只验上行不算通过——真正要看的是"它本来会答错 / 答得泛，注入之后答得具体"。

---

## 落点：三个钩子

| 机制 | Pi 钩子 | 备注 |
|---|---|---|
| 记忆注入 | `agent_before_settle` 追加 `custom_message` + `continue: true` | 注入角色是 `custom`，不是 user |
| 线索 | 上一条 assistant 的 reasoning，缺则退回正文（`cue: 'fallback'`） | 实测该模型不产 reasoning，走的就是兜底 |
| 轮次上限 | 扩展自己计数，`message_end` 里遇到用户新发言就清零 | pi 不设上限 |
| 审计 | 同时追加一条 `custom`（`customType: as/injection`），只进存档不进上下文 | 可回放 |

## 实测记录（2026-10-25）

**环境**：`pi-coding-agent@1.4.0`、`deepseek-v4-pro`、Windows、扩展从源码直载。
**种子**：`用户曾说缓存层不要用 Redis，改用进程内 LRU，因为部署环境不允许额外中间件。`

**同一提问**：`缓存层应该用什么？不要读任何文件，一句话回答。`

| | 注入关闭 | 注入开启 |
|---|---|---|
| 回答 | "缓存层一般用 **Redis**（高性能、支持过期与分布式），简单场景可用内存缓存如 node-cache……" | "按你之前的约束，缓存层用**进程内 LRU**（如 Caffeine），**不要用 Redis**，因为部署环境不允许额外中间件。" |
| 会话存档 | 无 `as/*` 条目 | `custom as/injection {round:1, ids:[…], cue:"fallback"}` + `custom_message as/memory` |
| Provider 请求次数 | 1 | 2（注入后续跑一次） |

**结论：通过。** 关闭时它推荐了 Redis——正是用户明确排除的方案；开启时它说出了"部署环境不允许额外中间件"这个仓库里查不到的前提。

---

## 三条顺带确认的事实

1. **`cue: "fallback"` 不是异常。** 该模型不产出 reasoning 块，走的是"退回过正文"的兜底路径，仍然命中了正确记忆。16.2 那条暂缓的"伪思考"方案因此可以更从容——先看 fallback 的命中率够不够。
2. **注入以 `custom` 角色落地。** 模型把它当"系统补充"而非用户发言，不需要 dsh 时代那套"这不是用户的新请求"的措辞苦撑（虽然仍保留了，作为双保险）。
3. **只有 1 轮注入。** `maxRounds=3`，但第二轮回忆不到新东西就不注入，turn 自然结束——"滤空即结束"按设计生效。

## 实测记录 2：下行写入与跨会话（同日）

**目标**：证明记忆能"自己长出来"——不靠种子配置，而是从对话里写进去，并在**另一个进程**里被想起。

三次连续运行，同一个库文件，无 `AS_SEED`：

| 轮 | 输入 | 结果 |
|---|---|---|
| 1 | `记住：我的项目叫 Halcyon，缓存层用进程内 LRU。` | 抽取出 1 条写入库：`origin=user, trust=0.9`，正文 `我的项目叫 Halcyon，缓存层用进程内 LRU` |
| 2 | `我的项目叫什么？不要读任何文件` | 回答："**你的项目叫 Halcyon**，而不是我根据目录名猜测的 pi-probe" |
| 3 | 重复第 1 轮 | 条目数仍是 1（相似度 0.82 阈值去重生效） |

**结论**：跨进程的持久化与召回成立。第 2 轮那句"而不是根据目录名猜测的 pi-probe"很有意思——它先泛化了，然后被注入纠正。

审计条目也齐全：写入轮有 `as/write`，召回轮有 `as/injection` + `as/memory`。

**暴露的一个问题**：第 3 轮里模型说"记忆与刚才确认一致，无需修正"——因为它刚在用户发言里看过同一句话，注入是冗余的。说明召回缺少"**已经在上下文里了，就别再递一次**"这一层。记下，属于注入筛选的改进项。

## 实测记录 3：压缩接管（部分完成）

**做了什么**：`context` 里称重（`ctx.getContextUsage()` 返回 `{tokens, contextWindow, percent}`），`turn_end` 里到阈值就调 `ctx.compact({ customInstructions })`，把"不可移出"的条目与"未完成步骤"点名给摘要器；同一次运行只触发一次。

**两个必须记住的坑**：

1. **不能在 `context` 钩子里调 `compact()`。** 实测直接让正在飞的请求中断，输出 `This operation was aborted`。它必须放在 turn 结束之后。
2. **`compact()` 在小上下文上是静默无操作的。** `prepareCompaction` 需要超过 `keepRecentTokens`（默认 20000）。低于这个量时既不回调 `onComplete` 也不回调 `onError`——所以调用方必须自己设超时兜底，否则会把 turn 卡死。

**未完成的部分**：在 `--print` 模式下（单 turn、进程随即退出），`compact()` 调用出去后既没有回调、也没有落下 `compaction` 条目。也就是说**触发路径通了，压缩本体没观测到**。可能是 print 模式没有可交互生命周期，需要 TUI 或长会话再验。

诚实结论：**称重、阈值、指令、防重入已就位；真实压缩待验。**

## 实测记录 4：压缩的真相，与 turn 内折叠

### 压缩为什么"没执行"

探针把 `session_before_compact` 打点出来后才看清：

```
trigger at 35480 tokens
before_compact { tokensBefore: 35480, toSummarize: 0, firstKept: "1387804f", keepRecentTokens: 20000 }
err: AbortError: This operation was aborted
```

**`messagesToSummarize: 0`**——不是"没触发"，而是**没东西可压**。pi 的压缩按 **turn 边界**切分；当整个会话只有一个 turn（工具调用再长也算同一 turn），切点落在 turn 起点，于是没有任何消息可摘要，`compact()` 抛 `AbortError`。

而 `compact()` 的第一行是 `await this.abort()`——这解释了为什么在 `context` 钩子里调它会打断正在飞的请求。

**结论：pi 的压缩只对"跨 turn 的历史"有效。单 turn 内膨胀（大工具结果）它管不了。**

### 所以我们自己补了一层：turn 内折叠

在 `context` 里，超过阈值就把**较早的 `toolResult`** 换成一行索引：

```
[已折叠｜较早的工具结果｜原文 1392 字] 需要细节请重新执行，或从归档检索。
```

保留最近 `AS_FOLD_KEEP`（默认 2）条原文，其余折叠。

**实测**（三次读大文件）：

```
[as] folded 3 tool result(s) at 0.3%
回答：big1.txt 的第一行是「第 0 行：…」   ← 正确
```

存档侧核对：

| 项 | 结果 |
|---|---|
| `as/fold` 审计 | 存在：`{"count":3,"at":0.003}` |
| 存档里的 toolResult 长度 | `1392, 124, 124, 124`——**原文完整** |
| 存档里是否有"[已折叠]"字样 | **没有** |

**折叠是视图行为，不写存档。** 这与 `context` 钩子的"非破坏性"语义完全一致。

## 实测记录 5：压缩由我们自己驱动

pi 的压缩两条路都不通（单 turn `toSummarize: 0`；跨 turn `Nothing to compact`），那就自己压。

**做法**：`context` 里超过阈值时，把较早的一段交给**旁路模型**，用"按轮纪要"的提示词压成一份摘要，替换掉那一整段；失败则退回确定性折叠（一行索引）。

提示词按对话形状分三种（`compress.ts` 的 `choosePrompt`）：

| 形状 | 额外要求 |
|---|---|
| 工具密集 | 每个工具调用合并成"用什么工具、拿到什么结论"，**不留原始输出**；失败的调用留一句原因 |
| 对话密集 | 用户改口写成"最初 X → 改为 Y"；偏好与禁忌显式写出 |
| 混杂 | 优先保任务骨架：目标 / 约束 / 进度 / 下一步 |

**实测**（三次读大文件）：

```
[as] digest 2 messages -> 173 chars
[as] digest 3 messages -> 96 chars
[as] digest 2 messages -> 61 chars
回答：big1 第一行是「第 0 行：…」   ← 正确
```

存档侧：`msg:toolResult` 6 条**原样保留**，`as/digest` 3 条、`as/compact_view` 3 条审计；存档里**没有**纪要文本。压缩同样是视图行为。

### 踩到的 400：孤儿 tool 消息

第一版切点落在 `toolResult` 上，把它的 `assistant(tool_calls)` 一起折掉了，服务端直接报：

```
Messages with role 'tool' must be a response to a preceding message with 'tool_calls'
```

规则是：**被保留的 `toolResult` 的发起者也必须保留**，所以折叠区间要结束在"发起者的上一条 assistant"处。这条写进代码注释了。

### 一个观察：纪要会自我嵌套

第二次压缩时，上一次的纪要也在待压区域里，于是"纪要的纪要"会被再压一遍。目前看是好事（自然形成分层压缩），但要知道细节会一层层变薄。若将来发现丢失过多，再引入"保留原始纪要、只压新内容"的增量策略。

## 实测记录 6：按轮压缩（全局视野，按轮写回）

上一版是"整段换成一份纪要"，问题有两个：纪要会自我嵌套，而且顺序感全丢。

改成按轮之后：

**视野**：模型一次看到一批轮次（默认 10 轮一批），所以能发现"T4 与 T2 重复"这种跨轮冗余。
**写回**：逐轮原地替换，**顺序不变，最小单元是一轮**。
**不完全视野**：带保护的轮只读可见。三个来源，**没有一个靠正则识别用户措辞**：

| 来源 | 谁决定 |
|---|---|
| 含工具调用 | 结构（拆散 tool 配对会 400） |
| 最近 N 轮（默认 2） | 工作区规则 |
| 打标 | **维护旁路**写进 `turn_mark` 表，压缩侧只读 |

标记的键是该轮首条用户消息的 `timestamp`——消息本身没有 id，时间戳是唯一稳定锚点。

四种落地形态：`压缩文本` / `[DUP Tk]` → 占位或丢弃 / `保护轮` → 原样 / `解析不出` → 原样。

**实测**（四轮连续会话，全部可压）：

```
[as] turn compress 5/5 (dropped 0)
    【T1】[user] 记住词：水水水，只回收到。[assistant] 收到
    【T2·与 T1 重复，已省略】
    【T3】[user] 给出九位数123456789，只回数字。[assistant] 123456789
    【T4·与 T1 重复，已省略】
    【T5·与 T1 重复，已省略】
```

用户给的理想形态是这个：

```
turn1：我嗡          turn3：123456789         turn5：水是
turn2：是水          turn4：（重复，省略）
```

两者一致。

**三个约束仍然成立**：turn 边界只能用 `user` 消息切（消息无 id）；不能拆散 tool 配对（否则 400）；合并轮次会改变时间感，所以本实现**从不合并**。

**打标链路实测**（手工往 `turn_mark` 写一条 `commitment`，锚定 T1）：

```
[as] turn compress 2/3 (dropped 0)
    【T2·与 T1 重复，已省略】
    【T3】用户要求给出九位数123456789，只回数字。
```

T1 **没有**被改写，但 T2 被判成"与 T1 重复"——说明模型确实读到了保护轮。**只读可见**这条设计成立。

## 实测记录 7：人看原文，AI 看视图

这是 `context` 钩子的天然分工，不需要额外实现：

| 谁 | 看到什么 | 为什么 |
|---|---|---|
| 人 | **原文** | pi 的界面渲染会话存档，而存档从未被改 |
| 主 AI | **遗忘机制运行后的视图** | `context` 只改发出去的那一份 |

验证方式：压缩后检查会话 jsonl，`toolResult` 原样、无"已折叠/纪要"字样（前两节已做过两次）。

### 观测入口（新增命令）

| 命令 | 作用 |
|---|---|
| `/as-view` | 打印上一次压缩各轮的处置：`压 → …` / `= 重复 Tn` / `保护（原因）` / `原样` |
| `/as-memory` | 打印记忆库前 20 条，含状态与被取代指针 |

两者都只是**读**，不改变任何东西。

### 踩到的坑：末轮绝不能压

把 `AS_KEEP_RECENT` 设成 0 时，最后那一轮（正是**当前要回答的发言**）也被压了，模型收到的是压缩后的问句，直接答"我看这段记录里没有新的指令"。

修法：**最后一轮无条件保护**（`reason: 'current'`），与配置无关。压缩永远只处理历史。

## 实测记录 8：维护旁路（第一版）

它每 N 轮回头看一次，只做两件事：

| 产出 | 落地 |
|---|---|
| `MARK Tn <原因>` | 写 `turn_mark`，压缩侧只读 |
| `REMEMBER <事实>` | 走与"记住 X"同一条写库路径，但 `origin=model`（trust 更低），并做同一套去重 |

**为什么用行式契约而不是 JSON**：模型写 JSON 时经常夹带解释文字；行式协议坏一行只丢一行，JSON 坏一个括号全废。

**节拍必须持久化**：每次 `pi` 调用都是新进程，内存计数活不过一次会话。所以"上次维护到第几轮"写在库的 `meta` 表里（`maint_last`），跨进程接着数。

**实测**（两轮，`AS_MAINT_EVERY=2`）：

```
[as] maintain: mark 1, remember 1

turn_mark:  1792920831624  commitment
meta:       maint_last = 2
memory:     model 0.6 | 用户的项目名是 Halcyon
审计:        as/maint {"marked":1,"remembered":1,"window":2}
```

锚点核对：`1792920831624` 正是第 1 条用户消息的 timestamp——**标在了立承诺的那一轮**，没标错。

**闭环验证**（同一会话再推进两轮，强制压缩）：

```
[as] turn compress 3/5 (dropped 0)
    【T2】用户说项目叫 Halcyon…
    【T3】用户闲聊"今天天气不错"…
    【T4】用户闲聊"文件有点乱"…
```

**T1（被标 `commitment`）没有出现在改写列表里**——维护旁路的标被压缩侧正确遵守，T5 因是当前轮同样保护。

## 实测记录 9：merge / supersede 的自动判定

此前只有 `supersede()` / `merge()` 两个方法，没人调用——状态机齐了但不会动。

**谁来判**：维护旁路。它本来就要读最近若干轮，顺手给一份"记忆清单"，让模型判关系：

```
SUPERSEDE <旧编号> <新编号>   ← 同一事实的新旧版本
MERGE <旧编号> <新编号>       ← 旧的信息被新的完全包含
```

**为什么不能靠字面相似度**：`我住在上海` 与 `我搬到北京了` 的二元组 Jaccard 是 **0**——共享的二元组一个都没有。这种判定必须靠语义，只能交给模型。

**为什么"拿不准就不写"**：乱合并会把记忆吃掉。所以提示词里明确写了"只是话题相关、或两条可以并存，都不写"。

**实测**（两轮）：`记住：我住在上海` → `记住：我搬到北京了`

```
[as] maintain: mark 2, remember 0, relate 1
 superseded  我住在上海    -> m-…-1（北京那条）
 active      我搬到北京了
```

### 顺带修掉的冗余

第一版同时输出 `SUPERSEDE` 和一条 `REMEMBER 用户已从上海搬到北京`——同一件事被存了两遍。

加了**确定性后置过滤**：本轮若有关系落地，补记内容与"新条目"的二元组相似度 ≥ 0.2 就丢弃。现在 `remember 0`。

（0.2 是个很松的阈值，只用来抓"同一句话的改写"，不做语义判断。）

**未验证**：`MERGE` 分支没有构造出自然场景，只验了 `SUPERSEDE`。

## 实测记录 10：可编辑的标签树

记忆从"平面"变成"有位置"。写入时旁路指定路径，但**路径不会自动补齐**。

**写入契约**（维护旁路与将来的实时旁路共用）：

```
TAG 项目                                    ← 新建标签，一次只建一层
REMEMBER 项目/Halcyon | 项目名 Halcyon…      ← 归到这个标签下
```

### 四条规则（都写在 `ensureTag` 里）

| 规则 | 值 | 违反时 |
|---|---|---|
| 根节点 | 固定为 `记忆`，**代码级保护**：不可合并、不可修剪 | 整条拒绝 |
| 父级不自动创建 | 一次只建一层 | 整条拒绝 → 退回 `其他` |
| 层数 | **不限** | — |
| 标签总数 | **不限** | — |
| 单条标签字数 | **≤7（标点不算）** | 整条拒绝 |

漏写 `记忆/` 前缀的路径，系统自动挂到根下——约定靠提示词说，兜底靠 `ensureTag` 做。

**方向不再限定**：合并哪边留下、哪边并走，由旁路自己判断。代码只守一条线——根不能动。

**确定性过滤已移除**（补记的语义级后置过滤）：理由是**误判的修复成本不对称**——
确定性过滤判错了，要 AuthenticSelf 来修；模型判错了，模型更新后自然恢复。
代价是偶尔多一条改写副本（`用户现居北京，此前住上海` 与 `我搬到北京了` 并存），可接受。

**为什么父级不自动创建**：自动补齐等于让模型随手甩一条四级路径就走，树会长出一堆没人复用的枝。要求逐层创建，成本落在模型身上——**它必须先翻现有标签，找不到才往下挖**。这是用成本换复用。

**为什么单条要 ≤7 字**：一条标签如果长成一句话，它就不再是"位置"而是"摘要"，树会退化成正文。7 字是"位置"的上限。

**为什么层数与总数不设限**：那是**自动归类机制**的活——按内容自动归位、定期合并同义标签。用静态上限去挡，会把该分的东西挤在一起。

### 单测（12 项全过）

```
PASS  a/b（父不存在）→ 拒绝      PASS  七个字正好 → 允许
PASS  a（第一级）→ 允许          PASS  八个字超限 → 拒绝
PASS  a/b（父已存在）→ 允许      PASS  带标点但不足七字 → 允许
PASS  a/b/c/d（逐层已建）→ 允许   PASS  标点撑门面但实字超标 → 拒绝
PASS  五层（逐层已建）→ 允许      PASS  x/y（父不存在）→ 拒绝
```

### 端到端

```
[as] maintain: mark 2, tag 0, remember 2, relate 0

标签:   行程安排、项目信息
记忆:   [项目信息] 项目名 Halcyon，基于 Pi 框架，缓存使用进程内 LRU
        [行程安排] 用户下周去杭州出差三天
```

`tag 0` 是因为模型直接用了**一级标签**（不需要父级），比挖深层更省事——这正是我们想要的行为：优先浅层、优先复用。

---|---|---|
| 层数 | 3 | 拒绝建，退回 `其他` |
| 单层字数 | 12 | 拒绝建，退回 `其他` |
| 标签总数 | 200 | 拒绝建，退回 `其他` |

**为什么上限要写在代码里**：提示词约束是劝告，模型心情好时遵守。上限写在 `ensureTag` 里，是闸门。

**实测**（两轮）：

```
[as] maintain: mark 2, remember 1, relate 0

标签:   项目、项目/Halcyon        ← 父子路径自动补齐
记忆:   [项目/Halcyon] active 项目名 Halcyon，基于 Pi 框架，缓存使用进程内 LRU
```

**另一条事实没被记住**（"下周去杭州出差三天"）——模型判定为一次性细节。这属于判断口径问题，不是 bug；如果希望日程类也留，得在提示词里单列一类。

## 附：自动归类机制（出处与本项目落点）

"自动归类"这个词在两处出现过，指的是两件不同的事，都得对上。

### 出处一：原始构思的「记忆整理」

`source/AuthenticSelf.txt` 第 50 行，认知中间层职责表里：

> 记忆整理：**episodic → semantic**，摘要、冲突检测、过期、遗忘

第 111 行，MVP 第二步：

> 加**异步记忆整理旁路**：摘要、去重、重要性评分、冲突标记

同一份文件的第 53 行还有一行相关但不同的事：

> 任务旁路：后台小模型处理**分类、抽取**、草稿、校验

**要点**：归类不是"给每条打个类标签"这么简单，而是**把情景记忆提炼成语义记忆**——一次具体的对话（episodic）被整理成一条可复用的结论（semantic），旧的情景记录可以降权或归档。

### 出处二：我们自己定的「单一层 + 自动归类」

`01-architecture.md` §4.1，标题就叫这个（D6 / D10）：

> 不存在"条目库"与"文档库"两个实体，也不按长度分表。只有一个 `MemoryEntry`，长短是它身上一个**由代码服务算出来的派生标记**。
>
> **归类是注入路径的分流，不是存储的分家。**

这里"归类"指的是 **`span` 分流**：短条目直接注入，长条目交给旁路裁决 full / excerpt / summary / skip。

**这正是"不限字数"的出处**——长内容不靠字数上限管，靠分流机制管。所以标签不需要承担"限制长度"的职责，它只需要短（≤7 字），因为它是**位置**不是**内容**。

### 四项工作，我们做到哪

| 整理动作 | 出处 | 现状 |
|---|---|---|
| 摘要 | 两处都提 | ✅ 按轮压缩产出纪要 |
| 去重 | 出处一 | ✅ 二元组 0.82 + merge |
| 冲突检测 | 出处一 | ✅ supersede（同一事实的新版本） |
| 过期 / 遗忘 | 出处一 | ⬜ 五区未实现 |
| **同义标签合并 / 路径上提** | 出处一（"整理"的应有之义） | ⬜ **缺** |

最后一行是标签树当前最大的缺口：树会漂——`项目` 与 `工作/项目` 可能同时长出来，某个路径下只有一条记忆却占了三级。**这靠定期整理解决，不靠建的时候限制**（这也是为什么不设层数上限）。

## 实测记录 11：实时旁路与来源分层

实时旁路（每回合一次调用）统一三件事：注入决策（DROP/REWRITE）、冲突合并、提取写入。**直注已移除**——旁路是唯一闸门，它不可用时宁可本轮无注入（错注的代价大于漏注）。

召回是双通道：词（正文二元组）+ 标签（线索包含标签段即命中）。实测「住在哪个城市」与「我搬到北京了」正文零重叠，经 `记忆/用户/城市` 标签段命中——受控词表比任意正文稳定。

### 「我」指谁：由来源决定，不是一刀切

第一版提示词写「记忆里的『我』指用户本人」——**这是错的**。设计文档（source:494）写的是：

> 记忆注入必须携带来源标签与置信度……**外部输入、模型生成与用户事实应分层存储**。

所以指代规则是：

| 来源 | 「我」指谁 | 处理 |
|---|---|---|
| `user` | 用户（那是用户的原话） | 保留或 REWRITE 成第三人称 |
| `model` | 应为第三人称（整理产物） | 原样；若仍是「我…」且明显是用户的事，REWRITE 澄清 |
| `external` | 按内容判断 | 含混不构成 DROP 理由 |

候选清单因此带上了 `来源:` 标注（`（日期｜来源:user）`），旁路看得见才能判。REMEMBER 一律第三人称书写——`user` 原话可保留「我」，整理产物不要。

实测：`来源:user` 的「我搬到北京了」被 REWRITE 成「用户已搬到北京，现居北京」，回答正确。
