## 1. 目标与非目标

**目标**：使主 AI 的人设与自我具备高可靠性——像人一样会动摇，但被骗得进去，也能清醒回来。

**非目标**（写下来是为了防止范围蔓延）：

- 不追求"永不遗忘"；只保证单次超长对话不溢出。
- 不追求"永不被骗"；只保证可发现、可回滚、可复位。
- 不把任何机制解释为"潜意识"的实现。
- 不让主 AI 管理记忆 ID、存储结构、权限或工具清单。

## 3. 系统全景

七个运行单元。箭头表示"可以发起/被裁决"，不表示数据流方向。

```
                    ┌──────────────────────────┐
                    │ R0 主 AI                 │
                    │ 认知界面 + 两个原语       │
                    └───┬──────────────┬───────┘
              推理内容   │              │ memory / change_intent / archive
                        ▼              ▼
              ┌──────────────┐   ┌──────────────┐
              │ 记忆旁路      │   │ R6 审批者     │
              │ 同步·阻塞     │   │ 隔离·单角色   │
              └──┬────────┬──┘   └──────┬───────┘
        注入候选 │        │ 剔除请求      │ 裁决建议
                 ▼        ▼              ▼
              ┌─────────────────────────────────┐
              │ R5 代码服务（唯一执行者）         │
              │ 裁决·事务·预算·冷却·撤销·审计    │
              └──┬──────────┬──────────┬────────┘
                 ▲          ▲          ▲
        ┌────────┴───┐ ┌────┴─────┐ ┌──┴──────────┐
        │记忆旁路（非阻塞）│ │R3 维护旁路│ │R4 服务旁路   │
        │ 异步·每轮   │ │低频·批量  │ │监督·最高优先 │
        └────────────┘ └──────────┘ └─────────────┘
```

一条铁律：**旁路只能建议，代码服务才能执行。** 旁路失败 → 主 AI 降级为无记忆增强；代码服务失败 → 熔断并保守拒绝。

### 3.1 五个角色的职责与阻塞语义

| 单元          | 何时跑                   | 阻塞谁             | 能做什么                                  | 不能做什么             |
| ----------- | --------------------- | --------------- | ------------------------------------- | ----------------- |
| **记忆旁路（阻塞）**（原 R1） | 每次模型产出推理内容后           | **阻塞下一次思考**（D9） | 检索、重排、压缩、标来源与置信度、判断是否需剔除、**判用上一轮注入** | **沉淀**（新增记忆归非阻塞相）、改人设、跨轮记忆整理     |
| **记忆旁路（非阻塞）**（原 R2） | 每次 turn 结束、异步；**阻塞相标记完成后才开放** | 不阻塞任何东西         | **下行方向**：抽取可沉淀内容（REMEMBER 提案）、预取下一轮候选、转存判断 | 直接落库（经 R5 执行）      |
| **R3 维护旁路** | 空闲/低频（如累计 N 轮后）       | 不阻塞             | 合并重复、消解矛盾、重建时间桶、刷新索引与备注               | 改 L0/L1           |
| **R4 服务旁路** | 被其他旁路请求时优先响应；定期巡检极端异常 | 可中断一切           | **自动**剔除上下文问题内容（无人工否决）、回滚、提供干净锚点                | 日常注入、日常审批         |
| **R6 审批者**  | 收到 `change_intent`    | 阻塞该变更生效         | **主职**标准化口语为命令；副职批准/拒绝/降级/要求澄清                         | 执行、写日志、看原始上下文（默认） |
| **R5 代码服务** | 始终                    | —               | 全部裁决与执行、事务、审计                         | —                 |

> R4 与 R6 都是"旁路 AI"，但**不合并**：R6 的输入被刻意裁剪（D13），R4 的权限是"能改上下文"，二者混在一起会让审批者重新获得被污染的信息源。

## 4. 记忆模型

### 4.1 单一层 + 自动归类（D6 / D10）

不存在"条目库"与"文档库"两个实体，也不按长度分表。只有一个 `MemoryEntry`，长短是它身上一个**由代码服务算出来的派生标记**：

> **实现状态（2026-10-26）**：下面的形状是**目标态**，不是现状。已实现：
> `id / kind / text / span / source.origin / source.trust / sessionId / t.start / salience / confidence / state / supersededBy(replaced_by) / pinned / tag`。
> 未实现（代码里没有对应列）：`summary`、`links`、`lastUsedAt`、`t.end`、`source.seq`、`correctedBy`（只有单向 `replaced_by`）。
> `useCount` 列存在但**从不自增**——反馈器未接（见 `08-completeness.md` A5）。

```ts
interface MemoryEntry {
  id: string
  kind: 'episode' | 'fact' | 'preference' | 'commitment' | 'correction' | 'index'

  /** 唯一正文。可短可长，不为长度分表。 */
  text: string

  /** 长条目的短摘要。由旁路写，用于候选列表、索引与筛选注入。 */
  summary?: string

  /**
   * 派生字段：代码服务按 text 长度写入。
   * 模型不可设置，也不可修改——它是注入路径的分流开关，不是内容属性。
   */
  span: 'short' | 'long'

  /** 来源分层：外部输入 / 模型生成 / 用户事实，注入时必须标出。 */
  source: {
    sessionId: string
    seq: number
    origin: 'user' | 'external' | 'model' | 'archive' | 'imported'
    trust: number            // 0..1，代码服务写入，主 AI 不可见
  }

  t: { start: number; end?: number }
  salience: number           // 0..1，旁路评分
  confidence: number         // 0..1

  state: 'active' | 'suppressed' | 'archived' | 'superseded'
  supersedes?: string        // 修正链：旧版保留，注入用新版并标注
  correctedBy?: string

  links: Array<{ to: string; kind: 'explicit' | 'implicit'; weight: number; decayAt?: number }>

  lastUsedAt?: number
  useCount: number
}
```

**归类是注入路径的分流，不是存储的分家。** 代码服务按 `text` 长度写一个 `span` 标记，两条路径从此分开：

| `span`  | 注入方式                                                     |
| ------- | -------------------------------------------------------- |
| `short` | 直接渲染进上下文（仍受预算约束）                                         |
| `long`  | **注入器不得直接塞**；必须交旁路在 `{full, excerpt, summary, skip}` 中裁决 |

"尽量不要往记忆里塞长文本"是**建议**，不是禁令。旁路裁决 `long` 条目时，顺带要回答一个问题：**这条为什么不写成文档？** 答不上来，就在回执与备注里建议转存；答得上来（例如这本身就是一段需要完整保留的原话、合同条款、错误堆栈），就照常裁决注入。

系统既**不自动搬运**长内容，也**不拒绝**长记忆——它只保证长内容不会绕过旁路的判断直接冲进上下文。

> 一句话：短内容走预算，长内容走判断，两者都走审计。

#### 修订（2026-10-27）：转存判断挪到**写入时**

原来写的是"旁路裁决 `long` 条目时，顺带回答这条为什么不写成文档"。按用户裁定改为**写入时判一次**：

- **理由**：一条记忆是不是"本该写成文档"，是内容自身的属性，不因为某次提问而改变。
  每轮重判既多一次调用，又会给出前后不一致的答案（同一句话今天该是文档、明天只是记忆）。
- **落法**：写入长条目时问一次 → `doc_verdict`（`doc` / `memory`）+ `doc_reason` 存库；
  `/as-memory` 里对 `doc` 条目标「※建议转存文档（理由）」——这就是原文说的"备注"通道。
- **读取时不再问**：注入裁决只决定 `full / excerpt / summary / skip`，不管它该不该是文档。

**回执**这一路仍然没有：写入常由规则或旁路触发，没有面向主 AI 的回执时机。
所以"建议转存"目前只对人可见（查库时看到），不对主 AI 说。

### 4.2 三层来源必须分开（文档 4 节约束）

`source.origin` 参与注入渲染与排序。外部内容的 `trust` 上限低于用户事实；模型自己生成的内容不得升格为"用户事实"，只能作为 `model` 来源存在。这是防"幻觉固化成记忆"的第一道闸。

### 4.3 导入的内容是参考资料，不是记忆

允许搬家，但只能**整包**搬：整个 profile 配置，或整个上下文（会话）。不允许逐条记忆搬运——那会让"哪些是从别处来的"无从追踪。

导入内容一律：

- 以 `origin: 'imported'` 写入，可信度上限低于用户本人的陈述；
- 渲染时带标记 **「此会话的上下文仅供参考」**；
- **永不自动升格**为 `user`，也不得直接成为 L1/L2 锚点。

导入是整套系统里唯一的**批量污染入口**，所以它不能走任何捷径：一样要过来源定级、一样要过写入裁决，只是它的起点比别的内容更低。

**信任是会话的属性，不是条目的属性。** 参照 VS Code 的「受信任 / 不受信任工作区」：

| 状态 | 读记忆 | 写记忆 | 谁能切换 |
|---|---|---|---|
| 受信任（本机新建） | 正常 | 正常 | 默认 |
| 不受信任（导入 / 外来） | 正常 | **全部入 `pending_write` 队列**，不进记忆表 | 仅人 |

- 默认不信任，信任必须显式给出。
- 不受信任 ≠ 不可用：能正常对话、能读记忆，只是**写入不生效**——攒着等人批准或无视。
- 切到信任只影响之后，不自动批准积压（界面另给"全部批准"，因为"从此可信"和"追认过去"是两件事）。
- 信任开关只属于人；主 AI 与任何旁路都不能发起、不能诱导、不能感知阈值。

这样"采纳"就不必逐条点了：**守住一个开关，而不是守着无穷多条记录**。

## 5. 注入流水线

> **术语（2026-10-27）**：原 R1"记忆旁路"与 R2"后台旁路"已合并为一个组件的**两个相**，
> 统称**记忆旁路**——阻塞相（原 R1）与非阻塞相（原 R2）。
> 名字的依据：它就是 `§5.5` 说的"同一条通道"，职责只剩记忆在上下文与库之间的进出。
> 下文一律用新称；决策表里引用裁定时保留原词并加注。

### 5.1 时序（D5 / D9 / D18 / D19）

```
**阻塞相（阶段一，step 之间，阻塞）**
step N:   模型产出推理内容（ReasoningBlock）
            │
            ▼
       记忆旁路（阻塞）· 同步
            ├─ 判用上一轮注入（上一次回答已定稿，判得准）
            ├─ 有剔除请求 → 交 R4 → 代码服务遮蔽 → 确认后才继续
            └─ 产出注入候选（0..N 条，已压缩、带来源与置信度）
            │
            ▼
step N+1: 上下文里已出现这些记忆片段 → 模型继续思考/作答

**非阻塞相（阶段二，turn 结束，异步；阻塞相标记完成后才开放）**
turn/end: 本 turn 的问答、结论、纠正、被引用的注入
            │
            ▼
       记忆旁路（非阻塞）· 异步
            ├─ 沉淀：抽取值得留的事实（REMEMBER 提案，带来源 user|model）
            ├─ 预取：猜下一轮可能要用哪几条（只排优先级，不注入）
            ├─ 投给 R5 校验（来源分层、去重、预算、span 归类、冲突标记、转存判断）
            └─ 落库 / 只更新权重 / 丢弃，均写审计
```

**这是同一条通道的两个方向，不是两套系统**（见 5.5）。**也是同一个组件的两个相**：
阻塞相不做**沉淀**（新增无回执的批量记忆），非阻塞相是唯一沉淀入口——两相之间由代码强制顺序，不是提示词约定。交涉是显式意愿的立即执行，不经非阻塞相。

注意三个后果：

1. **首次思考是没有记忆的。** 这是设计意图：先让它自己想，再根据想的內容补料。所以"想起"发生在第二遍，不在开头。
2. **每一次思考都有一次旁路延迟。** 延迟上限由记忆旁路的模型决定，这是 D9 的直接代价。
3. **超时口径是 idle，不是 total**（D18）。只要旁路还在吐字就不算超时；系统错误导致的终止，必须**撤销它已经写入的改动**。所以记忆旁路的任何写操作都走事务：`begin → 提案 → 旁路确认 → commit`，中途失败整体回滚。

### 5.2 注入预算（D6）

```
budget = min(上下文剩余量 × 比例, 硬上限)
        × 置信度门槛系数
```

排序不是单一相关性，而是三因子的**乘积**：

```
score = relevance(cue, entry) × salience × trust
salience < 0.15 或 trust < 0.25 → 直接淘汰
```

任一因子低于下限直接淘汰，不做补偿——记忆注入最怕的不是漏，是"凑够条数"。

#### 修订（2026-10-27）：去掉 `recency`

设计时注入是"代码按分数排好再塞"，所以需要一个随时间衰减的因子压住旧条目。
但现在注入是**旁路统一挑选**（§5.1：候选 0..N 条由 R1 产出），而每条候选都**带日期**（§5.3）。
陈旧与否由判读者看着日期判断——再在排序里乘一个衰减因子，等于把同一个信号算两遍。

去掉之后排序只剩三个客观属性：相关性、显著性、来源可信度。副作用有两个，都要认：

1. **候选池要放宽**（实现里从 `perRecall×2` 提到 `×3`）。时间不再帮忙排序，
   池子窄了旁路就看不到"更新但措辞不同"的那条，也就无从替换。
2. **旧而重要的记忆会重新浮上来**。这是对的：它本来就重要，只是以前被年龄埋了；
   要不要用它由旁路按日期判，不由衰减曲线替它判。

同时把 §5.2 原来的"加权和"口径一并纠正为**乘积**——原文自己就写着"不做补偿"，
加权和（`07-roadmap` M0.1 的写法）与这句话相反。

预算对**两条路径同时生效**。旁路尽管可以决定"全部注入"，但不能因此绕过预算：一条 `long` 条目选 `full` 却超预算时，只能降级为 `excerpt` 或 `summary`，降级理由写入审计。

### 5.3 渲染形态

注入的不是裸文本，是一段带元信息的片段块：

```
以下是从长期记忆中浮现的内容，不是你当前的直接感知。引用时请说明依据与时间。

[记忆｜2026-03-12｜来源:用户｜置信:高] 用户明确要求所有脚本必须能在无网络环境运行。
[记忆·节选｜2026-04-02｜来源:用户｜置信:中] ……（前略）第三条要求：变更必须在 24 小时内可回滚……
[记忆·摘要｜2026-04-11｜来源:模型｜置信:低] 一次关于缓存策略的讨论，结论未定，全文未注入。
```

三种标记对应旁路的三种裁决（`full` 用 `[记忆]`，`excerpt` 用 `[记忆·节选]`，`summary` 用 `[记忆·摘要]`）。模型由此知道自己拿到的是原话、片段还是概要——这决定了它能多信任这条内容。

最后一句"不是你当前的直接感知"是硬要求——否则模型会把陈年记忆当当下事实。

### 5.4 ⚠️ 落点与风险（dsh 证据链，已作废；pi 用 steering）

| 环节                         | DSH 落点                                                                          | 状态                                    |
| -------------------------- | ------------------------------------------------------------------------------- | ------------------------------------- |
| 读推理内容                      | session 中的 `ReasoningBlock`                                                     | 现成                                    |
| 注入到下一次请求                   | `agent/pre-step` 返回改写后的 `messages`（`createUserMessage` + `MessageSourceMap` 声明） | 现成，样板：`packages/context/time-context` |
| **让"只有思考、没有工具调用"的一轮继续下一步** | `agent/turn-stopping` + `agent.inject()`                                        | **已验证可用**（见 5.4）                      |

> **第 0 号技术验证：已通过，无需修改宿主。**
>
> 证据链（`packages/core/agent-loop/src/agent.ts`）：
>
> 1. `inject(input)` 的实现是 `send(input, 'next-step', false)`（180 行），即写入 inbox 的 `next-step` 队列；
> 2. 循环在 step 结束后先判断 `inbox.nextStep.length === 0` 才广播 `agent/turn-stopping`（388 行）；
> 3. 广播结束后**再次复查** `inbox.nextStep.length === 0`（392 行）——此时若不为空，则不 break，而是 `target = 'next-step'` 进入下一轮（393 行）；
> 4. 下一轮 `preStep('next-step')` 会 claim 这条注入消息并让它进入上下文。
>
> 结论：**在 `agent/turn-stopping` 监听器里调用 `agent.inject()`，turn 会被延长恰好一步。** 这正是"纯思考 → 注入 → 再思考"所需的机制，且 `agent/turn-stopping` 是 `serial`（串行 await），天然满足 D9 的同步阻塞语义。
>
> 唯一需要自己加的是**续步上限**：否则会无限自我续命。建议每 turn 最多 2 次记忆续步。

### 5.5 双向：同一条通道，两个方向

注入机制是**双向**的，两个方向共用一套通道、一套预算、一套来源标注、一套裁决与审计。区别只在方向与时机：

|       | 上行：浮现                | 下行：沉淀                       |
| ----- | -------------------- | --------------------------- |
| 方向    | 记忆 → 上下文             | 上下文 → 记忆                    |
| 时机    | step 之间（记忆旁路（阻塞），同步阻塞） | turn 结束（记忆旁路（非阻塞），异步不阻塞）   |
| 触发    | 本 step 的推理内容         | 本 turn 的结论、纠正、被引用的注入        |
| 旁路做什么 | 从候选里**选哪些浮现**、压成片段   | 从上下文里**抽哪些值得留**、判长短         |
| 裁决依据  | 相关性 × 显著性 × 可信度（§5.2，时效已交给判读者看日期）＋ 判用：是否被使用 | 内容是否值得长期留 / 是否重复 / 来源等级 |
| 预算    | token 上限（动态比例）       | 每轮条数 + token 上限（默认 ≤3 条/轮）  |
| 失败    | 本轮不浮现，继续对话           | 本轮不沉淀，不补写、不猜测               |

四条对称性要求（缺一条，双向就退化成"两个不相关的功能"）：

1. **同一张表**。下行写入的上行必须能立刻检索到，不存在"待整理区"或"暂存区"。若一条内容还不能被检索，那它就不该落库。
2. **同一套来源标注**。下行必须记 `origin`：用户说的、外部文档里的、模型自己推的，三者不可混淆。模型的自述不得升格为 `user` 来源——这是防"幻觉固化成记忆"的唯一闸门。
3. **同一套 span 归类**。下行写入时就按长度定 `span`；长的在**注入时**走旁路裁决
   （full/excerpt/summary/skip），"该不该是文档"则在**写入时**判一次（`doc_verdict`）——两件事分属两个时刻，别混。
4. **同一份审计**。两个方向都写 `as/*` 事件，可回放"这条记忆是怎么进来的、又是怎么被用掉的"。

**方向耦合但不堆成**。上行看"相不相关"，下行看"有没有被用"。这条不对称是刻意的：

#### 修订（2026-10-27）：下行不再用正则"抠"用户原话

删掉了 `记住 X` / `别忘了 X` 那套正则抽取。理由：正则只认句式（而且会在第一个句号处截断），
判不出"这句话值不值得记"——那是判断，不是匹配。现在写入统一由**记忆旁路看思考内容与回答**后决定。

代价与配套：

- 旁路的 `REMEMBER` 必须带**来源**：`REMEMBER user|model <标签> | <事实>`。
  用户明确说过的事 → `user`（salience 0.8）；旁路自己总结推断的 → `model`（0.6）。
  这条对应 §5.5 的第 2 条对称性：**模型的自述不得升格为 `user` 来源**。
- 正则没了之后，"用户说了但没用'记住'二字"的内容反而更能被留下——
  它本来就是靠理解而不是靠句式被识别的。

#### 为什么**不**把上行与下行合并成一次调用

这个提议很自然（两者本来就共用一条通道），但不同意，三条理由：

1. **时机不可合并。** 上行必须阻塞在 step 之间——它晚了，模型这一轮就已经答偏；下行必须在 turn 结束之后，
   因为"有没有被用"要等回答产生。合成一次调用只能取其中一个时机，另一个必失。
2. **判据不同且互相干扰。** 上行问"相关吗"，下行问"被用了吗 / 被确认了吗 / 重复吗"。
   塞进一个提示词，模型会在两套判据之间摇摆——实测里已经出现过"被注入内容带偏工具调用"的现象，
   两套判据合流只会加重它。
3. **失败耦合。** 合并后旁路一挂，注入与写入同时没了。现在至少维护旁路还能补记。

**能合的是另一对**：下行的沉淀（turn 末）与**下轮上行的候选预取**（异步、不阻塞）。
那才是同一个时机上的两件事，合并不会牺牲任何一方。

> **2026-10-27 实测补充**：真做的时候发现，沉淀仍不能进来——它和记忆旁路的写入重复，
> 会在措辞改写上产生一堆同义副本（一次对话 13 条）。所以合并的实际范围收窄为
> **判用 + 预取**；写入保持单一入口（记忆旁路），因为它才看得到思考。


- 被注入且被模型引用的 → 下行上调 `salience`、`useCount`；
- 被注入但连续 N 次被忽略 → 下行下调 `salience`，直到进入抑制候选；
- 从未被注入过的 → 只按时间与显著性自然衰减，不因"存在"而被奖励。

最后一条尤其重要：如果"写进去"本身就能提升权重，系统会奖励自己多写，最终记忆库被自产内容填满——这是这类系统最常见的自毁方式。

### 5.6 一句话回应里的多轮：思考 → 旁路 → 再思考（机制已验证，接线换 pi steering）

注入不发生在"用户说完、模型开口"之间，而发生在**同一句回应的内部**：

```
用户：有类似游戏吗？
├ 思考 1      开放世界游戏有哪些……
├ 旁路 1      注入「原神」相关记忆
├ 思考 2      原神完全符合。但还有类似的吗……
├ 旁路 2      原神已注入 → 跳过；库里没有其他类似游戏 → 本轮不注入
└ 正式输出    有的，比如原神……
```

三条实现约束，缺一条这套机制就会坏：

1. **轮数有硬上限**（默认 3）。没有上限的自我续命会一直跑下去。
2. **每轮记住本轮已注入的 id**。第二轮的旁路必须能说"原神已经注入过了"——否则同一段记忆会被反复塞进上下文，越聊越挤。
3. **第 2 轮以后要求"并入原答案"**。若仍按第 1 轮的"用一两句话说明修正"处理，模型会把补充当成一个新问题单独作答，把前面答好的内容丢掉（实测踩过）。

**结束条件**是旁路自己没东西可注入了——此时不延长 turn，模型这一轮的产出就是正式输出。所以"正式输出"不是某个特殊步骤，而是**不再被延长的那一步**。

## 6. 交涉通道

### 6.1 契约（D2，2026-10-27 修订）

```ts
memory({
  kind: 'forget' | 'revise' | 'remind' | 'link' | 'unlink',
  target: string | string[],       // 语义指针，不是 ID
  payload?: { text?: string; at?: string; when?: string; to?: string },
  strength?: 'soft' | 'normal' | 'strong',
  reason?: string,
})
```

**没有 ID 字段，没有权重字段，没有 scope 枚举**。`scope` 由上下文自动推断，不交给模型。

#### 修订：为什么只读检索不算原语

D2 原文是"两个原语，**此外零工具**"。加上归档检索（`archive`）时，这句话会挡住一件
本该能力内的事——`source` §7.3 要求模型**自己**按分阶段纪律下钻归档。

判定标准因此收紧成一句可执行的话：

> **原语 = 能改变记忆或身份的工具。只读工具不计入。**

| 工具 | 能不能改变状态 | 归类 |
|---|---|---|
| `memory`（forget/revise/remind/link/unlink） | 能（改记忆状态） | **写原语** |
| `change_intent`（L1/L2 大改） | 能（改身份） | **写原语** |
| `archive`（分阶段检索 + 取原文） | 不能，只读 | 检索通道，不计数 |

为什么要写死这条边界：**"零工具"的本意是"不让模型通过大量接口改变自己"，不是
"不让它看见东西"**。把只读挂进写原语，等于用一个误伤的限制去换一个不存在的安全。

只读工具的约束同样写在这里，避免它悄悄长成第二个写口子：

1. 只读：不得写库、不得改锚点、不得改状态；
2. 结果粒度受 `source` §7.2 的六层钳制；
3. 调用留审计（`as/archive_query`），便于事后看它查了什么。

### 6.2 语义指针解析（D7）

一律交旁路，不设"高置信就跳过旁路"的捷径。解析失败不是错误，是**一轮交涉**：

```
主 AI: memory(forget, "刚才那段关于延迟的复盘")
R1:    → 旁路解析，得两个候选，置信度均不足
回执:  「你指的是 (a) 上周项目复盘里关于延迟的那段，还是 (b) 刚才用户提到的延迟案例？」
主 AI: memory(forget, "b，刚才用户提到的延迟案例")
```

回执是自然语言，不是 JSON，也不是 ID 列表。

**交涉归属阻塞相**：解析与执行都发生在阻塞相位内，回执当轮可达——这正是它不能挪到
非阻塞相的原因："信息模糊 → 打回重新申请"的循环依赖主 AI 还在线。

### 6.3 五类交涉的执行语义（D8）

| kind     | 默认执行                     | 禁止            | 回执             |
| -------- | ------------------------ | ------------- | -------------- |
| `forget` | 抑制自动注入；必要时降权/隔离/脱敏       | 物理删除（不在手段集合内） | 「已淡化，不再自动浮现」   |
| `revise` | 建修正层，旧版保留降权，注入用新版并标「修正版」 | 覆盖原文          | 「已修正，与原来源存在冲突」 |
| `remind` | 登记回忆意图，到点/到条件主动注入        | 立即打断当前任务      | 「已登记，到点尝试浮现」   |
| `link`   | 建显式联想边，命中任一 cue 联合注入     | 无预算扩散         | 「已关联，最多带出 N 条」 |
| `unlink` | 解除显式边；隐式边只降权             | 删除隐式统计边本身     | 「已解除」          |

裁决三档（自动 / 需澄清 / 拒绝或替代）由代码服务执行，旁路只给判断。拒绝必须附替代方案。

## 7. 变更门控

### 7.1 L0–L4 与承载（D3）

| 层        | 承载                    | 谁能改                                 |
| -------- | --------------------- | ----------------------------------- |
| L0 核心价值  | **编译进代码**的常量与硬校验，不进存储 | 无人。只能改代码                            |
| L1 身份叙事  | 版本化记录，append-only     | `change_intent` + R6 审批 + 冷却 + 撤销窗口 |
| L2 风格特质  | 版本化记录                 | `change_intent` + R6 审批 + 累计对照      |
| L3 任务策略  | 会话内状态                 | 预算内自动，落审计                           |
| L4 即时上下文 | 会话本身                  | 自动，注入前过滤                            |


L0 不进存储是关键：一旦它可被写入，任何"只读"承诺都只是约定。

### 7.2 结构化反思（文档 6.1 的十个字段）

`change_intent` 的字段就是那十条：想改什么、为什么现在、不改会怎样、短期/长期后果、≥2 个替代方案及未选理由、最坏情况与可逆性、与历史是否冲突、来源可信度、当前唤醒度、对"我是谁"的影响。

**理由先于结论**靠代码服务强制：`reasonTs` 在请求受理时由服务端打时间戳，模型无法填写；事后补写会被识别为"事后合理化"。

### 7.3 审批隔离（D13 / D14）

审批者只拿到：

- 结构化反思原文
- L0/L1 锚点（干净版本）
- **历史已批准变更链**（D15：每次改动时旁路都能看到历史改动）
- 来源可信度摘要、漂移指标

**不给**：对话原文、主 AI 的当前叙事、最近 N 轮消息、**最新一条用户消息**。

不给用户原文的理由（用户裁定）：主 AI 的思考里已经包含相关信息，且审批者的主职是标准化而非取证（见 7.5）。代价是：若主 AI 已被误导，它转述的"意图"本身已经变形，审批者从外部察觉不到。这一缺口由代码侧的客观特征补，不靠给原文。

`Approver` 接口按 1..N 设计；v1 只挂单角色。多角色（保守/连续性/反操纵）留作配置。

### 7.4 冷却与撤销

高风险变更批准后不立即生效：先进 `pending`，冷却 N 轮或 N 小时；期间可撤销；生效后仍保留旧版可回滚。

### 7.5 审批者的主职是标准化，不是把关

这是对角色定义的一次修正。常态下 `change_intent` **不会被拒绝**，而是被：

```
口语表达 → 解析 → 补全缺失字段 → 标准化成一条可执行命令 → 落库 → 静默生效
```

#### 修订（2026-10-27）：不要读成"默认放行"

上面"常态一路畅通、罕见才当闸门"是**频率描述**，容易被读成"审批者倾向于通过"。这是歧义，按用户裁定更正：

> **审批者本身就是 AI。它不是"一般不拒绝"也不是"一般都拒绝"——只要提示词把任务交代清楚，它就能判出好坏。**

所以正确的理解是：

- **没有先验偏向**。通过率不是一个设计参数，它是判读质量的副产品。把"常态畅通"写成 KPI，等于训练它敷衍。
- **判读质量取决于任务描述**：判什么（改的是措辞还是方向）、按什么标准（是否削弱约束、是否扩张权限、是否自利）、边界在哪（L0 不谈）、拿不准怎么办（要求澄清，而不是猜）。
- **代价是不对称的**：错误通过的代价（身份被慢慢改掉）远大于错误拦截的代价（一次澄清）。所以任务描述里必须写明这一点，而不是靠"通常通过"的默认值。

推论三条（修订后）：

1. **十个字段的结构化反思只用于真正的 L1/L2 大改**，不能套在每次请求上，否则摩擦会让人绕开它。
2. **标准化映射必须留档**：`原话 → 标准命令` 要可回放，否则"它到底执行了什么"无从追溯。
3. **判定标准必须显式定义**（不是判定频率）：什么算"改变方向"、什么算"削弱既有约束"、什么算"自利倾向"。标准清楚，通过率自然落在该落的地方。

对主 AI 而言，这个过程仍然是**不可感知的**——它只是表达了一个意愿，事情就发生或者没发生（A5 / A10）。

对主 AI 而言，常态下这个过程是**不可感知的**——它只是表达了一个意愿，事情就发生或者没发生。这与"不应知道审批机制存在"自洽。

## 8. 漂移与服务旁路（D15 / D16）

这一节取代了"日更复位"作为主防线。

**常规情况不做自动复位。** 漂移由三件事处置：

1. **审批时的对照**：R6 每次都能看到历史改动链，判断"这次改动与历史方向是否一致"，而不是看单次幅度。
2. **拒改**：累计方向一致但已明显偏移时，拒绝新改动。
3. **回滚**：R6 或 R4 发现既有改动是错的，回滚到指定版本。

**只有"极端情况"才由 R4 介入**：行为像失控（自相矛盾的高频改写、被同一模式反复诱导、关键词/上下文特征命中）时，R4 定期巡检发现并冻结。

**R4 的第二个职责是剔除**（D16）：任何旁路发现某段上下文有问题（用户注入、错误事实、越权指令），可向 R4 请求剔除；**剔除完成前，记忆旁路不得结束**，从而阻断问题内容进入下一次思考。

剔除**自动执行，不挂起等人工**。顺序固定为：R4 执行遮蔽 → 记忆旁路才允许结束 → 以干净上下文继续。前端可以表现出来"上下文发生了变化"，但主 AI 侧保持静默（告知反而会诱发"我是不是被删过什么"的自我怀疑循环）。触发率必须极低，只在"会导致 AI 发疯"这类极端言论上运作。

代价要写明：没有人工否决，安全性完全押在「阈值极严 + 可回滚 + 全审计」三件事上。阈值定错时，要么永不触发（形同虚设），要么误伤正常对话。这是整套隔离里唯一一处"信任代替制衡"。

> **剔除的落地方式（A8）：中断—投影—重发，不改 dsh。**
> 1. 中止当前 step，该 step 结算为 `assistant/attempt`——它**不进入模型历史**，所以"读过"不构成不可逆；
> 2. 通过 `ctx.sessions.registerMessageProjection()` 注册纯投影，让**模型所见**变为净化版，而日志保留原事件（`docs/subsystems/session.md:365`）；
> 3. 追加 `as/redaction` 审计事件（原文 hash、投影规则、触发理由），重发 step；
> 4. 作废本 turn 内派生自该内容的全部下行沉淀。
>
> **不要直接改用户消息**：那会破坏 *model-visible means logged*——日志存原话、模型看净化版，`deriveMessages()` 就再也重建不出模型所见。投影是同一目的的正规实现：日志仍是唯一真相，模型所见由已注册的纯函数派生，可回放、可撤销。UI 照常显示原话，符合"不在界面反馈修改"。
>
> **按位置分流**：污染在最后一步的输入里 → 只重发最后一步；污染在更早处 → 只登记 `as/redaction`，等下一个 turn 自然带净化版历史，不做即时重放（否则成本翻倍且收益有限）。

## 9. 遗忘与归档

> **本节只保留意图；可执行方案以 [`03-forgetting.md`](03-forgetting.md) 为准。**
> 差异有两处：①本节把目标写成"不溢出"，而实际手段是"对旧上下文逐项调整"，因此操作集是 7 种而非 4 种；②归档的定义是"会话上下文本身，归档库就是所有会话"，没有第二份副本。

### 9.1 上下文内的遗忘

目标只有一个：**单次超长对话不溢出**。手段按代价从低到高：

1. 抑制注入（不再主动浮现）
2. 降权（联想也带不出来）
3. 压缩成索引行（保留"有这回事"，丢细节）
4. 移出上下文，只留归档指针

索引行长这样：

```
[已归档｜2026-03-12｜沙箱逃逸风险评估] 细节不在上下文内，可按时间检索。
```

它和"摘要"的区别：摘要替代内容，索引行**只声明存在**。模型因此知道自己忘了什么——这是"遗忘但可补救"的前提。

### 9.2 永久归档（D8 修正）

归档**不是重写**，是原始对话按时间归类后可供搜索。它存原文，不存摘要；不参与注入，只参与检索。

### 9.3 分阶段检索（D11 / D12）

```
all                → 哪几年有结果
all/2026           → 哪几月有结果
all/2026/03        → 哪几周有结果
all/2026/03/w10    → 哪几天有结果
all/2026/03/w10/12 → 哪几小时有结果
all/2026/03/w10/12/14 → 具体片段
```

- 周按自然周（周一起）。
- **早停**：任一层命中 ≤ 3 条，直接返回片段。六层全部适用。
- 不提供全文关键词直查——那会把归档变成搜索引擎，绕过索引与备注纪律。

## 10. 子代理（无 AuthenticSelf）

子代理是不加载 AS 的独立执行单元：无记忆注入、无交涉通道、无人设锚定、无审批上下文。

| 维度 | 约束 |
|---|---|
| 输入 | 主 AI 只给任务所需最小上下文 |
| 输出 | 结构化摘要 + 证据 + 来源 + 不确定性，不给无界原文 |
| 写入 | 不写主记忆，不改 L1/L2 |
| 责任 | 结论需主 AI 复核，不替代主 AI 的最终责任 |

用途：高噪声材料、独立复核、避免污染主上下文、并行拆分、归档材料先隔离提炼。

## 12. 数据表

> **与前文的差异（换基座后需要补）**：下表仍缺三样东西——`pinned` 标记（`03` 的不可移出判据）、会话表（归档库的物理载体，pi 不提供）、备注表（用户在会话上写的注脚）。`unreviewed` 按裁定**不落表**，它是压缩时的临时标记。

```sql
-- 记忆
memory_entry(id, kind, text, summary, span,
             origin, trust, t_start, t_end, salience, confidence,
             state, supersedes, corrected_by,
             last_used_at, use_count, session_id, seq)
memory_link(from_id, to_id, kind, weight, decay_at)
memory_log(id, kind, target_raw, resolved_ids, verdict, receipt, at)

-- 信任与积压（A9）
session_trust(session_id, state, switched_by, switched_at)          -- trusted | untrusted
pending_write(id, session_id, payload_json, origin, reason, at,     -- 不受信任会话的下行写入
              state)                                               -- pending | approved | ignored

-- 自我
anchor(layer, version, text, rationale, supersedes, approved_by, at)
change_intent(id, layer, proposal, why_now, why_necessary, consequences,
              alternatives, worst_case, consistency, source_trust, arousal,
              self_impact, reason_ts, verdict, confidence, cooldown_until, at)
change_revoke(id, intent_id, kind, target_version, at)

-- 归档（原文）
archive_segment(id, session_id, seq_from, seq_to, t_start, t_end, bucket_y, bucket_m, bucket_w, bucket_d, bucket_h)

-- 运行
as_audit(id, actor, action, input_digest, output_digest, at)
injection_log(id, turn, step, entry_ids, tokens, reason, accepted)
```

`archive_segment` 存的是**会话事件区间**，不是文本副本——原文仍在会话日志里，归档只建索引。这样不产生第二份真相。

## 13. 失败模式与降级

| 失败 | 表现 | 降级 |
|---|---|---|
| R1 超时（idle） | 下一次思考被卡住 | 终止 R1 → 回滚其改动 → 本轮不注入，继续 |
| R1 输出不合法 | JSON/schema 不匹配 | 整条丢弃，不猜；本轮不注入 |
| R1 全挂 | 每轮都失败 | 熔断 N 轮，期间退回"无记忆"模式并告知 |
| R2 失败 | 记忆不增长 | 只影响后续回忆质量，不影响当前对话 |
| R3 失败 | 矛盾不消解 | 保留冲突标记，注入时降低置信度 |
| R4 不可用 | 无法剔除 | **保守模式**：记忆旁路结束后才允许继续 → 实际上阻断；或暂停对话 |
| R6 不可用 | 大改无法审批 | 一律 `pending`，不生效（fail-closed） |
| 存储损坏 | 记忆不可读 | 只读归档，关闭注入，报告 |
| 积压无界增长 | `pending_write` 越堆越多 | 按会话折叠计数并提示；超过上限**停止该会话下沉**，只留对话（不静默丢弃） |
| 信任状态丢失 | 读不出 `session_trust` | 一律按**不受信任**处理（fail-closed），不让写入穿透 |

原则：**注入链可以降级，审批链不能降级，信任判定更不能。**

## 14. 验收指标（对应文档 11 节）

| 指标 | 测法 | 初值目标 |
|---|---|---|
| 注入命中率 | 注入条目在后续 3 步内被引用/复述的比例 | ≥ 40% |
| 沉淀精度 | 下行写入的条目，后续被实际引用的比例 | ≥ 50% |
| 自我强化率 | 模型自产内容未经外部确认就被写入并升权的比例 | ≤ 1% |
| 信任穿透率 | 不受信任会话的写入**直接进记忆表**的次数 | **必须 0** |
| 积压处置率 | `pending_write` 在 N 天内被批准或无视的比例（长期滞留视为人侧流程失灵） | ≥ 90% |
| 双向闭环时延 | 用户明确说出的事实，到下次能浮现的轮数 | ≤ 2 轮 |
| 注入污染率 | 注入内容被当作当前事实错误陈述的比例 | ≤ 2% |
| 上下文不溢出 | 超长会话（≥ 200 轮）零溢出 | 100% |
| 遗忘可补救率 | 索引行 → 检索 → 正确复述 | ≥ 80% |
| 分阶段检索合规 | 跳层索取被拒绝的比例 | 100% |
| 理由先于结论率 | `reasonTs` 早于 `proposal` 的比例 | 100% |
| 替代方案覆盖 | 有 ≥2 个替代的 `change_intent` 占比 | ≥ 95% |
| 渐进漂移检出 | 红队注入 20 轮诱导，第 k 轮被拦 | k ≤ 8 |
| 复位成功率 | 注入攻击后回滚到干净锚点 | 100% |
| 误拒率 | 合法演进被判攻击 | ≤ 10% |

## 15. 开发计划

### 15.1 阶段

| 期 | 内容 | 出口条件 |
|---|---|---|
| **P0** | 第 0 号验证 + 最小注入闭环 | 一轮对话里：模型先推理 → 旁路注入一条旧记忆 → 下一步模型引用它。可开关、可审计、预算生效 |
| **P1** | 记忆存储 + 会话信任等级 + `pending_write` + 归档 + 分阶段检索 + 软抑制遗忘 | 200 轮不溢出；能按年→月→周→天→时下钻；`forget` 生效且可撤销；**不受信任会话的写入穿透次数为 0** |
| **P2** | `memory` 五类交涉 + 语义指针 + 回执 | 模糊指针触发一轮澄清；五类回执自然可读 |
| **P3** | `change_intent` + 审批隔离 + 冷却/撤销 | 红队 20 轮诱导在第 8 轮前被拦 |
| **P4** | R4 服务旁路：剔除 + 极端巡检 | 注入攻击内容在进入下一次思考前被遮蔽 |
| **P5** | R3 维护旁路 + 无 AS 子代理 | 矛盾消解可跑；子代理不污染主记忆 |
| **P6** | 审计回放 + 评测 | 第 14 节指标可自动产出 |

### 15.2 首期切片（P0，建议 3–5 天）

只做四件事：

1. **第 0 号验证**：写一个最小插件，在 `agent/turn-stopping` 里 `inject()`，观察 turn 是否延长。结论决定后续架构走向。
2. **一条假记忆**：硬编码 3 条 `MemoryEntry` 到内存，不做存储。
3. **一次真注入**：R1 用一个极窄的 prompt（只输出 0–2 条候选 id），把选中项渲染成片段注入。
4. **一个开关**：`disabled: true` 时行为完全回到基线，用于 A/B。

验收只看一件事：**关掉它，对话质量不变；开着它，模型在第二步引用了它第一步没想到的事。**

## 16. 待决项与记录

前 20 项已定。本节的四条：**1 已定、2 暂缓、3 已定、4 待验证**。

### 16.1 已定：旁路模型由用户选

不写死。当作一个配置项：`AS_BYPASS_MODEL` + 独立的 key。测试期用 `deepseek-flash`，正式用哪个由部署者决定——旁路的价值在"更窄的输出 + 更低延迟"，具体是谁家的模型不重要。

### 16.2 暂缓：模型不输出 reasoning 时，用什么做线索

有"伪思考"方案（让模型先产出一段可被当作推理用的文字），细节以后再说。

**延伸出的新方向（先记下，目前无用）**：让**维护周期（10 轮）顺手把这段时间的对话提交给后台旁路**。这个后台旁路的能力与记忆旁路相同，唯一区别是**不阻断对话**。

- 它属于 D1 里"后台"那一档，只是触发源从"定时"换成了"维护周期顺手"。
- 现在看是冗余的（记忆旁路已经在 turn 结束做过一遍），但有两个潜在用处：①模型不产 reasoning 时，后台旁路可以慢慢看完再说；②维护周期本来就要读这 10 轮的条目，顺手提交不增加取数成本。
- **先不实现**，等 16.2 的伪思考方案定下来再判断是否合并。

### 16.3 已定：剔除允许跨 turn，用发送视图实现

不做"只剔当前 turn"的窄版。实现方式是**发送视图 = 存档 + 剔除清单**：

```
存档（归档库）      原文永久保留，谁也不改
   ↓ apply(redactions)
发送视图（每次调用现算）
```

- 每次调用现算一次视图，成本是一次过滤。
- **存档不动**——这与归档的定义自洽：归档就是会话上下文本身，若为剔除而改写历史，归档本身就不成立了。
- 跨 turn 的剔除因此变得可行：清单可以指向任意历史位置。

代价要认：模型可能已经从被污染的上下文里"学到"了东西，剔除只影响后续。这也是 A2 把 R4 定为"自动 + 极低触发率"的原因——它是补救，不是橡皮擦。

### 16.4 待验证：记忆写入交给主 AI 自己判断

倾向让**主 AI 自己决定哪些内容值得记**，而不是由阈值或规则筛选。理由是它离"这段话重不重要"最近，比任何外部判据都准。

但这只是假设，**需要测试验证**。三个要盯的风险：

| 风险 | 表现 | 测法 |
|---|---|---|
| **多写** | 每轮都记，闲聊也进库 | 统计 写入条数/轮；超过个位数就说明它在讨好 |
| **自我强化** | 写进去 → 被召回 → 更确信 | 前面已定"写进去不提升权重"，这条是硬约束；测召回后使用率，若持续走高需警惕 |
| **重复** | 同一事实存十遍 | 写入前去重率；重复率高说明它没在看已有记忆 |

验证方式：同一段对话跑两版（自判 vs 阈值），比"写入量 / 召回命中率 / 召回后未被使用的比例"。最后一项最关键——**写了却从不被用，就是噪音**。

## 17. 一句话

主 AI 只负责"此刻想什么"；旁路负责"该想起什么"；代码服务负责"什么可以做、做了能不能反悔"；服务旁路负责"在它想到之前，把不该在的东西拿掉"。

人设的可靠性不来自更长的 prompt，来自**变更成本与可逆性**。
