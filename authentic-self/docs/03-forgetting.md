# 遗忘机制落地方案（从参考稿 §14 提取）

> 依据：参考稿《14. 遗忘机制（设计增补）》；基座改为 pi。
> 目的：把 §14 的意图压成可实现的结构，并标出必须由你拍板的点。

---

## 0. 先纠正我上一轮的误判

我把「只需保证单次超长对话不溢出」读成「只做压缩」，进而建议砍掉降权、隔离。**这个读法是错的。**

参考稿的读法是反过来的：**不溢出是靠"对旧上下文按需逐项调整"实现的**——重要的不动，不重要的只留下摘要/索引。要做到"逐项"，就需要分区、需要降权、需要索引化、需要补救通道。

所以结论不是"机制更少"，而是**粒度更细**。降权、脱敏、隔离在 §14 里都是明确的操作项，保留。

---

## 1. 骨架：五区 + 硬预算

**每次模型调用前只称重，不重新分区。** 分区是压缩时刻才做的事（见 6.3 的展开）：

```
可用预算 = 窗口 − 输出预留          ← 预留是用户可改的固定值（默认 8192）
每次调用：系统锚点 + 计划摘要 + 工作区 + 待注入 ≤ 可用预算 ? 发请求 : 触发一次压缩
```

| 分区 | 内容 | 策略 |
|---|---|---|
| **不可移出** | L0/L1 锚点、安全标记、用户明确纠正、未完成承诺、当前计划当前步骤 | 硬保留；压缩时先削别的区 |
| **计划区** | 计划摘要、步骤状态、开放问题 | 只留摘要，详细计划在外部计划板 |
| **工作区** | 最近 N 轮原文、当前任务相关记忆片段 | 按预算滚动，旧轮转压缩 |
| **可压缩** | 旧对话、低显著情景、重复信息、已解决分支 | 摘要/去重/降权/移出 |
| **索引区** | 摘要索引、线索、来源、置信度、归档指针、**用户备注** | 几乎不占原文，供补救重取与检索 |

**阈值**（相对可用预算）：70% 预警 → 85% 强制压可压缩区、限制新注入 → 95% 冻结非关键注入、保底截断并记录。

保底截断**只**作用于低优先级可压缩区，且必须产出「已移出可恢复」信号——不允许悄悄丢东西。

## 2. 操作集（七种）

| 操作 | 语义 | 可恢复性 |
|---|---|---|
| 压缩 | 多轮 → 情景摘要 | 原文归档，可回溯 |
| 去重 | 合并重复表述 | 保留来源 |
| 降权 | 降低自动注入优先级 | 可恢复权重 |
| 移出上下文 | 从当前上下文移除 | 保留索引与归档指针 |
| 索引化 | 生成线索/实体/时间/来源标签 | 支持线索重取 |
| 归档 | 原文移入受控归档 | 审计可回放 |
| 脱敏 | 敏感内容替换或屏蔽 | 原始受权限保护 |

**铁律：移出 ≠ 删除。** 移出的是"当前上下文里的位置"，不是记忆本身。

**审批分工**（照 §14.4）：
- 常规压缩、去重、低显著降权 → 代码服务按预算自动做
- 移出「用户明确事实 / 未完成承诺 / 安全标记」→ 要么旁路审批，要么事前打上不可移出
- 删除、修改长期记忆 → 走交涉通道（`memory_intent`）

## 3. 补救：R2–R5（R1 已取消）

| 级 | 方式 | 适用 |
|---|---|---|
| ~~R1~~ | ~~计划板回放~~ | **取消**：不建计划板，计划只活在上下文里（见 3.1） |
| R2 | 按线索取回情景摘要 | 细节模糊但索引在 |
| R3 | 按归档指针回原文片段 | 摘要不足或冲突 |
| R4 | 向用户澄清关键指代 | 线索不足或高风险 |
| R5 | 承认不可恢复 | 原文不可用且不可猜 |

原则：**先轻后重、先索引后原文、先计划后细节、先澄清后猜测。**

配套三条：重取计入预算；同一线索短时间内限流（防抖动挤出别的信息）；摘要重建必须带来源、置信度、版本。

### 3.1 取消 R1 的后果：计划会跟其他内容一样被压

不建计划板，代价是「上下文可以忘，计划不能丢」不再由结构保证。模型写下的计划就在对话里，压缩时和其他内容一样被摘要——而计划恰恰是最不该丢的那类。

两个不需要计划板的补丁，建议都做：

1. **压缩旁路的提示词硬约束**：压缩时必须保留**尚未完成的步骤与其状态**；可以压已解决的步骤，不得压掉"还没做的"。压缩本身就是一次 LLM 调用，这条写进它的提示词即可。
2. **维护旁路把计划段标 `important`**：它本来就在读这 10 轮的条目，认出"这段是计划"是顺手的判断，标上就 pin 住，不吃压缩。

两条加起来的效果接近计划板，但不需要外部存储、不需要登记流程、也不需要"未登记就单步降级"的强制机制。

### 3.2 备注：用户写给对话的注脚，不是旁路的产物

原教旨 G 要求归档「只能通过**索引、备注**、强制分阶段搜索」。这里的"备注"曾被我理解成"旁路自动生成的小结"，那是多余的——旁路已经产出摘要了，再多一层自动备注只是同义反复。

**备注 = 用户为对话加的注脚。** 由人写，不由模型写。

| | |
|---|---|
| **挂在哪** | 挂在**会话**上（一条会话可有多条备注），不挂在时间桶上 |
| **写什么** | 人话。"那次关于缓存的讨论最后定了 LRU""这段别删，还在跟进" |
| **怎么用** | 与分阶段时间检索**并列**运行：时间检索回答"哪几年/哪几月有结果"，备注检索回答"我给它写过什么"。两者命中同一批会话时取并集 |
| **注入吗** | 不注入。它是检索入口，不是记忆内容——这点和 `MemoryEntry` 分开 |

这样"备注"才真正补上了原文要求的那一层：**人记得某段时间发生过什么**，靠的是人自己那句话，而不是模型再猜一遍。

> 顺带一个语义澄清：**归档就是一个会话的上下文本身，归档库就是所有会话。**
> 叫"归档"只是因为旧会话一般不会再被启用，而"归档"比"在所有会话中搜索"更不出戏、也更好说。
> 所以归档不是第二份存储，不存在"归档副本与原文不一致"的问题——只有一个会话库，时间桶只是它的索引。
> 这也意味着**会话必须持久化**（pi 本身不提供），它是归档库的物理载体。

## 5. 分期（改编自 §14.9，已按裁定 4 调整）

| 期 | 内容 | 出口条件 |
|---|---|---|
| **F1** | 预算管理器（称重 + 阈值）+ 统一压缩 + 五区分类 | 200 轮不溢出；压缩产出「已移出可恢复」信号 |
| **F2** | 压缩、去重、索引化、归档 + `pinned` 打标（甲） | 被 pin 的条目在压缩后仍在；索引可反查原文 |
| **F3** | 补救 R2 摘要重注入 + R3 原文回溯 + 重取限流 | 被移出的内容能按线索取回，且带来源与版本 |
| **F4** | R4 澄清 + R5 承认不可恢复 + 补救失败检测 | 失败时不伪造细节，能给出不确定信号 |
| **F5** | `memory_intent(recall)` 与自然回执 | 主 AI 说"我记得有 X 但细节不清"能走通 |
| ~~F6~~ | ~~复杂请求识别 + 计划板 + R1 回放~~ | **取消**：LLM 本来就会对自己能判断出的复杂请求先展开计划，只需在系统提示词里告知（见 3.1 的两个补丁） |

F1–F2 是硬保证，必须先立住。原 F6 不成立为工程——它只是一条提示词。

## 6. 五点的裁定

| # | 问题 | 裁定 |
|---|---|---|
| 1 | pi 的 compaction | **接管**。关掉 pi 的裁剪，全部走本方案的五区。"不可移出区"必须由预算管理器掌握绝对优先权 |
| 2 | 输出预留 | **可被用户修改的固定值**（默认 8192 token）。阈值按「窗口 − 预留」的可用预算计算，不按裸窗口 |
| 3 | 逐项调整的粒度 | **不是每次调用都判定**。它的定位是"替代完全重写上下文的那种绝对有损压缩"；平时只做总量检查，**到达阈值后统一执行一次** |
| 4 | 计划板 | **规划完成后做**。R1 整层推迟，补救先只有 R2–R5 |
| 5 | 不可移出区谁维护 | **待讨论**，见 6.5 |

### 关于裁定 3：这条把方案简化了一半

初稿读起来像"每次调用前都重新分区"，裁定 3 把它拨回来了：

```
每次模型调用前：  只算总量（系统锚点 + 计划摘要 + 工作区 + 待注入 + 预留）
                  └─ 未超阈值 → 直接发请求（零额外开销）
                  └─ 超阈值   → 触发一次「统一压缩」
统一压缩：        五区分类 → 压缩/去重/降权/移出/索引化 → 写审计 → 记「已移出可恢复」
```

三个实际差别：

- **五区是压缩时刻的分类，不是每次调用的账本。** 平时不需要维护"这条属于哪个区"。
- 逐项调整只跟"完全重写上下文"对比才有意义——它的价值是**保住重要的**，而不是把每条都算一遍。
- 预算管理器退化成两个动作：**称重**（廉价、每次）与**做一次手术**（昂贵、偶发）。

阈值语义随之明确：70% 预警、85% 强制压缩、95% 冻结注入，全部相对「窗口 − 预留」的可用预算。

### 6.5 不可移出区怎么维护（已定：维护旁路批量标 + 尾巴现场判）

我原来担心竞态：标记还没写上，东西已经被压掉。**用"批量打标 + 未审尾巴"把它化解了**——因为未审的条目数被周期上界住，是可控的。

### 机制

```
维护旁路：每约 10 轮跑一次，批量给这段时间的条目打标（important / trivial）
压缩触发：任意时刻（由预算阈值决定），与 10 轮周期解耦
压缩时：  已打标 → 按标签处理
          未打标 → 自动带 unreviewed，交给压缩旁路当场判
```

以你给的例子：第 76 次触发遗忘时，前 70 条已被维护旁路标过，**剩 6 条**落在 `unreviewed`。

### 未审尾巴怎么处理

三点：

1. **数量有上界。** 未审条目最多是一个维护周期内的新增，量级是个位数。压缩旁路当场看这几条，成本远低于扫全量——这才是这个方案能成立的原因。
2. **`unreviewed` 是临时标记，不是状态。** 只在「有未标记条目需要开始遗忘」的那一刻打上，这一趟处理完就摘掉，条目回到正常流程。不落库、不累积，因此不需要容限计数。
3. **判不出就不改动。** 保守默认保留原文，而不是"没标就压"；它摘掉标记后进入正常流程，下一趟若仍未被打标，会再被临时标记一次。

> 第 3 条有个可接受的代价：维护周期是 10 轮，压缩可能在 76、78 两轮各发生一次，同一批尾巴会被判两次。量级是个位数，不值得为它引入"判定过"的持久记录——那会把临时标记变回状态。

<!-- 上一版计划里的"只保一审（2 次容限）"已删：临时标记不残留，容限就失去意义。 -->

### 第二道保险：明确记住的内容进记忆库

你补的这点很重要，它让"不可移出"不再是单点：

> 用户明确要求记住的内容，除了在上下文里，还会被**写进记忆库**。

所以即使上下文那条被压掉了，记忆仍在，可通过 R2/R3 取回。上下文里的 pin 只是"省一次取回"，不是唯一副本。

```
用户："记住，X"
  ├─ 记忆旁路在 turn 结束时写入 memory_store（origin=user, trust 高）  ← 第二道保险
  └─ 上下文条目打 pinned                                              ← 第一道，省掉将来的 R2/R3
```

这也顺带解决了原教旨里"想删掉某个记忆"——删的是库里那条，上下文自然不再注入。

### 两个细节（已定）

1. **"记住 X" 写库** —— 2026-10-27 起**正则抽取已删**：写库由记忆旁路·**非阻塞相**在 turn 结束时统一完成
   （它看得到完整回答，判断"值不值得留"比句式匹配可靠），来源由旁路标注（user = 用户明确说过，model = 自己推断）。
   好处不变：不新增模块、不新增写入路径；代价："这一轮说、下一轮就知道"要等 turn 结束——可接受。

2. **"10 轮"按 turn 计**（一句话的回应为一轮）。step 的数量受工具调用影响，同一件事可能三步也可能三十步，按 step 计会让维护周期不可预测。

### 附：为什么不让记忆旁路当主力

| | 记忆旁路 | 维护旁路 |
|---|---|---|
| 看的范围 | 本步推理内容（阻塞相）／本 turn 问答（非阻塞相） | 这 10 轮的全部条目 |
| 延迟位置 | **同步阻塞在思考之间** | 后台，不影响对话 |
| 能否对历史条目标 | **不能** | 能 |

记忆旁路仍然有用：它可以在**已经因为别的原因在跑**时顺手输出 `pin: [...]`（零增量成本）。但它替代不了批量标注——它没有账本。
