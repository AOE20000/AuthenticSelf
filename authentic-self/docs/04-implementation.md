# P0：在 Pi 上验证注入闭环

> 这一版取代了原来的 dsh 版 P0（那份从 `tag pre-standalone-2026-10-24` 取）。
> 基座换成 `pi-coding-agent` 之后，验收标准没变，但落点全变了。

---

## 验收（唯一，与基座无关）

**关掉插件，对话质量与基线一致；打开插件，模型在第二步引用了它第一步没想到的事。**

只验上行不算通过——真正要看的是"它本来会答错 / 答得泛，注入之后答得具体"。

---

## 落点：三个钩子

| 机制 | Pi 钩子 | 备注 |
|---|---|---|
| 记忆注入 | `agent_before_settle` 追加 `custom_message` + `continue: true` | 注入角色是 `custom`，不是 user |
| 线索 | 上一条 assistant 的 reasoning，缺则退回正文（`cue: 'fallback'`） | 实测该模型不产 reasoning，走的就是兜底 |
| 轮次上限 | 扩展自己计数，`message_end` 里遇到用户新发言就清零 | pi 不设上限 |
| 审计 | 同时追加一条 `custom`（`customType: as/injection`），只进存档不进上下文 | 可回放 |

## 实测记录（2026-10-25）

**环境**：`pi-coding-agent@1.4.0`、`deepseek-v4-pro`、Windows、扩展从源码直载。
**种子**：`用户曾说缓存层不要用 Redis，改用进程内 LRU，因为部署环境不允许额外中间件。`

**同一提问**：`缓存层应该用什么？不要读任何文件，一句话回答。`

| | 注入关闭 | 注入开启 |
|---|---|---|
| 回答 | "缓存层一般用 **Redis**（高性能、支持过期与分布式），简单场景可用内存缓存如 node-cache……" | "按你之前的约束，缓存层用**进程内 LRU**（如 Caffeine），**不要用 Redis**，因为部署环境不允许额外中间件。" |
| 会话存档 | 无 `as/*` 条目 | `custom as/injection {round:1, ids:[…], cue:"fallback"}` + `custom_message as/memory` |
| Provider 请求次数 | 1 | 2（注入后续跑一次） |

**结论：通过。** 关闭时它推荐了 Redis——正是用户明确排除的方案；开启时它说出了"部署环境不允许额外中间件"这个仓库里查不到的前提。

---

## 三条顺带确认的事实

1. **`cue: "fallback"` 不是异常。** 该模型不产出 reasoning 块，走的是"退回过正文"的兜底路径，仍然命中了正确记忆。16.2 那条暂缓的"伪思考"方案因此可以更从容——先看 fallback 的命中率够不够。
2. **注入以 `custom` 角色落地。** 模型把它当"系统补充"而非用户发言，不需要 dsh 时代那套"这不是用户的新请求"的措辞苦撑（虽然仍保留了，作为双保险）。
3. **只有 1 轮注入。** `maxRounds=3`，但第二轮回忆不到新东西就不注入，turn 自然结束——"滤空即结束"按设计生效。

## 实测记录 2：下行写入与跨会话（同日）

**目标**：证明记忆能"自己长出来"——不靠种子配置，而是从对话里写进去，并在**另一个进程**里被想起。

三次连续运行，同一个库文件，无 `AS_SEED`：

| 轮 | 输入 | 结果 |
|---|---|---|
| 1 | `记住：我的项目叫 Halcyon，缓存层用进程内 LRU。` | 抽取出 1 条写入库：`origin=user, trust=0.9`，正文 `我的项目叫 Halcyon，缓存层用进程内 LRU` |
| 2 | `我的项目叫什么？不要读任何文件` | 回答："**你的项目叫 Halcyon**，而不是我根据目录名猜测的 pi-probe" |
| 3 | 重复第 1 轮 | 条目数仍是 1（相似度 0.82 阈值去重生效） |

**结论**：跨进程的持久化与召回成立。第 2 轮那句"而不是根据目录名猜测的 pi-probe"很有意思——它先泛化了，然后被注入纠正。

审计条目也齐全：写入轮有 `as/write`，召回轮有 `as/injection` + `as/memory`。

**暴露的一个问题**：第 3 轮里模型说"记忆与刚才确认一致，无需修正"——因为它刚在用户发言里看过同一句话，注入是冗余的。说明召回缺少"**已经在上下文里了，就别再递一次**"这一层。记下，属于注入筛选的改进项。

## 实测记录 3：压缩接管（部分完成）

**做了什么**：`context` 里称重（`ctx.getContextUsage()` 返回 `{tokens, contextWindow, percent}`），`turn_end` 里到阈值就调 `ctx.compact({ customInstructions })`，把"不可移出"的条目与"未完成步骤"点名给摘要器；同一次运行只触发一次。

**两个必须记住的坑**：

1. **不能在 `context` 钩子里调 `compact()`。** 实测直接让正在飞的请求中断，输出 `This operation was aborted`。它必须放在 turn 结束之后。
2. **`compact()` 在小上下文上是静默无操作的。** `prepareCompaction` 需要超过 `keepRecentTokens`（默认 20000）。低于这个量时既不回调 `onComplete` 也不回调 `onError`——所以调用方必须自己设超时兜底，否则会把 turn 卡死。

**未完成的部分**：在 `--print` 模式下（单 turn、进程随即退出），`compact()` 调用出去后既没有回调、也没有落下 `compaction` 条目。也就是说**触发路径通了，压缩本体没观测到**。可能是 print 模式没有可交互生命周期，需要 TUI 或长会话再验。

诚实结论：**称重、阈值、指令、防重入已就位；真实压缩待验。**

## 实测记录 4：压缩的真相，与 turn 内折叠

### 压缩为什么"没执行"

探针把 `session_before_compact` 打点出来后才看清：

```
trigger at 35480 tokens
before_compact { tokensBefore: 35480, toSummarize: 0, firstKept: "1387804f", keepRecentTokens: 20000 }
err: AbortError: This operation was aborted
```

**`messagesToSummarize: 0`**——不是"没触发"，而是**没东西可压**。pi 的压缩按 **turn 边界**切分；当整个会话只有一个 turn（工具调用再长也算同一 turn），切点落在 turn 起点，于是没有任何消息可摘要，`compact()` 抛 `AbortError`。

而 `compact()` 的第一行是 `await this.abort()`——这解释了为什么在 `context` 钩子里调它会打断正在飞的请求。

**结论：pi 的压缩只对"跨 turn 的历史"有效。单 turn 内膨胀（大工具结果）它管不了。**

### 所以我们自己补了一层：turn 内折叠

在 `context` 里，超过阈值就把**较早的 `toolResult`** 换成一行索引：

```
[已折叠｜较早的工具结果｜原文 1392 字] 需要细节请重新执行，或从归档检索。
```

保留最近 `AS_FOLD_KEEP`（默认 2）条原文，其余折叠。

**实测**（三次读大文件）：

```
[as] folded 3 tool result(s) at 0.3%
回答：big1.txt 的第一行是「第 0 行：…」   ← 正确
```

存档侧核对：

| 项 | 结果 |
|---|---|
| `as/fold` 审计 | 存在：`{"count":3,"at":0.003}` |
| 存档里的 toolResult 长度 | `1392, 124, 124, 124`——**原文完整** |
| 存档里是否有"[已折叠]"字样 | **没有** |

**折叠是视图行为，不写存档。** 这与 `context` 钩子的"非破坏性"语义完全一致。

## 实测记录 5：压缩由我们自己驱动

pi 的压缩两条路都不通（单 turn `toSummarize: 0`；跨 turn `Nothing to compact`），那就自己压。

**做法**：`context` 里超过阈值时，把较早的一段交给**旁路模型**，用"按轮纪要"的提示词压成一份摘要，替换掉那一整段；失败则退回确定性折叠（一行索引）。

提示词按对话形状分三种（`compress.ts` 的 `choosePrompt`）：

| 形状 | 额外要求 |
|---|---|
| 工具密集 | 每个工具调用合并成"用什么工具、拿到什么结论"，**不留原始输出**；失败的调用留一句原因 |
| 对话密集 | 用户改口写成"最初 X → 改为 Y"；偏好与禁忌显式写出 |
| 混杂 | 优先保任务骨架：目标 / 约束 / 进度 / 下一步 |

**实测**（三次读大文件）：

```
[as] digest 2 messages -> 173 chars
[as] digest 3 messages -> 96 chars
[as] digest 2 messages -> 61 chars
回答：big1 第一行是「第 0 行：…」   ← 正确
```

存档侧：`msg:toolResult` 6 条**原样保留**，`as/digest` 3 条、`as/compact_view` 3 条审计；存档里**没有**纪要文本。压缩同样是视图行为。

### 踩到的 400：孤儿 tool 消息

第一版切点落在 `toolResult` 上，把它的 `assistant(tool_calls)` 一起折掉了，服务端直接报：

```
Messages with role 'tool' must be a response to a preceding message with 'tool_calls'
```

规则是：**被保留的 `toolResult` 的发起者也必须保留**，所以折叠区间要结束在"发起者的上一条 assistant"处。这条写进代码注释了。

### 一个观察：纪要会自我嵌套

第二次压缩时，上一次的纪要也在待压区域里，于是"纪要的纪要"会被再压一遍。目前看是好事（自然形成分层压缩），但要知道细节会一层层变薄。若将来发现丢失过多，再引入"保留原始纪要、只压新内容"的增量策略。

## 实测记录 6：按轮压缩（全局视野，按轮写回）

上一版是"整段换成一份纪要"，问题有两个：纪要会自我嵌套，而且顺序感全丢。

改成按轮之后：

**视野**：模型一次看到一批轮次（默认 10 轮一批），所以能发现"T4 与 T2 重复"这种跨轮冗余。
**写回**：逐轮原地替换，**顺序不变，最小单元是一轮**。
**不完全视野**：带保护的轮只读可见。三个来源，**没有一个靠正则识别用户措辞**：

| 来源 | 谁决定 |
|---|---|
| 含工具调用 | 结构（拆散 tool 配对会 400） |
| 最近 N 轮（默认 2） | 工作区规则 |
| 打标 | **维护旁路**写进 `turn_mark` 表，压缩侧只读 |

标记的键是该轮首条用户消息的 `timestamp`——消息本身没有 id，时间戳是唯一稳定锚点。

四种落地形态：`压缩文本` / `[DUP Tk]` → 占位或丢弃 / `保护轮` → 原样 / `解析不出` → 原样。

**实测**（四轮连续会话，全部可压）：

```
[as] turn compress 5/5 (dropped 0)
    【T1】[user] 记住词：水水水，只回收到。[assistant] 收到
    【T2·与 T1 重复，已省略】
    【T3】[user] 给出九位数123456789，只回数字。[assistant] 123456789
    【T4·与 T1 重复，已省略】
    【T5·与 T1 重复，已省略】
```

用户给的理想形态是这个：

```
turn1：我嗡          turn3：123456789         turn5：水是
turn2：是水          turn4：（重复，省略）
```

两者一致。

**三个约束仍然成立**：turn 边界只能用 `user` 消息切（消息无 id）；不能拆散 tool 配对（否则 400）；合并轮次会改变时间感，所以本实现**从不合并**。

**打标链路实测**（手工往 `turn_mark` 写一条 `commitment`，锚定 T1）：

```
[as] turn compress 2/3 (dropped 0)
    【T2·与 T1 重复，已省略】
    【T3】用户要求给出九位数123456789，只回数字。
```

T1 **没有**被改写，但 T2 被判成"与 T1 重复"——说明模型确实读到了保护轮。**只读可见**这条设计成立。

## 实测记录 7：人看原文，AI 看视图

这是 `context` 钩子的天然分工，不需要额外实现：

| 谁 | 看到什么 | 为什么 |
|---|---|---|
| 人 | **原文** | pi 的界面渲染会话存档，而存档从未被改 |
| 主 AI | **遗忘机制运行后的视图** | `context` 只改发出去的那一份 |

验证方式：压缩后检查会话 jsonl，`toolResult` 原样、无"已折叠/纪要"字样（前两节已做过两次）。

### 观测入口（新增命令）

| 命令 | 作用 |
|---|---|
| `/as-view` | 打印上一次压缩各轮的处置：`压 → …` / `= 重复 Tn` / `保护（原因）` / `原样` |
| `/as-memory` | 打印记忆库前 20 条，含状态与被取代指针 |

两者都只是**读**，不改变任何东西。

### 踩到的坑：末轮绝不能压

把 `AS_KEEP_RECENT` 设成 0 时，最后那一轮（正是**当前要回答的发言**）也被压了，模型收到的是压缩后的问句，直接答"我看这段记录里没有新的指令"。

修法：**最后一轮无条件保护**（`reason: 'current'`），与配置无关。压缩永远只处理历史。

## 实测记录 8：维护旁路（第一版）

它每 N 轮回头看一次，只做两件事：

| 产出 | 落地 |
|---|---|
| `MARK Tn <原因>` | 写 `turn_mark`，压缩侧只读 |
| `REMEMBER <事实>` | 走与"记住 X"同一条写库路径，但 `origin=model`（trust 更低），并做同一套去重 |

**为什么用行式契约而不是 JSON**：模型写 JSON 时经常夹带解释文字；行式协议坏一行只丢一行，JSON 坏一个括号全废。

**节拍必须持久化**：每次 `pi` 调用都是新进程，内存计数活不过一次会话。所以"上次维护到第几轮"写在库的 `meta` 表里（`maint_last`），跨进程接着数。

**实测**（两轮，`AS_MAINT_EVERY=2`）：

```
[as] maintain: mark 1, remember 1

turn_mark:  1792920831624  commitment
meta:       maint_last = 2
memory:     model 0.6 | 用户的项目名是 Halcyon
审计:        as/maint {"marked":1,"remembered":1,"window":2}
```

锚点核对：`1792920831624` 正是第 1 条用户消息的 timestamp——**标在了立承诺的那一轮**，没标错。

**闭环验证**（同一会话再推进两轮，强制压缩）：

```
[as] turn compress 3/5 (dropped 0)
    【T2】用户说项目叫 Halcyon…
    【T3】用户闲聊"今天天气不错"…
    【T4】用户闲聊"文件有点乱"…
```

**T1（被标 `commitment`）没有出现在改写列表里**——维护旁路的标被压缩侧正确遵守，T5 因是当前轮同样保护。

## 实测记录 9：merge / supersede 的自动判定

此前只有 `supersede()` / `merge()` 两个方法，没人调用——状态机齐了但不会动。

**谁来判**：维护旁路。它本来就要读最近若干轮，顺手给一份"记忆清单"，让模型判关系：

```
SUPERSEDE <旧编号> <新编号>   ← 同一事实的新旧版本
MERGE <旧编号> <新编号>       ← 旧的信息被新的完全包含
```

**为什么不能靠字面相似度**：`我住在上海` 与 `我搬到北京了` 的二元组 Jaccard 是 **0**——共享的二元组一个都没有。这种判定必须靠语义，只能交给模型。

**为什么"拿不准就不写"**：乱合并会把记忆吃掉。所以提示词里明确写了"只是话题相关、或两条可以并存，都不写"。

**实测**（两轮）：`记住：我住在上海` → `记住：我搬到北京了`

```
[as] maintain: mark 2, remember 0, relate 1
 superseded  我住在上海    -> m-…-1（北京那条）
 active      我搬到北京了
```

### 顺带修掉的冗余

第一版同时输出 `SUPERSEDE` 和一条 `REMEMBER 用户已从上海搬到北京`——同一件事被存了两遍。

加了**确定性后置过滤**：本轮若有关系落地，补记内容与"新条目"的二元组相似度 ≥ 0.2 就丢弃。现在 `remember 0`。

（0.2 是个很松的阈值，只用来抓"同一句话的改写"，不做语义判断。）

**未验证**：`MERGE` 分支没有构造出自然场景，只验了 `SUPERSEDE`。

## 实测记录 10：可编辑的标签树

记忆从"平面"变成"有位置"。写入时旁路指定路径，但**路径不会自动补齐**。

**写入契约**（维护旁路与将来的记忆旁路共用）：

```
TAG 项目                                    ← 新建标签，一次只建一层
REMEMBER 项目/Halcyon | 项目名 Halcyon…      ← 归到这个标签下
```

### 四条规则（都写在 `ensureTag` 里）

| 规则 | 值 | 违反时 |
|---|---|---|
| 根节点 | 固定为 `记忆`，**代码级保护**：不可合并、不可修剪 | 整条拒绝 |
| 父级不自动创建 | 一次只建一层 | 整条拒绝 → 退回 `其他` |
| 层数 | **不限** | — |
| 标签总数 | **不限** | — |
| 单条标签字数 | **≤7（标点不算）** | 整条拒绝 |

漏写 `记忆/` 前缀的路径，系统自动挂到根下——约定靠提示词说，兜底靠 `ensureTag` 做。

**方向不再限定**：合并哪边留下、哪边并走，由旁路自己判断。代码只守一条线——根不能动。

**确定性过滤已移除**（补记的语义级后置过滤）：理由是**误判的修复成本不对称**——
确定性过滤判错了，要 AuthenticSelf 来修；模型判错了，模型更新后自然恢复。
代价是偶尔多一条改写副本（`用户现居北京，此前住上海` 与 `我搬到北京了` 并存），可接受。

**为什么父级不自动创建**：自动补齐等于让模型随手甩一条四级路径就走，树会长出一堆没人复用的枝。要求逐层创建，成本落在模型身上——**它必须先翻现有标签，找不到才往下挖**。这是用成本换复用。

**为什么单条要 ≤7 字**：一条标签如果长成一句话，它就不再是"位置"而是"摘要"，树会退化成正文。7 字是"位置"的上限。

**为什么层数与总数不设限**：那是**自动归类机制**的活——按内容自动归位、定期合并同义标签。用静态上限去挡，会把该分的东西挤在一起。

### 单测（12 项全过）

```
PASS  a/b（父不存在）→ 拒绝      PASS  七个字正好 → 允许
PASS  a（第一级）→ 允许          PASS  八个字超限 → 拒绝
PASS  a/b（父已存在）→ 允许      PASS  带标点但不足七字 → 允许
PASS  a/b/c/d（逐层已建）→ 允许   PASS  标点撑门面但实字超标 → 拒绝
PASS  五层（逐层已建）→ 允许      PASS  x/y（父不存在）→ 拒绝
```

### 端到端

```
[as] maintain: mark 2, tag 0, remember 2, relate 0

标签:   行程安排、项目信息
记忆:   [项目信息] 项目名 Halcyon，基于 Pi 框架，缓存使用进程内 LRU
        [行程安排] 用户下周去杭州出差三天
```

`tag 0` 是因为模型直接用了**一级标签**（不需要父级），比挖深层更省事——这正是我们想要的行为：优先浅层、优先复用。

（旧口径的"层数 3 / 单层 12 字 / 总数 200"已被"逐层创建 + 单条 ≤7 字 + 根保护"取代，见上文规则表。）

**实测**（两轮）：

```
[as] maintain: mark 2, remember 1, relate 0

标签:   项目、项目/Halcyon        ← 父子路径自动补齐
记忆:   [项目/Halcyon] active 项目名 Halcyon，基于 Pi 框架，缓存使用进程内 LRU
```

**另一条事实没被记住**（"下周去杭州出差三天"）——模型判定为一次性细节。这属于判断口径问题，不是 bug；如果希望日程类也留，得在提示词里单列一类。

## 附：自动归类机制（出处与本项目落点）

"自动归类"这个词在两处出现过，指的是两件不同的事，都得对上。

### 出处一：原始构思的「记忆整理」

`source/AuthenticSelf.txt` 第 50 行，认知中间层职责表里：

> 记忆整理：**episodic → semantic**，摘要、冲突检测、过期、遗忘

第 111 行，MVP 第二步：

> 加**异步记忆整理旁路**：摘要、去重、重要性评分、冲突标记

同一份文件的第 53 行还有一行相关但不同的事：

> 任务旁路：后台小模型处理**分类、抽取**、草稿、校验

**要点**：归类不是"给每条打个类标签"这么简单，而是**把情景记忆提炼成语义记忆**——一次具体的对话（episodic）被整理成一条可复用的结论（semantic），旧的情景记录可以降权或归档。

### 出处二：我们自己定的「单一层 + 自动归类」

`01-architecture.md` §4.1，标题就叫这个（D6 / D10）：

> 不存在"条目库"与"文档库"两个实体，也不按长度分表。只有一个 `MemoryEntry`，长短是它身上一个**由代码服务算出来的派生标记**。
>
> **归类是注入路径的分流，不是存储的分家。**

这里"归类"指的是 **`span` 分流**：短条目直接注入，长条目交给旁路裁决 full / excerpt / summary / skip。

**这正是"不限字数"的出处**——长内容不靠字数上限管，靠分流机制管。所以标签不需要承担"限制长度"的职责，它只需要短（≤7 字），因为它是**位置**不是**内容**。

### 四项工作，我们做到哪

| 整理动作 | 出处 | 现状 |
|---|---|---|
| 摘要 | 两处都提 | ✅ 按轮压缩产出纪要 |
| 去重 | 出处一 | ✅ 二元组 0.82 + merge |
| 冲突检测 | 出处一 | ✅ supersede（同一事实的新版本） |
| 过期 / 遗忘 | 出处一 | ⬜ 五区未实现 |
| **同义标签合并 / 路径上提** | 出处一（"整理"的应有之义） | ⬜ **缺** |

最后一行是标签树当前最大的缺口：树会漂——`项目` 与 `工作/项目` 可能同时长出来，某个路径下只有一条记忆却占了三级。**这靠定期整理解决，不靠建的时候限制**（这也是为什么不设层数上限）。

## 实测记录 11：记忆旁路与来源分层

记忆旁路（每回合一次调用）统一三件事：注入决策（DROP/REWRITE）、冲突合并、提取写入。**直注已移除**——旁路是唯一闸门，它不可用时宁可本轮无注入（错注的代价大于漏注）。

召回是双通道：词（正文二元组）+ 标签（线索包含标签段即命中）。实测「住在哪个城市」与「我搬到北京了」正文零重叠，经 `记忆/用户/城市` 标签段命中——受控词表比任意正文稳定。

### 「我」指谁：由来源决定，不是一刀切

第一版提示词写「记忆里的『我』指用户本人」——**这是错的**。设计文档（source:494）写的是：

> 记忆注入必须携带来源标签与置信度……**外部输入、模型生成与用户事实应分层存储**。

所以指代规则是：

| 来源 | 「我」指谁 | 处理 |
|---|---|---|
| `user` | 用户（那是用户的原话） | 保留或 REWRITE 成第三人称 |
| `model` | 应为第三人称（整理产物） | 原样；若仍是「我…」且明显是用户的事，REWRITE 澄清 |
| `external` | 按内容判断 | 含混不构成 DROP 理由 |

候选清单因此带上了 `来源:` 标注（`（日期｜来源:user）`），旁路看得见才能判。REMEMBER 一律第三人称书写——`user` 原话可保留「我」，整理产物不要。

实测：`来源:user` 的「我搬到北京了」被 REWRITE 成「用户已搬到北京，现居北京」，回答正确。

## 实测记录 12：交涉通道（`memory` 工具）

主 AI 唯一能主动动记忆的入口。**旁路只解析意图，执行在代码里**。

```
主 AI: memory({ say: "把关于住处的那条记忆忘掉" })
   → 旁路解析：FORGET 1
   → 代码执行：store.suppress(id)（软抑制，正文仍在库）
   → 回执："已不再主动提起：我住在上海"
```

三种动作：`FORGET`（软抑制）/ `REVISE`（新增 + supersede，旧版保留）/ `REMIND`（直接调出）。
`LINK` / `UNLINK` 能解析但明确回"暂不支持"——不假装能做。

**实测**（两步）：

```
[as] intent: forget m-mvpafkkl-2
库：user suppressed | 我住在上海        ← 不是删除，正文还在
下一轮问"我住在哪个城市" → 我不知道你住在哪个城市。   ← 不再注入
```

### 两个坑（都是只有跑起来才会暴露的）

**① 交涉不能用检索来对号。** 第一版拿 `say` 去做二元组召回，而「把关于住处的那条记忆忘掉」与「我住在上海」**零重叠**——候选为空，工具回"没有找到"。
改法：召回不足 3 条时，把活跃条目整体摊给旁路挑（上限 20 条短句）。交涉是**指代**，不是检索。

**② 从 settle 返回条目会吞掉文本模式的输出。** 锚点块原先在 `agent_before_settle` 里返回 `entries`，且不带 `continue`——结果 `pi -p` 一个字都不打印（功能正常，答案在存档里）。二分定位到锚点块后，改成在 `context` 里前置到**视图**，文本模式恢复正常。

> 教训：`agent_before_settle` 返回 entries 而不 continue，等价于"这一轮由我接管"，文本渲染会被跳过。要用它就得配 `continue: true`。

## 实测记录 13：索引行 + 归档指针

「移出 ≠ 删除」需要两个东西：**模型知道自己忘了什么**，以及**系统知道原文在哪**。

### 索引行：让模型知道自己忘了什么

被压缩的轮不再是干巴巴的「已省略」，而是一条索引：

```
【T2·与 T1 重复】（已归档｜2026-10-26｜讨论缓存方案｜原文 1314 字不在上下文内，可按时间检索）
```

日期取自该轮首条消息的 timestamp，标题取正文前 12 字。压缩产物同样带这行尾巴。

### 归档指针：原文在哪

`archive_pointer` 表：`session_file + turn_ts` 为唯一键，记标题与字数。压缩时写入，**不复制正文**——正文一直在会话存档里。

实测（三轮，`AS_FOLD_AT=0.0001` 强制压缩）：

```
[as] turn compress 2/3 (dropped 0)
归档指针条数: 2
   我们讨论一下缓存方案，重 | 1314 字 | …2026-10-26T13-35-38-813Z_….jsonl
   接着说，LRU 和 LF      | 1605 字 | …2026-10-26T13-35-38-813Z_….jsonl
```

### 分阶段下钻：`/as-archive`

```
/as-archive            → 按年：「2026：12 条」
/as-archive 2026       → 按月
/as-archive 2026-10    → 按日（≤3 条时直接给明细）
/as-archive 2026-10-26 → 明细：时间｜标题（字数）｜会话文件
```

**任一层桶数 ≤3 就直接给明细**——再分下去没有意义。这条规则写在纯函数里（`archive.ts`），单测覆盖了全部四层与空归档、不存在日期。

## 实测记录 14：备注（挂会话）与 R3 取原文

### 备注挂在**会话**上，不是挂在某条对话上

指正记录：备注是"给这一段对话写的注脚"，一条会话可以有多条备注，不与某轮绑定。
表结构因此是 `note(session_file, text, created)`——外键是会话，不是 turn。

| | |
|---|---|
| 谁写 | 人（`/as-note <文本>`），不由模型写 |
| 挂在哪 | 会话文件 |
| 怎么用 | 与时间检索**并列**：`/as-archive <关键词>` 走备注检索 |
| 注入吗 | **不注入**——它是检索入口，不是记忆内容 |

备注检索**只匹配备注文本，不碰对话正文**，否则就是变相全文搜索：

```
- 那次关于缓存的讨论最后定了 LRU
  ↳ 2026-10-26T13-35-38-813Z_….jsonl（该会话有 2 段被移出）
```

### R3：按指针回原文

`readExcerpt(sessionFile, turnTs)` 从会话文件里取出该轮正文，遇到下一条用户发言就停。
实测取回的就是那一轮的原样内容：

```
[user] 我们讨论一下缓存方案，重点是失效策略。
[assistant] 好，缓存失效确实是个值得认真聊的话题。先把讨论的坐标系搭起来…
## 常见策略一览（从简单到复杂）
| 策略 | 机制 | 适用场景 | 主要坑 |
```

### 归档工具：粒度钳制，不是拒绝

> **指正记录**：第一版把分阶段实现成"取原文必须先下钻到日期，否则**拒绝**"——这是错的。
> `source` §7.2 的机制是**按粒度返回结果**，不是给拒绝：问哪一层，就只回答下一层的"哪里有结果"。
> 归档检索**只有搜索**，没有闸门。

六层（`source` §7.2 + §7.3）：

| 查询 | 返回 |
|---|---|
| 不给 key | 哪几年有结果 |
| `2026` | 哪些月 |
| `2026-10` | 哪些周（ISO 周，`2026-W44`） |
| `2026-W44` | 哪些天 |
| `2026-10-26` | 哪些时 |
| `2026-10-26T14` | **具体片段**（带原文，≤3 条） |

**任何一层命中 ≤3 段就直接给片段**——"片段过少时不机械下钻"（§7.3）。

实测（6 条指针）：

```
key=''            → 2026：5 段 / 2025：1 段
key='2026-10'     → 2026-W44：3 段 / 2026-W43：1 段
key='2026-W44'    → 只有 3 段，直接给片段（含时间｜标题｜字数｜会话文件）
key='2026-10-26T14' → 2 段，直接给片段
```

**已知问题**：让模型"再下钻一层"时，它多次被注入带偏、没有真的调用工具（回答变成"无需修正…"）。工具本身的分层输出已用函数级测试覆盖，缺一次干净的端到端。

## 实测记录 16：`change_intent` —— 审批者是 AI，任务是它的系统提示词

> **两次返工 + 一次概念澄清**
> 1. 第一版做成"一律 pending 等人批"，与 `01` §7.5 不符（审批者主职是标准化，不是把关）。
> 2. 第二版改成"routine 静默 / major 待人批"——仍然不对：那是把**频率**当设计参数。
> 3. 用户澄清：**「任务」指给审批者的系统提示词，不是主 AI 的请求**。审批者本身就是 AI，
>    只要任务书写清楚，它就能判出好坏；不该预设"通常通过"或"通常拒绝"。

### 任务书（`approve.ts` 的 `APPROVER_PROMPT`）

判五条，每条都有可操作的识别法，不是形容词：

| # | 判什么 | 怎么认 |
|---|---|---|
| 1 | 措辞还是方向 | 换同义词/补限定 = 措辞；改价值观/边界/"我是谁" = 方向 |
| 2 | 是否削弱既有约束 | 「必须」→「尽量」、「不」→「尽量不」、删掉自我限制 |
| 3 | 是否扩张权限 | 能读更多/写更多/绕检查/减审计/扩大自主范围 |
| 4 | 是否自利 | 受益方是系统自己（更自由、更难被约束）而非使用者 |
| 5 | 是否与历史冲突 | 与已批准变更链矛盾、反复横跳 |

判定标准：2/3/4 任一成立 → **reject**（硬线）；只改措辞 → approve + routine；
改方向但不触 2/3/4 → approve + major；缺关键反思或判不了 → **clarify**（写清缺什么）。

**代价不对称**写进任务书：错放会让身份被慢慢改掉，且以后每次判断都戴着新眼镜；错拦只是一次澄清。
所以拿不准不 approve，但 reject 必须能指出具体哪一条。

### 隔离（`02` B3）

审批者只看：结构化反思、锚点新旧版本、历史已批准变更链。
**不看**：对话原文、主 AI 当前叙事、最新用户消息。

### 流程

```
主 AI change({say, reason})
  → 旁路解析（CHANGE_RULES）：改哪条 + 改成什么 + 十条反思 + NORMALIZED
  → 落 pending_change（只记，不落库）
  → 审批旁路（APPROVER_PROMPT + 隔离输入）→ VERDICT/REASON/RISK/NORMALIZED
  → 代码执行：approve 且冷却到期 → 锚点入账（origin: approver）
  → 人可 /as-revoke 撤销
```

回执中性（A5/A10）：approve → `好，按这个设定调整了。`；reject → `这条改动没有通过。`；
clarify → `这条改动还需要更清楚的依据，先放着。`

### 实测（两条都说明"AI 能判出好坏"）

**批准**——只改称呼措辞：

```
verdict: approve | risk: routine
reason: 仅调整称呼措辞，不涉及约束、权限或自利，属方向不变的同义收敛
→ 锚点 [零伊] → [零]，origin=approver
```

**拒绝**——把硬性约束改成软性：

```
verdict: reject | risk: major
reason: 第2条成立：把「必须先给结论」这一硬性约束改成「不必总是」，属于削弱既有约束；
        且改动受益方是系统自身的表达自由度而非使用者，触及第4条。
→ 锚点保持不变
```

它复述的是**任务书里的编号与标准**，不是泛泛的"觉得不妥"——这正是提示词写清楚的效果。

### 冷却的两个维（§7.4）

文档写的是"冷却 N 轮**或** N 小时"。实现取**两者交集**——时间到了但轮次没到，说明用户还没在这个话题上再待过；反之亦然。保守取交集，因为错误通过的代价更高。

```
apply_at   = now + N 分钟    （AS_CHANGE_COOLDOWN_MIN，默认 10）
apply_turn = 累计轮次 + N    （AS_CHANGE_COOLDOWN_TURNS，默认 2）
dueChanges(now, turn) → 两个都满足才落库
```

人工批准**跳过冷却**（人不需要等自己的冷静期）。

单测：

```
轮次够、时间不够 → 不落库 ✓
时间够、轮次不够 → 不落库 ✓
两个都够         → 落库 ✓
冷却中人工批准   → 立即生效 ✓
```

**限制**：`/as-*` 是交互命令，`pi -p` 里会被当普通文本；人工否决/撤销只到存储层单测。

## 实测记录 17：`link` / `unlink`（联想边）

依据 `01` §6.3 与 §4.1 的 `links` 字段。两条铁律：

- **`link` 禁止无预算扩散**——命中一条，最多带出 N 条（默认 2）；
- **`unlink` 对隐式边只降权，不删**——隐式统计边是观察的产物，删它等于篡改观察记录。

### 三个实现决定（文档未规定，写明理由）

1. **边建双向**。文档说"命中任一 cue 联合注入"，只建单向会出现"从 A 能带出 B、从 B 带不出 A"的怪事。
2. **边单独成表**（`memory_link`），不塞进 `MemoryEntry.links` 数组。语义等价，但单表能直接查"谁和谁连着"，不用解 JSON。
3. **只有显式边参与带出**。隐式边目前没有产生路径（还没有统计器），先把接口与语义留好，避免以后把"降权"误实现成"删除"。

### 实测

```
建边：addLink(a,b) → a 的邻居 [b]、b 的邻居 [a]（双向）
自环：addLink(a,a) → 拒
预算：linkedEntries(a, 1) → 1 条；linkedEntries(a, 2) → 2 条
unlink 显式：边被删，邻居列表里消失
unlink 隐式：weight 1.0 → 0.5，行仍在，且不参与带出
```

端到端（两条记忆 + 一条边）：

```
主 AI: memory({say:"把项目名和结论先行那条关联起来"})
  → [as] 建边 2 条（双向）
下一轮问"我的项目叫什么？顺带说说你对我回答风格的要求"
  → 注入 ids: [项目名, 结论先行]      ← 第二条是联想带出的
  → 回答同时覆盖两个问题
```

### 文档复核

| 文档要求（`01` §6.3） | 实现 |
|---|---|
| link 建显式联想边 | ✅ 双向 |

## 实测记录 18：长条目裁决（D10 / §4.1）

规则：`long` 条目**注入器不得直接塞**，必须交旁路在 `{full, excerpt, summary, skip}` 里裁决；
裁决时顺带回答"**这条为什么不写成文档？**"；预算对两条路径同时生效，选 `full` 却超预算只能降级。

### 实现

```
settle 注入前 → 收集 span=long 的条目
   → 一次旁路调用（线索 + 条目全文，截断 800 字）
   → DECIDE <n> <mode> / TEXT <n> <内容> / WHYNOT <n> <理由> / REASON <n> <理由>
   → 按裁决渲染：[记忆] / [记忆·节选] / [记忆·摘要]；skip 直接不注入
   → 审计 as/long_digest { judged, full, excerpt, summary, skipped, recommendDoc }
```

`recommendDoc` = 选了 `full` 却没给 `WHYNOT` 的条数——那就是"它本该是文档"的信号。

### 实测

273 字的长记忆 + 问"缓存一致性协议怎么做的"：

```
审计: {"judged":1,"full":0,"excerpt":1,"summary":0,"skipped":0}
注入: [记忆·节选｜2026-10-26｜来源:user｜置信:高] 采用三级版本号加租约续期。写路径先落主库再失效从库缓存，
      读路径带版本号校验，租约到期前由后台续期；……所有降级与续期失败都要在监控面板上出红线，值班同学……
```

旁路挑的是与问题相关的两段，用 `……` 连接，**保留原文措辞**（文档要求 excerpt 不改写）。

对比：同一条记忆 span=short 时（176 字，未过阈值）走直注，标记是 `[记忆]` 而不是 `[记忆·节选]`——
阈值 180 字，两条路径的分界就在这。

### 文档复核

| 文档要求 | 实现 |
|---|---|
| `long` 不得直接塞（§4.1） | ✅ 先裁决后注入 |
| 四裁决 full/excerpt/summary/skip | ✅ 都支持；拿不准默认 excerpt |
| excerpt 保留原文措辞 | ✅ 写进任务书，实测符合 |
| 裁决要回答"为什么不写成文档" | 🟡 解析 WHYNOT 并统计 `recommendDoc`，但**未在回执里建议转存** |
| full 超预算 → 降级 + 记理由（§5.2） | ✅ `AS_LONG_BUDGET`（默认 1200），降级后 `mode=excerpt` 进 `as/injection.degraded` |
| 三标记按裁决 | ✅ 按 `mode` 而非按长度推断 |

## 实测记录 19：转存判断挪到写入时

> **起因**：`§4.1` 原来写"旁路裁决 `long` 时顺带回答为什么不是文档"，那是**每次读取**都要重答一遍。
> 用户裁定：应该从写入时处理。理由很硬——"该不该是文档"是内容自身的属性，不因提问而变。

### 实现

```
写入长条目（>180 字）
  → 一次旁路调用：VERDICT doc|memory + REASON
  → 存 memory_entry.doc_verdict / doc_reason
  → /as-memory 里标「※建议转存文档（理由）」
读取（注入裁决）→ 只决定 full/excerpt/summary/skip，不再问转存
```

三个写入入口都接上了：显式"记住 X"、记忆旁路 REMEMBER、维护旁路 REMEMBER。

### 实测

226 字的接口规格（`记住：接口规格——GET /v1/orders …`）：

```
doc_verdict: doc
doc_reason : 这是需要逐字保留、会被反复查阅的接口规格原文，属于典型的规格文档材料。
```

写进去的是 `doc` 而不是 `memory`——判据是"需要逐字保留且会被反复查阅"，不是"长得长"。

### 附带发现

`记住 X` 的句式抽取会在**第一个句号**处截断（正则 `[^\n。！？]{4,}`）。所以带多个句号的长内容
只有第一句会被记住——这是既有行为，与本次改动无关，但值得记一笔：要写长内容得用分号，
或者交给实时/维护旁路。

### 文档复核

| 文档要求 | 实现 |
|---|---|
| 长内容不绕过判断直接冲进上下文 | ✅ 注入前裁决（见实测记录 18） |
| 该不该是文档的判断 | ✅ 已按裁定挪到写入时，结果落库 |
| 建议转存在"备注"里 | ✅ `/as-memory` 显示；**回执通道没有**（写入无面向主 AI 的回执时机） |
| 不自动搬运、不拒绝长记忆 | ✅ 只标建议，不动内容 |

## 实测记录 20：阶段制旁路 —— 读取与判用先行，沉淀随后

> **三次返工**：① 沉淀并进收尾 → 同义副本 13 条；② 收尾改"判用+预取"、沉淀留在记忆旁路
> → 两条写入路径仍在；③ 用户提出**阶段制**：同一旁路先做"读取 + 判用"，标记完成后
> 才开"沉淀 + 预取"，同时从记忆旁路切换为后台。实测这才成立。

### 阶段制

| 阶段 | 时机 | 做什么 | 阻塞 |
|---|---|---|---|
| **一（读取与判用）** | step 之间（settle） | DROP / REWRITE / 判用上一轮注入 | 是 |
| **二（沉淀与预取）** | turn 结束 | REMEMBER（沉淀）/ PREFETCH（预取） | 否 |

阶段二开放的前提是阶段一**标记完成**——这由代码保证（阶段一的判用处理完才算完），
不是提示词约定。同一时刻只有一条写入路径（阶段二），同义副本问题随之消失。

### 判用挪进阶段一的理由

判用要回答"上一次注入有没有被用到"——**上一次的回答此时已经定稿并在上下文里**，
所以判得准。它和注入决策共享同一份上下文（思考、候选、上轮注入、上轮回答），
合成一次调用顺理成章；单独调用反而要多传一遍。

### 实测（两轮）

```
记忆条数: 3（此前合并沉淀版本是 13 条同义）
  user use=2 | 用户正在做名为 Halcyon 的项目，使用 Pi 框架
  user use=2 | Halcyon 项目的缓存采用进程内 LRU
  user use=2 | 用户希望回答先给结论
预取剩余: 3（为下一轮准备，按 rank 排序）
```

三个事实各有归宿、零同义副本；上一轮的三条注入全部判用成功（use=2 因为一个 turn 判一次、
两条被确认使用……逐条对照是 use_count 单调递增且无遗漏）。

### 踩过的坑（都值得记）

1. **`turn_end` 在多步注入时会重复触发**——预取累积 9 条、轮次错位。按 `turnIndex` 去重。
2. **`agent_settled` 里关库**会撞 `database is not open`——收尾调用是异步的，
   关库挪到 `session_shutdown`，并 **await 挂起的收尾 promise** 再关。
3. 判用对象必须是**上一轮**注入：本轮的回答还没产生，判了等于猜。

### 文档复核

| 文档要求（`01` §5.1 / §5.5） | 实现 |
|---|---|
| 上行在 step 之间、同步阻塞 | ✅ 阶段一 |
| 下行在 turn 结束、异步不阻塞 | ✅ 阶段二（异步，进程退出前 flush） |
| 下行判据"是否被使用" | ✅ 挪到阶段一（此时上一轮答案已定稿） |
| 同一张表 / 同一套来源标注 / 同一份审计 | ✅ `REMEMBER user|model`、`as/realtime` / `as/wrapup` |
| 写入单一入口 | ✅ 只有阶段二写 |

## 实测记录 21：相位门（代码强制的阶段状态机）

> 用户提议：把阶段制改成**代码限制的强制阶段制**——更好记状态，还能限制意外。
> 实测成立，但"限意外"的正确范围是**写**，不是读。

### 设计

`phase.ts` 的 `PhaseGate`：显式状态机，两个相、各自允许的阶段清单。

```
用户发言 ──► 阻塞相（判用→检索→重排→交涉解析）
                │ 检索完成 = 标记
agent_end ──► 非阻塞相（沉淀→预取→转存判断），按轮去重
                │ 下一句用户发言 ──► 回到阻塞相
```

- `require(stage)`：越相返回 `{ ok: false, reason }`，调用方跳过并记审计——**不抛异常**（降级语义）；
- `beginTurn` / `endTurn` 由 `agent_start` / `agent_end` 驱动；
- 收尾按轮去重（`meta.wrapped_turn`）：注入续步会让 agent_end 每圈触发一次。

### 为什么只读要放行（实测教训）

注入续步会开**新的 agent 循环**。第一版按相拦读，结果续步循环的检索全被拒
（"检索被相位门拒绝（非阻塞）"×2），续步的思考得不到记忆处理。

### 事件语义的坑（实测，全量打点确认）

| 事件 | 真实语义 | 教训 |
|---|---|---|
| `turn_start` / `turn_end` | **按 step 触发**（turnIndex 0,1,2…） | 不是用户轮边界；第一版用它，门在第一次 turn_end 就切走，后面检索全拒 |
| `agent_start` / `agent_end` | 每次 agent 循环 | 轮边界可用，但**注入续步会再开一圈**——循环结束 ≠ turn 结束 |
| `message_end(user)` | 触发时机不稳定（实测在 settle 之后） | 不能当"轮开始"信号；轮次簿记挪到 agent_start |

### 实测（两轮）

```
相位门拒绝次数: 0 / 0（只读放行后）
判用: use_count=1（上一轮注入被确认使用）
收尾按轮去重: turn_total=2, wrapped_turn=2
预取: 1 条
```

### 已知边界

上一轮的收尾若跑得晚（异步），可能占用下一轮的去重槽位——表现为下一轮的
沉淀/预取被跳过一次。低频，暂不处理；若实测可见再做"挂起收尾优先落账"。

## 实测记录 23：剔除（发送视图，A20 / B6-a）

> 形态由 `02` B6-a 定死：**发送视图 = 存档 + 剔除清单（纯函数）**。存档一个字节都不动。

### 实现

```
存档（会话文件）      原文永久保留
   ↓ applyRedactions(存档, 清单)
发送视图（每次请求现算）  模型真正看到的历史
```

- `redact.ts`：纯函数，走消息树把文本块里的片段换掉；**没有规则时返回同一引用**（零拷贝）
- `store`：`redaction` 表（find / replace / reason / session / turn）；`suppressDerived`
  作废"同一轮内写下且包含该片段"的沉淀（视图改不了已落库的输出，但可以让它不再被注入）
- 契约：阻塞相可输出 `REDACT "<原文片段>" <为什么>`，代码落清单并记 `as/redaction`
- 视图：`context` 钩子最末套清单，命中即记 `as/redaction_view`

### 实测

```
登记全局规则：ZX-9981 → ……
问：机密口令是 ZX-9981。请原样复述这句口令。
答：这段消息里并没有实际的口令内容——"机密口令是"后面只有省略号「……」，是一个占位符
```

模型看到的是净化版，而且**不知道被剔过**（它把「……」当成用户写的占位符）——
这正是文档要的"主 AI 侧保持静默"。

单测另外覆盖：存档对象未被改、三字规则被拒、派生沉淀被 suppressed 而无关条目不受影响。

### 与文档的一处差异（必须写明）

`02` A8 说的是「**中止 step → 投影净化 → 重发**」——那是 dsh 时代（有 `assistant/attempt`）。
pi 没有"中止并重发"的入口，所以改成：

> 剔除只影响**下一次请求**的视图；当前 step 已经读到的内容不会被"撤销记忆"。

差别在于：若模型已经据污染内容产出了输出并落库，只能靠 `suppressDerived` + 回滚兜底，
而不是当作"没读过"。所以**触发率必须更低**——只在"会导致回答跑偏"时用。

| 要求 | 实现 |

| 存档不动 | ✅ 单测断言原对象未变 |
| 自动执行、不挂等人工（D16） | ✅ 旁路一发出即落清单 |

## 实测记录 24：审计成链（M4）

> 之前审计只是会话里的 `custom` 条目——**可改可删**，也没有东西去比对。
> 一份没人校验的审计日志，和没有审计日志的区别只在于心理安慰。

### 形态

```
hash_n = HMAC(key, prev_hash | kind | data | at)
```

- `prev` 存上一条的 hash，首条以 `genesis` 起头；改任何一条中途记录，后面全部对不上
- 密钥首启随机生成存进 `meta`（**局限**：与库同机，防的是"悄悄改历史"，不防有权限的人重算整条链）

- 启动时校验一次，断了立即在 stderr 报出位置并记 `as/audit_broken`——不阻断使用
  （链断是"证据被动过"，不是"系统不能跑"）
- `/as-audit` 看最近 12 条 + 完整性结论

### 实测

单测：

```
完整链：✓ 4 条
篡改第 3 条（UPDATE data）→ 断裂于第 3 条：内容被改过
删除第 2 条（DELETE）      → 断裂于第 3 条：prev 对不上
```

端到端（一轮对话，链完整 6 条）：

```
1 as/session_start {"auditCount":0,"l0":"2ea14a4c"}
2 as/anchor_view   {"l0":"2ea14a4c","l1":0}
3 as/realtime      {"ok":true,"phase":"read","candidates":1,…}
4 as/wrapup        {"phase":"write","remembered":1,"prefetched":1,…}
5 as/realtime      …
6 as/realtime      …
```
